# BACKEND.md

Backend foundation for the Displaced Camps Management Platform — Supabase, PostgreSQL, Supabase Auth and Row Level Security.

**Phase 1 is the database, not the app.** The existing HTML + CSS + vanilla-JS frontend is untouched and still runs entirely on `localStorage`. Nothing was migrated to a framework, no page was rewired, and no mock data was replaced. What exists now is a schema the frontend can be pointed at in Phase 2.

## 2 · The migration map

The existing frontend is the source of truth. Every column below traces to a field the UI already reads.

| localStorage collection (`core/store.js`) | PostgreSQL |
|---|---|
| `camps` | `camps` |
| `users` (id, email, **password**, role, campId, status) | `auth.users` (identity + password) + `profiles` (role, camp, status) |
| `organizations` | `organizations` |
| `families` (`FAM-000001`, campId, headId, notes) | `families` (uuid PK + generated `reference_code`) |
| `displaced` (a person; every one belongs to a family) | `family_members` |
| — (`AID_TYPES` in `config.js`) | `aid_types` |
| `aid` (`{types[], familyIds[], organizationId, campId, date}`) | `aid_distributions` + `aid_distribution_types` + `aid_distribution_families` |
| `registrationRequests` | `registration_requests` |
| `documents` | `documents` |
| `messages` | `messages` |
| `notifications` | `notifications` |
| `store.preferences` | `user_preferences` |

Four deliberate shape changes:

1. **`displaced` became `family_members`.** In the frontend every displaced person already belongs to exactly one family, so a separate "displaced" table would have been the same rows twice.
2. **String ids became uuids.** `families.reference_code` preserves the human-facing `FAM-000001`, generated by a sequence and trigger. This replaces `selectors.nextFamilyId()`, which read the highest id in the browser and would hand two concurrent admins the same code.
3. **`aid.types[]` and `aid.familyIds[]` became junction tables.** Same data, queryable and referentially sound.
4. **Passwords left the application database.** `users.password` has no equivalent column anywhere; Supabase Auth owns it.

## 3 · Tables

Fourteen tables, all in `public`, all with RLS enabled.

| Table | Purpose | Notable columns |
|---|---|---|
| `camps` | a displacement camp | `name`, `governorate`, `status` |
| `profiles` | application identity for an `auth.users` row | `role`, `camp_id`, `family_member_id`, `status` |
| `families` | a household | `reference_code`, `camp_id`, `head_member_id` |
| `family_members` | a displaced person | identity, contact, shelter, health, economic, `is_orphan` (generated) |
| `organizations` | aid donors | `name` required; `phone` and `responsible_person` optional |
| `aid_types` | aid categories | `code`, `label_ar` |
| `aid_distributions` | a distribution event | `organization_id`, `camp_id`, `distributed_on` |
| `aid_distribution_types` | distribution → aid types | composite PK |
| `aid_distribution_families` | distribution → beneficiary families | composite PK |
| `registration_requests` | the approval workflow | `status`, `reviewed_by`, `family_member_id` |
| `documents` | file **metadata** | owner refs + Cloudinary columns, unused in Phase 1 |
| `messages` | displaced ↔ camp administration | `sender_id`, `camp_id`, `subject`, `reply` |
| `notifications` | per-account notices | `recipient_id`, `is_read` |
| `user_preferences` | settings-page toggles | one row per account |

Two derived views, both `security_invoker = true` so the caller's RLS still applies:

- **`family_member_facts`** — the SQL form of `selectors.personFacts()`: `age_years`, `is_child`, `under_1/2/3`, `is_orphan`, `has_chronic`, `has_disability`, `is_pregnant`, `is_breastfeeding`, `maternity_applies`.
- **`family_stats`** — the SQL form of `selectors.familyFacts()`: `members_count` and every member-characteristic count.

`members_count` is computed here and is **not** a column on `families`.

### Relationships

```
camps ──< profiles                    camps ──< families ──< family_members
                                                    │              │
                                        aid_distribution_families  │
                                                    │              │
organizations ──< aid_distributions ──<─────────────┘              │
                        │                                          │
                        └──< aid_distribution_types >── aid_types   │
                                                                   │
auth.users ──1:1── profiles ─────────────────────────────────────>─┘
                                                (family_member_id)

camps ──< registration_requests ──< documents
families / family_members ──< documents
profiles ──< messages, notifications, user_preferences
```

Camps and organizations use `ON DELETE RESTRICT` — they are protected while still referenced, matching `campInUse()` / `organizationInUse()` in the prototype. Families cascade to their members; deleting a person does **not** delete aid, because aid belongs to the family.

## 4 · Constraints and indexes

**Uniqueness**

- `family_members.national_id` — unique platform-wide. This is the duplicate-registration guard, and because it is global it also enforces "one national ID cannot exist in two camps".
- `registration_requests.national_id` — unique among requests that are not `rejected`, so an ID can be re-submitted only after a rejection.
- `profiles.role` where `role = 'super_admin'` — a partial unique index that makes a second Super Admin impossible.
- `camps.name`, `organizations.name`, `families.reference_code`, `aid_types.code`.

**Value constraints**

**17** enumerated types, one for every fixed vocabulary in `config.js`: `app_role`, `account_status`, `camp_status`, `request_status`, `gender`, `marital_status`, `parent_status`, `nationality`, `tent_type`, `governorate`, `work_status`, `income_source`, `family_relationship`, `document_category`, `message_subject`, `message_status`, `notification_type`. `tent_type` has exactly two values.

Check constraints cover national-ID format (9 digits), phone and email format, non-negative income and file size, sane birth and distribution dates, "a decided request records who decided it and when", "an approved request points at the person it created", "a reply has an author and a timestamp", "a document has at least one owner", and — the important one — **maternity flags may only be non-null on a female record**.

**Indexes**

Every foreign key column has a leading index (asserted by the test suite). Beyond those: `national_id`, `camp_id`, `family_id`, `role`, `status`, `created_at DESC`, `organization_id`, `distributed_on DESC`, and a composite `(camp_id, distributed_on DESC)` for the aid list.

Five partial indexes back the family filters — orphans, chronic cases, disability, pregnant, breastfeeding. Each covers a small minority of rows, so they stay far smaller than a full index.

## 5 · Authentication

Supabase Auth, email + password. No custom authentication, no password handling in application code, no password column anywhere in `public`.

```
auth.users  ──(id)──>  public.profiles  ──> role, camp_id, status
```

A trigger on `auth.users` creates the profile on sign-up:

```sql
insert into public.profiles (id, full_name, phone, role, status)
values (new.id, …, 'displaced', 'pending');
```

**The role is hard-coded.** `raw_user_meta_data` is user-editable and reachable from `auth.jwt()`, so a sign-up requesting `role: 'super_admin'` would otherwise be granted it. Elevated roles are assigned only by the seed script (secret key) or by the Super Admin through an `UPDATE` that the privilege guard below permits.

A displaced account is linked to its person record by `profiles.family_member_id`. Nothing personal is duplicated between `auth.users`, `profiles` and `family_members` — the name, national ID and camp live on the person record and are reached through that foreign key.

## 6 · Roles

| Role | Scope | Writes |
|---|---|---|
| `super_admin` | everything; exactly one exists; belongs to no camp | camps, camp admins, aid types |
| `camp_admin` | one camp, set on their profile | families, people, aid, documents, request decisions, message replies |
| `displaced` | their own family only | a registration request, a message; nothing else |

The write column is a direct translation of the `PERMISSIONS` table in `assets/js/core/auth.js`. The Super Admin reads everything but does not author camp-level records, because the application does not offer them those controls.

Status gates authorization, not just authentication: a `disabled` camp admin and a `pending` or `rejected` displaced account sign in successfully and are authorized for nothing.

## 7 · Row Level Security

RLS is enabled on all fourteen tables; 52 policies. Anonymous access is granted to exactly one thing.

### Helper functions

The `private` schema holds **23** functions: 7 `SECURITY DEFINER` identity helpers — `current_role()`, `current_status()`, `current_camp_id()`, `current_family_id()`, `is_super_admin()`, `is_camp_admin()`, `is_displaced()` — plus 2 more that exist only to break policy recursion (below), the `SECURITY INVOKER` context check `is_browser_session()`, 12 trigger and utility functions, and the privilege-hardening event-trigger handler added in §7's Function privileges correction below.

They must be `SECURITY DEFINER`: a policy on `profiles` cannot itself read `profiles` without recursing. Each reads only the caller's own row via `auth.uid()`, so elevated execution leaks nothing beyond what the caller already knows about themselves. `private` is **not** in `config.toml`'s exposed `schemas`, so none of them is reachable as an RPC.

Two more — `distribution_camp_id()` and `family_receives_distribution()` — exist specifically to break mutual recursion between `aid_distributions` and `aid_distribution_families`, whose policies would otherwise re-enter each other.

Every policy wraps its helper call as `(select private.…())` so Postgres evaluates it once per query rather than once per row.

### The matrix

| Table | `super_admin` | `camp_admin` | `displaced` | `anon` |
|---|---|---|---|---|
| `camps` | full | read own + active | read active | **read active** |
| `profiles` | full | read/update own camp | own row | — |
| `families` | read | full, own camp | read own family | — |
| `family_members` | read | full, own camp | read own family | — |
| `organizations` | full | full | read | — |
| `aid_types` | full | read | read | — |
| `aid_distributions` (+ junctions) | read | **full, own camp** | read own family's | — |
| `registration_requests` | read | read/update own camp | own request | — |
| `documents` | read/write | full, own camp | read + upload own family's | — |
| `messages` | read/reply | read/reply own camp | own threads, send only | — |
| `notifications` | own | own | own | — |
| `user_preferences` | own | own | own | — |

The one anonymous read is the list of active camps: the public registration form has to render it before an account exists, and a camp name is not personal data. If that is not acceptable in your deployment, drop `camps_select_anon` and `grant select on public.camps to anon` from `003`.

### Beyond RLS

RLS decides which **rows** may be written; it cannot restrict **columns**. Two `BEFORE UPDATE` triggers close that gap:

- `guard_profile_privileges()` — a user with a legitimate "edit my own profile" policy still cannot send `role: 'super_admin'`, move themselves to another camp, or change their own account status. A camp admin may attach a newly approved account to their own camp and nothing else.
- `guard_notification_update()` — a recipient may mark a notification read; they may not rewrite its title, body or type.

Both skip the check for trusted server-side contexts, identified by `private.is_browser_session()`.

That function **fails closed**. It anchors on `session_user`, which is `authenticator` for every Data API request and never for a direct database connection; the JWT role claim is then consulted only to carve the secret key back out. So an unreadable, empty or malformed claims GUC leaves the caller classified as a browser session and every guard stays on, rather than silently switching itself off. `session_user` rather than `current_user` is essential: inside a `SECURITY DEFINER` function `current_user` has already become the function owner and would report `postgres` for every caller, while `session_user` is unaffected.

### Grants

Migration `003` revokes everything from `anon` and `authenticated` and re-grants explicitly, table by table. Grants decide reachability; RLS decides rows. Both are applied to every exposed object.

It also resets the **default** privileges:

```sql
alter default privileges in schema public revoke all on tables    from anon, authenticated;
alter default privileges in schema public revoke all on sequences from anon, authenticated;
```

Supabase announced on 2026-04-28 that new `public` tables would stop being auto-exposed, with enforcement on 2026-10-30 — but this project still carries the legacy defaults, which grant `anon` and `authenticated` full DML on every table `postgres` creates. A plain `REVOKE` only reaches objects that already exist, so without the two statements above the first table Phase 2 adds would be exposed to anonymous callers the moment it was created. `service_role` is deliberately untouched.

The resulting model, in order of precedence: **default privileges** grant browser roles nothing → **explicit grants** open only the tables and verbs a role needs → **RLS policies** are the actual authorization boundary.

Migration `005` additionally revokes `EXECUTE` on the pre-existing `public.rls_auto_enable()` from `PUBLIC`, `anon` and `authenticated`. That function backs the project's `ensure_rls` event trigger, which auto-enables RLS on new `public` tables — a safety net that complements the explicit statements in `003`. It is neither dropped nor disabled: event-trigger functions are invoked by the system without an `EXECUTE` check on the calling user, so the revoke removes the RPC surface (`/rest/v1/rpc/rls_auto_enable`, linter warnings 0028 and 0029) and leaves the behaviour intact.

`EXECUTE` on the four `SECURITY DEFINER` workflow functions in `public` is revoked from `PUBLIC` before being granted — Postgres grants `EXECUTE` to `PUBLIC` on every new function, and `anon`/`authenticated` inherit from it, so revoking from those two roles alone would leave the workflow functions callable by anyone.

### Function privileges correction (post-Phase-1 security close-out)

A follow-up audit — run specifically because the table/sequence default-privilege fix above raised the question "did functions get the same treatment?" — found that they had not, in two layers:

**1. A second legacy default-privilege leak, on functions.** This project's legacy default-privilege set covers a *third* object type migration `003` didn't originally touch: `anon` and `authenticated` were being granted `EXECUTE` directly, at creation time, on every new function in `public` — independent of the `revoke ... from public` statements that only strip the separate PUBLIC-inherited privilege. In practice, `anon` could call all five of `approve_registration_request`, `reject_registration_request`, `create_family_with_members`, `create_aid_distribution`, and `reset_family_reference_sequence`.

**2. A PostgreSQL-intrinsic default that `ALTER DEFAULT PRIVILEGES` does not reach on this instance.** PostgreSQL grants `EXECUTE` on every new function to `PUBLIC` automatically at creation time — a built-in default, distinct from the default-privilege mechanism. This was confirmed empirically, not assumed: running `alter default privileges in schema public revoke execute on functions from public;` immediately before `create function public.__probe()...` **in the same transaction** still produced a function whose ACL carried a `PUBLIC` grant. Tables and sequences do not have this problem — verified with the same probe technique — so it is function-specific. Since `anon`/`authenticated` inherit anything granted to `PUBLIC`, this alone would have re-opened every function `ALTER DEFAULT PRIVILEGES` was supposed to close.

**The fix, in three migrations:**

- `20260817000000_fix_function_default_privileges.sql` — `alter default privileges in schema public revoke all on functions from public, anon, authenticated;` plus explicit per-function revokes on the five functions that already existed (the `ALTER` only prevents *future* leaks).
- `20260817000100_enforce_function_execute_baseline.sql` — because layer 2 above cannot be closed by `ALTER DEFAULT PRIVILEGES` alone, this adds an event trigger, `enforce_function_no_public_execute`, that fires on `ddl_command_end` for `CREATE FUNCTION` and revokes `PUBLIC`'s grant the instant a function is created — the same pattern this Supabase instance already uses for `ensure_rls` (§5). It revokes **only** from `PUBLIC`, never from `anon`/`authenticated` directly, so it cannot undo an explicit grant a migration makes in a later statement, and is a no-op on `CREATE OR REPLACE FUNCTION` redeploys of an already-fixed function (verified: a function created, granted to `authenticated`, then redeployed via `CREATE OR REPLACE`, keeps its `authenticated` grant and gains no `PUBLIC` grant).
- `20260817000200_close_private_schema_public_execute.sql` — the same layer-2 leak existed on all 20 pre-existing `private` schema functions (the identity/authorization primitives every RLS policy calls). Not independently reachable — `anon` has no `USAGE` on `private`, confirmed live, so calling one returns `permission denied for schema private` before the function-level grant is ever consulted — but closed anyway as defense in depth, and the event trigger above was widened to cover `private` too.

**End state, verified against the live project (catalog checks plus real HTTP calls with the publishable key):**

| Function | `anon` | `authenticated` | `service_role` |
|---|---|---|---|
| `approve_registration_request`, `reject_registration_request`, `create_family_with_members`, `create_aid_distribution` | denied | ✅ (internally authorized) | ✅ |
| `reset_family_reference_sequence` | denied | denied | ✅ only |
| all 20 `private.*` helpers | denied | ✅ | — (not needed; `service_role` reaches data via direct table grants and bypasses RLS) |

All five `public` functions were called anonymously over real HTTP (`POST /rest/v1/rpc/<fn>` with the publishable key) and returned `{"code":"42501","message":"permission denied for function ..."}`. A throwaway probe function created after the fix, in both `public` and `private`, came back with no `anon`, `authenticated` or `PUBLIC` grant at all — confirming the fix is prospective, not just retroactive.

`get_advisors` before the correction: 10 `WARN`-level `*_security_definer_function_executable` findings (5 functions × `anon` + `authenticated`). After: 4 — the four workflow functions remain flagged for `authenticated` reachability, which is correct and intentional (each is internally authorized and the linter cannot see that); `reset_family_reference_sequence` and every `private.*` function no longer appear at all.

## 8 · Business rules in the database

The client's domain rules are enforced by Postgres, not by JavaScript. Several are *absences* that look like oversights and are not.

| Rule | Mechanism |
|---|---|
| Exactly one Super Admin | partial unique index on `profiles(role)` |
| The camp admin **is** the camp representative | no representative-name column anywhere |
| National ID prevents duplicate registration, in any camp | global unique index + `9`-digit check |
| **Orphan status is derived, never a checkbox** | `is_orphan` is `GENERATED ALWAYS AS (father_status = 'deceased' or mother_status = 'deceased') STORED` — writing to it raises |
| Age bands are cumulative | `family_member_facts` computes `age < N` independently for 1, 2, 3 and 18, so `under_2` necessarily includes `under_1` |
| Shelter is a **type**; no tent, caravan or file number | `tent_type` enum with two values; no such columns exist |
| Health = chronic disease and disability only | two columns, no others |
| No "family needs" in the economic section | not a column |
| Documents have no expiry date | not a column |
| Aid is not a financial transaction | no `value`, `price`, `estimated_value`, `displaced_id` or `recipient_id` |
| The beneficiary of aid is the **family** | `aid_distribution_families`; there is no individual link |
| Aid is created/edited/deleted by Camp Admin only | RLS write policies name `is_camp_admin()` alone |
| A donor is a name plus optional phone and contact | `organizations` has three columns |
| A family is independent, with a generated ID | `families` + `family_reference_seq` |
| `membersCount` is always derived | `family_stats` view; no stored column |
| A family and its members register in **one** form | `create_family_with_members()` — one transaction |
| Removing the head promotes another member | `promote_family_head()` trigger; the last member leaving deletes the family |
| Maternity flags exist only on female records | check constraint + normalising trigger; switching to ذكر clears both |
| A member always lives in their family's camp | `sync_member_camp()` derives `camp_id` from the family |

### Transactional entry points

Two invariants span more than one row and are enforced by `DEFERRABLE` constraint triggers that fire at `COMMIT`. Because the Data API runs every request in its own transaction, they are only satisfiable through a single call:

- `create_family_with_members(camp_id, head, members, notes, created_by)` — a family is never left headless, and members inherit the head's household fields (shelter, origin, area) but not their personal or medical ones.
- `create_aid_distribution(organization_id, camp_id, distributed_on, aid_type_codes, family_ids, all_families_selected, created_by)` — a distribution always has at least one type and one beneficiary. `all_families_selected` records the admin's intent, and the beneficiaries are still materialised one row per family.

Plus the registration workflow, which creates several records at once and would be half-applied if driven from the browser:

- `approve_registration_request(request_id, gender, birth_date)` — creates the person, a family with them as its head, activates the account and sends the notification.
- `reject_registration_request(request_id, note)`.

All four authorise the caller internally rather than trusting the UI, and all four are `SECURITY DEFINER` with `search_path = ''`.

This is **not** general CRUD — that is Phase 2. Only the writes whose invariants cross rows are exposed.

## 9 · Environment variables

Copy `.env.example` to `.env` (git-ignored) and fill in from **Project Settings → API Keys**.

| Variable | Where it goes | Safe in a browser? |
|---|---|---|
| `SUPABASE_URL` | frontend + tooling | yes |
| `SUPABASE_ANON_KEY` (publishable, `sb_publishable_…`) | frontend + tooling | **yes** — RLS is what protects the data |
| `SUPABASE_SECRET_KEY` (secret / service_role, `sb_secret_…`) | seed + tests only | **never** — it bypasses RLS entirely |
| `SUPABASE_DB_URL` | `supabase db push`, psql | no — contains the database password |

The browser reads its two values from `assets/js/core/supabase-config.js`, which is git-ignored and generated:

```bash
cd supabase && npm run frontend:config
```

That script **refuses** to write a key beginning `sb_secret_`, which is the one mistake that would undo every policy in this document.

```bash

```

Unchanged — it still needs a static server and still uses mock data:

```bash

```

## 11 · Development seed

**Development and testing only. Every person, phone number, national ID and password in it is fictional.** Never run it against production; `npm run seed:reset` deletes every row and every auth user first.

`supabase/seed/seed.mjs` imports `assets/js/data/mock-data.js` directly rather than restating the fixtures, so the seeded database and the prototype cannot drift. It is, in effect, the executable form of the migration map in §2.

It creates:

- 3 camps
- 7 donor organizations
- 1 Super Admin, 3 Camp Admins (one per camp, one deliberately `disabled`), 4 displaced accounts — password `123456` for all
- 8 families and 28 people, including orphans, chronic and disability cases, pregnant and breastfeeding mothers, and infants under one, two and three so the cumulative age bands are genuinely exercised
- 15 aid distributions across three camps
- 5 registration requests
- 12 document records (metadata only), 6 messages, 8 notifications

Two details worth knowing:

- Approved and rejected requests are produced by **calling the real workflow functions**, not by writing a decided row. The seed therefore cannot contain a state the application itself could not reach.
- Families are seeded in id order, so the generated reference codes reproduce `FAM-000001 … FAM-000008` exactly as the prototype shows them.

It finishes by printing row counts and re-checking the integrity rules `store.validateData()` asserts in the browser.

## 12 · Testing

Two suites, deliberately different in what they can prove.

### `npm run test:schema` — 48 tests, offline

Runs the migration set against PGlite and drives each persona with `SET ROLE` plus a JWT-claims GUC, so Postgres evaluates the same policy expressions it will evaluate in production. Needs no project, no Docker and no network.

Covers: RLS enabled everywhere · `security_invoker` on both views · every FK indexed · the sign-up role guard · one-Super-Admin · family/member creation and household inheritance · orphan derivation and non-writability · maternity rules in both directions · national-ID uniqueness and format · shelter-type vocabulary · absent columns (tent number, aid value, document expiry) · cumulative age bands · derived aggregates · headless-family rejection and head promotion · multi-type/multi-family aid · the full approval workflow · **and the whole isolation matrix below.**

### `npm run test:rls` — end-to-end, needs a seeded project

The same isolation matrix, but through real Supabase Auth and real HTTP: `signInWithPassword`, PostgREST, publishable vs secret keys. This is what catches anything PGlite's stubs cannot model.

### The isolation matrix (spec §37), covered by both

| # | Scenario | Result |
|---|---|---|
| 1 | Super Admin reads every camp's families, people and aid | ✅ allowed |
| 2 | Camp Admin A reads camp A | ✅ allowed |
| 3 | Camp Admin A reads camp B — including its medical data, by direct id | ✅ zero rows |
| 3b | Camp Admin A writes into camp B (create family, record aid, update, delete) | ✅ rejected |
| 3c | Camp Admin A decides a camp B registration request | ✅ rejected |
| 3d | A **disabled** camp admin signs in | ✅ authorized for nothing |
| 4 | Displaced A reads their own family, members and aid history | ✅ allowed |
| 5 | Displaced A reads another family, another person, the review queue, other profiles | ✅ zero rows |
| 5b | Displaced A creates or deletes aid, or edits their own record | ✅ rejected |
| 6 | Anonymous reads any protected table | ✅ zero rows |
| 6b | Anonymous reads active camps | ✅ allowed, by design |
| 7 | Displaced A sets their own role to `super_admin` | ✅ rejected |
| 7b | Camp Admin A moves themselves to camp B | ✅ rejected |

All 48 offline tests pass. One real bug was found and fixed while writing them: a deferred `AFTER INSERT` constraint trigger fires at `COMMIT` but still carries the tuple version from insert time, so `enforce_family_head()` saw a head that a later `UPDATE` in the same transaction had already assigned. **One thing this suite structurally cannot test.** `is_browser_session()` keys on `session_user`, and PGlite cannot produce a session where that is `authenticator`: `SET SESSION AUTHORIZATION` is not reversible there, and its `username` option changes only `current_user`. The suite therefore asserts that the shipped definition is the fail-closed one, proves that expression's truth table across all four execution contexts, and installs a clearly-labelled test double so the guard-dependent tests still exercise the guards. The `session_user` binding itself is verified against the live project over real HTTP, which is the only place it can be.

## 13 · Security notes

- **RLS is the only access control that matters.** The frontend's `can()` checks decide what to render; they are not security, and the database does not consult them.
- **`user_metadata` is never trusted.** It is user-editable and appears in `auth.jwt()`. The role comes from `profiles`, written server-side.
- **The secret key never enters the browser.** It exists in `.env` (git-ignored) and is used only by the seed script and the end-to-end tests. `write-frontend-config.mjs` refuses to emit it.
- **`SECURITY DEFINER` is used sparingly and deliberately** — for RLS helpers that would otherwise recurse, for integrity triggers that must see rows the caller cannot, and for the four transactional workflow functions. All set `search_path = ''`, all authorise internally, and the helper schema is not exposed to the Data API.
- **`TO authenticated` is never used alone.** Every policy pairs the role with an ownership or scope predicate, so authentication is not mistaken for authorization.
- **Every `UPDATE` policy has both `USING` and `WITH CHECK`**, so a row cannot be reassigned to another owner or another camp on the way out.
- **Medical data (`chronic_diseases`, `disability`, medical-report documents)** is scoped exactly like the rest of the person record: a camp admin never reaches another camp's, and a displaced person never reaches another family's.
- **Deleting an auth user does not invalidate their existing access token.** For sensitive changes, revoke the session as well as the account.
- **Rotate the secret key immediately** if it is ever pasted into a browser file, a screenshot or a commit.

### Known gaps

- **No rate limiting on registration requests** beyond Supabase Auth's own sign-up limits. Worth revisiting before launch.
- **Email confirmation is off** in the local config, so seeded accounts are usable immediately. Turn it on for any deployed environment.
- **`aid_distributions.all_families_selected` is a snapshot of intent.** A family added to a camp after the distribution is not retroactively a beneficiary — which is correct, but means the flag is not a live query.
- **`create_family_with_members` takes `jsonb`.** It is validated by the table's own constraints rather than by a typed signature. A composite type would be stricter; it was not worth the churn in Phase 1.
- ~~Search is prefix-only.~~ Resolved in Phase 2 (§15): `pg_trgm` GIN indexes on `family_members.full_name` and `organizations.name` support substring search; `family_members(lower(full_name) text_pattern_ops)` still backs the prefix case.
- **The two check constraints that reference `current_date`** (birth date not in the future, distribution date not far in the future) only ever loosen with time, so a `pg_restore` of older rows stays valid.

## 16 · Phase 3 — Cloudinary document storage

Binary files now upload to, download from and delete on Cloudinary through three Supabase Edge Functions. `documents` keeps its Phase 1 shape unchanged — it already carried every Cloudinary column this phase needed. Postgres never sees a byte of file content; Cloudinary never sees a byte of the API secret leave its own dashboard.

Before writing anything, the live project was inspected directly (not assumed): `documents`' RLS policies, its existing CHECK constraints (`documents_has_owner`, `documents_cloudinary_complete`), its indexes, and the current frontend document-handling code (`assets/js/pages/documents.js`, `ui/upload.js`, `assets/js/supabase/documents.js`). No Phase 1/2 blocker was found on the database side. One real blocker *was* found and is documented in §16.6 below.

### 16.1 · Architecture

```
Browser
  │  supabase.functions.invoke('documents-upload', FormData)
  ▼
Edge Function (Deno)                    ← the ONLY place the Cloudinary secret exists
  │  caller-scoped Supabase client (Authorization: Bearer <user JWT>, publishable key)
  │  every DB read/write goes through this client — RLS is still the real boundary
  ▼
Cloudinary (type: private)              ← binaries live here, never in Postgres
  │
  ▼
documents row (metadata only)           ← Postgres, same shape as Phase 1
```

Three functions, each `verify_jwt: true` at the platform gateway (a request with no valid JWT never reaches the function body):

- **`documents-upload`** — validates the file, resolves the owner (`family_member_id` / `family_id` / `registration_request_id`) and `camp_id` **server-side** via an RLS-scoped `select` (a client-supplied `camp_id` is never trusted — §26), signs and uploads to Cloudinary, inserts the metadata row through the *same* caller-scoped client (so `documents_insert_scoped` re-checks independently — defense in depth), and destroys the just-uploaded Cloudinary asset if the metadata insert fails (§36 orphan cleanup).
- **`documents-access`** — download **and** preview share this one function (§18: no separate weaker path). An RLS-scoped `select` is the authorization gate — `documents_select_scoped` already covers super_admin (all), camp_admin (own camp), displaced (own family) exactly, and a denied/nonexistent id returns the same generic 404 either way (§28/§29: existence is never leaked). The function fetches the bytes from Cloudinary itself and streams them back — **the browser never receives a Cloudinary URL or credential**, so there is nothing to leak by inspecting network traffic or guessing an id.
- **`documents-delete`** — `documents_select_scoped` (broader) is *not* enough to prove delete authorization, so the function explicitly re-checks the caller's own `profiles.role`/`camp_id` against `documents_delete_admin`'s shape (super_admin, or camp_admin in their own camp) **before** touching Cloudinary. Order: verify → Cloudinary `destroy` → delete the metadata row only if the destroy succeeded or the asset was already gone. A genuine Cloudinary failure leaves the row intact and returns an error (§19) rather than silently losing the reference.

`supabase/functions/_shared/` holds the code all three share: `cloudinary.ts` (signing, upload/download/destroy, file-type allowlist, `MAX_FILE_SIZE`), `supabase-client.ts` (the caller-scoped client builder), `cors.ts`, `http.ts` (response helpers + the `Content-Disposition` encoder — see §16.6).

### 16.2 · Cloudinary signing

One algorithm, Cloudinary's standard Admin/Upload API request signature (confirmed against `cloudinary.com/documentation/authentication_signatures`), reused for all three Cloudinary calls: sort the signable params alphabetically as `name=value`, join with `&`, append the API secret, SHA-1 hex digest.

- **Upload** — `type: 'private'` (never publicly reachable by a plain URL — §9, §29), `public_id` is a fresh `crypto.randomUUID()` (never the national ID — §29), folder `camps-platform/documents/<identity|medical|other>/` (§14).
- **Download** — Cloudinary's SDKs expose a `private_download_url` *helper* that signs a link to `{api_base}/v1_1/<cloud>/<resource_type>/download`, documented as SDK behaviour rather than a standalone REST reference. Reconstructed here with the same generic signature and confirmed working live against a real Cloudinary account during verification (200, correct bytes, correct content-type). If Cloudinary ever changes this path the failure mode is a clean 401/404 (fails closed — no file served to the wrong caller), not a leak.
- **Destroy** — signed `POST .../destroy`; `result: 'ok'` or `'not found'` both count as "gone" for orphan-cleanup and delete purposes.

### 16.3 · File validation and limits

One centralized `MAX_FILE_SIZE` (5 MB, matching the number already shown in `ui/upload.js`'s dropzone hint) and one allowlist covering `image/jpeg`, `image/png`, `image/webp`, `application/pdf`. The declared `Content-Type` is never trusted alone (§11) — each type also has a magic-byte check against the actual first bytes of the file (JPEG `FF D8 FF`, PNG's 8-byte signature, WEBP's `RIFF....WEBP`, PDF's `%PDF`), so a renamed executable with a spoofed `image/jpeg` type is rejected before it ever reaches Cloudinary. Oversized files are rejected before the magic-byte check even runs (cheaper check first).

### 16.4 · Migration

One new migration, `20260817200000_phase3_document_privilege_guard.sql` — verified first that Phase 1's `documents_has_owner` and `documents_cloudinary_complete` CHECK constraints and every FK index already existed, so nothing redundant was added. What Phase 1 left open: RLS decides which **rows** may be updated, not which **columns** (§7 "Beyond RLS") — `documents_update_admin` lets an admin edit a document's `name`/`category`, but nothing stopped that same UPDATE from also reassigning `family_id`, `camp_id`, or the Cloudinary identity columns, which spec §20 requires be effectively immutable. `private.guard_document_privileges()`, a `BEFORE UPDATE` trigger following the exact pattern of `guard_profile_privileges()`/`guard_notification_update()`, closes that: only `name` and `category` may change via plain UPDATE; ownership and Cloudinary-identity columns raise `42501`. Skips the check for trusted server contexts via the existing `private.is_browser_session()`.

### 16.5 · Frontend

`assets/js/supabase/cloudinary.js` is the new data-access module — `uploadDocument`, `getDocumentBlob`, `deleteDocumentAsset` — calling the three functions through the existing shared client's `.functions.invoke()` (no module here constructs its own client, per the rule every other file in this folder already follows). Errors are mapped through the same `DataAccessError`/Arabic-message convention as `errors.js`.

`assets/js/pages/documents.js`'s upload/download/delete handlers branch on whether a real Supabase session exists. When one does, upload goes through `cloudinary.js` and the resulting metadata is mirrored into the existing localStorage `store.documents` row (marked with a `backendId` field) so the page's existing list/preview/delete code — untouched, still reading `store.documents` — renders and acts on it exactly like any other row; download and delete re-route to the backend for any row carrying a `backendId`. No markup changed.

### 16.6 · A real gap found and reported, not silently worked around

Per the task's own instruction to inspect before changing anything and report a blocker rather than route around it: **no page in this project establishes a genuine Supabase Auth session today.** `core/auth.js` is entirely localStorage-mock; `assets/js/supabase/auth.js` (Phase 2) exists but nothing imports it. Every Edge Function here requires a real JWT — that is the whole security model — so `documents.js`'s upload/download/delete buttons cannot succeed in an actual browser click-through until login is separately wired to Supabase Auth, which is Phase 2 work (`core/auth.js → Supabase Auth`, item 1 in §14's Phase 2 order-of-work), not Phase 3.

Asked directly, the decision was: build the full secure backend now, verify it with a real signed-in Node test suite (same pattern as `tests/rls.test.mjs`), and wire `documents.js` defensively so it activates the moment a real session exists later — without doing any of that auth-wiring now. `backendAvailable()` in `documents.js` checks this on every action rather than caching it, so no further change is needed there once login is wired.

### 16.7 · Three real bugs found during live verification

All caught by actually running the new test suite against a live Cloudinary account, not by inspection — worth recording since the same classes of mistake are easy to reintroduce:

1. **`ui/upload.js`'s `readFile()` discarded the original `File` after reading it into a data URL** — fine for the localStorage prototype, but `cloudinary.js` needs real bytes to upload. Fixed by keeping `raw: file` alongside the existing `{name, size, mime, dataUrl}` shape (additive, nothing existing reads a new field it doesn't expect).
2. **`documents-access` returned the document's real MIME type as `Content-Type`.** `@supabase/supabase-js`'s `FunctionsClient` only auto-parses a response into a `Blob` when `Content-Type` is *exactly* `application/octet-stream` — anything else, including a real `image/jpeg`, is decoded with `.text()`, silently corrupting binary bytes via lossy UTF-8 decoding. Fixed by always answering `application/octet-stream` and carrying the real MIME as a custom `X-Document-Mime` header (exposed cross-origin via `Access-Control-Expose-Headers`) that `cloudinary.js` re-types the Blob with client-side.
3. **`Content-Disposition: inline; filename="<Arabic name>"` crashed the function** with `TypeError: Value is not a valid ByteString`. Raw HTTP header values must be Latin-1 ByteStrings, and *every* document name in this app is Arabic (CLAUDE.md: "All visible text is Arabic") — this would have broken every real download or preview. Fixed with `_shared/http.ts`'s `contentDisposition()`, which follows RFC 6266/5987: an ASCII-stripped `filename` fallback plus a percent-encoded UTF-8 `filename*` directive.

A fourth, unrelated bug was found and fixed along the way: `supabase/seed/seed.mjs`'s `reset()` cleared `camps` before `profiles`, which violates `profiles_camp_id_fkey` the moment a project has been seeded once with real camp-scoped admin profiles — it had simply never been hit before, since every prior reset ran against an empty project. Fixed by clearing `profiles` (via the service-role client, so no cascade is needed) immediately before `camps` in the same loop.
