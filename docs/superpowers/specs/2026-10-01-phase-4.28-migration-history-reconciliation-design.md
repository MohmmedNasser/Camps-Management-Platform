# Phase 4.28 — Migration History Reconciliation (Option B) · Design

Date: 2026-10-01 · Scope: documentation and verification only · Application, schema, RLS, RPCs, Edge Functions, auth, data and the live migration history: **unchanged**.

## 1. Problem

After Phase 4.27 the repository holds **30** migration files and the live project's
`supabase_migrations.schema_migrations` holds **31** rows. Exactly one live version has no local file:
`20260817081611_phase2_move_pgtrgm_to_extensions_schema`. This phase decides how to treat it.

## 2. Current state (evidence, all read-only)

- Local: 30 files in `supabase/migrations/`; none named `20260817081611_*`; none local-only.
- Live (via the Supabase MCP, project `qlvftlecwoqmvtagaykr`): 31 rows; `20260817081611` present; every other version has a file.
- Live `pg_trgm` schema: `extensions`.
- The Supabase CLI is not linked/authenticated (`migration list --linked` → "Cannot find project ref"); it was not linked or logged in during this phase.
- Row counts (unchanged from the Phase 4.27 baseline): auth.users 14, profiles 14, families 16, family_members 39, aid_distributions 17, documents 14, registration_requests 7, messages 7, notifications 13, organizations 7, camps 4, activation tokens 3.

## 3. The two migrations

| Version | Name | Live statement (md5) |
|---|---|---|
| `20260817081611` | `phase2_move_pgtrgm_to_extensions_schema` | `alter extension pg_trgm set schema extensions;` (`addfb16d…`) |
| `20260817090719` | `phase2_move_pgtrgm_to_extensions_schema_v2` | `create schema if not exists extensions; alter extension pg_trgm set schema extensions;` (`3aaf6eef…`) |

`20260817081403` creates `pg_trgm` without a schema (→ `public`). The first migration ran live successfully because Supabase
pre-creates the `extensions` schema. It has no `create schema` guard, so it cannot run on a database without that schema.
`_v2` adds the guard and so works in both situations; it supersedes the original for clean-database replay. No later
migration depends on `pg_trgm`'s schema.

## 4. Replay evidence (PGlite, bare Postgres, `pg_trgm` created first)

| Sequence | Result | Final `pg_trgm` schema |
|---|---|---|
| original alone | **fails**: `schema "extensions" does not exist` | `public` |
| `_v2` alone | succeeds | `extensions` |
| original, then `_v2` | original fails, `_v2` succeeds | `extensions` |

The old migration is therefore not required for the final state in a clean environment.

## 5. Options considered

| Option | Outcome |
|---|---|
| A. `supabase migration repair --status reverted 20260817081611` | Rejected (see §6). |
| B. Document only | **Chosen.** |
| Add the file verbatim | Rejected — clean replay fails. |
| Add a guarded/modified copy, or a placeholder/empty/compat/renamed file | Rejected — no longer the SQL that was applied; fake history. |
| Patch the PGlite harnesses to admit the verbatim file | Rejected — edits unrelated tests to admit a pure duplicate of `_v2`'s effect. |

## 6. Why `migration repair` is intentionally not performed

1. **The migration really was applied.** Its effect persists (`pg_trgm` is in `extensions`); "reverted" would be false.
2. **Repair only edits history.** It deletes a row from `supabase_migrations.schema_migrations`; it does not undo the schema change. It would make the counts match while making the history less accurate.
3. **No benefit.** Database work goes through the Supabase MCP, the CLI is not linked, and `_v2` already supersedes it.
4. **Adding it locally is worse** (§5).

## 7. Decision

**Option B — documentation only.** `20260817081611` is the one intentional remote-only migration. No repair, no live write,
no migration file added or edited, nothing pushed.

## 8. Risks / limitations

- The CLI reports `20260817081611` as remote-only (30 local vs 31 live). `supabase db push`/`db pull` will refuse until that is handled deliberately.
- Historical items from Phase 4.27 remain: five local files whose text differs from the originally recorded live statements (`rls_policies`, `fix_function_default_privileges`, `enforce_function_execute_baseline`, `phase4_17_activation_ttl_param`, `orphan_rule_and_request_demographics`); two live changes applied directly with no history entry (`user_preferences_update_own`, ACL on `is_orphan()`); three probe migrations in live history.

## 9. Future handling guidance

Do not add this migration verbatim, as a modified copy, or as a placeholder; do not mark it reverted without an explicit,
separate migration-history decision. If `db push`/`db pull` is ever adopted, handle this one version deliberately
(for example `supabase migration repair --status reverted 20260817081611` after a conscious decision, understanding it
only deletes the history row).

## 10. Verification plan

Git baseline; local file inventory (30, no `…081611`); live history re-read (31, row present, `pg_trgm` in `extensions`,
counts equal baseline); `npm run test:all`; diff limited to documentation; no secrets/SECURITY DEFINER/RLS/RPC/Edge Function changes; one local commit, no push.
