# Phase 4.26 — Test data & notification cleanup (design)

**Scope:** tests and test helpers only. No schema, RLS, RPC, Edge Function, grant or application code changed.

## 1. Root cause

`private.notify_aid_beneficiary_family()` (migration `20260928010000`, trigger `aid_distribution_families_notify_beneficiary`, `AFTER INSERT` on `aid_distribution_families`, `SECURITY DEFINER`) inserts one `notifications` row per account linked to each beneficiary family (title `تمت إضافة مساعدة جديدة إلى ملفك`, href `aid.html`, respecting `user_preferences.notify_aid`).

`notifications` has **no foreign key or column referencing the distribution** (columns: id, recipient_id, type, title, body, href, is_read, read_at, created_at). Deleting a distribution therefore cascades to its junction rows but never to the notifications the trigger wrote. Any test that creates a distribution and only deletes the distribution leaks them.

## 2. Inventory (verified from code)

| Suite | Creates aid | Trigger fires | Deleted aid | Deleted notifications (before) |
|---|---|---|---|---|
| `phase4.6-aids-verification` (UI create→edit→delete) | yes, "select all families" | yes | via UI, `finally` fallback | **no — leak** |
| `phase4.25-aid-isolation` (RPC fixture) | yes | yes | `finally` | yes, inline id-diff |
| `phase4.6-camp-isolation`, `phase4.13-displaced-isolation` | attempts, all rejected | no | n/a | n/a |
| all other suites | read only | no | n/a | n/a |

Live evidence: 15 notifications (5 batches × 3 recipients, identical `created_at` per batch, all bodies dated `15/01/2026` — the 4.6 UI fixture's date) with **no** distribution dated 2026-01-15 in the database. That is what drove the count to 28.

## 3. Strategy (A/B hybrid, test-only)

`supabase/tests/helpers/aid-fixture-cleanup.mjs`:

1. `snapshotAidState(service)` — ids of all notifications and distributions before the fixture exists.
2. `cleanupAidFixture(service, snapshot, { fixtureDates })` — deletes (a) distributions that are new *and* carry a fixture date, (b) notifications that are new (not in the snapshot) *and* carry the trigger's exact signature (title + href). The id-diff is the identity; the signature is a second guard; a message string alone is never used.
3. Every call is awaited, its `error` is checked and cleanup failures throw.

Used in `finally` by `phase4.6-aids-verification` and `phase4.25-aid-isolation`; the 4.6 test also asserts the notification and distribution sets equal the snapshot afterwards. Cleanup is idempotent and tolerates a fixture the UI already deleted (the notifications outlive their distribution and are still removed).

Strategy C (a correlation column) was not needed and was rejected: it would change the production schema for the tests' sake.

## 4. Seed protection

Rows that pre-date the snapshot are never candidates. `notificationFingerprint()` compares every column of every notification (`id, recipient_id, type, title, body, href, is_read, read_at, created_at`) before/after in the new suite.

The 15 pre-existing debris rows were removed once, by exact id, guarded by title, body suffix and "no distribution dated 2026-01-15 exists". The one other aid notification created on 2026-09-28 corresponds to an existing distribution (2026-09-28) and was left alone, as were the August seed rows and the approval/message notifications from earlier phases.

## 5. Verification

`phase4.26-test-data-cleanup-verification`: side effect really occurs; cleanup removes distribution, junction rows and every generated notification; two consecutive lifecycles start from the same baseline; a failure after creation still cleans up and the original error still surfaces; idempotence; pre-snapshot rows untouched; a last-resort final assertion that the aid count and notification fingerprint equal the baseline whichever subtest failed.

## 6. Not changed

Production schema/RLS/RPC/trigger, Edge Functions, frontend, auth. Message- and registration-approval notifications (Phases 4.7/4.19) are outside this phase.
