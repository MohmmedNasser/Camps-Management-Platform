# Phase 4.24 — Server-Side Filtering & Aggregation (design)

## 1. Current architecture (post-4.23)

`supabase/*.js` → `core/selectors.js` → `pages/*` → `ui/*`. Every list page has a single `collect(session)` that
(a) fetches every row of its scope with `fetchAll()` (batched, 4.23), (b) filters in JS with a shared
`matchesXFilters()` predicate, (c) renders, counts and exports from the same array. Pagination in the UI is
client-side slicing of that array (`PAGE_SIZE`). `statistics.html` fetches four whole tables
(people, families, aid, documents) and aggregates in `selectors.js`.

## 2. Phase 4.23 findings carried in

* Whole-table reads are complete but O(N) in transfer and memory.
* `families.js` performs three round trips per list (families, `family_stats` chunked by `.in()`, aid links chunked by `.in()`).
* `onPreview` in `families.js` re-runs a full `collect()` on every staged filter change.

## 3. Live-database facts (authoritative; project `qlvftlecwoqmvtagaykr`)

Rows today: families 16, family_members 39, aid_distributions 17, documents 14, registration_requests 7, messages 7, notifications 22, camps 4, organizations 7.

* `family_stats` and `family_member_facts` are **`security_invoker=true`** views: they already run under the caller's RLS.
* Domain facts already live in SQL: `age_in_years(date)` = `extract(year from age(current_date, birth))` (null when no birth date);
  `is_orphan(m)` = parent deceased AND `marital_status='single'` AND age < 18 (JS `isOrphan` documents itself as the mirror);
  child = `age < 18`; under-3/2/1 = `age < n`; chronic/disability = column `<> ''`; pregnant/breastfeeding counted only where true (maternity
  is written only on female rows, rule 16).
* Family size = `count(family_members)` per family: **every** member incl. head; there is no deceased/inactive member notion.
* Indexes: `families(camp_id)`, `families(reference_code)` (+pattern_ops), `aid_distribution_families(family_id)`, `aid_distribution_types(aid_type_id)`, `family_members(family_id/camp_id/birth_date)`, trigram on `full_name`. No new indexes are justified at this data size and none is added.
* Existing `get_dashboard_statistics` / `get_family_statistics` are `SECURITY INVOKER` with an explicit displaced-role refusal — the pattern this phase follows.

## 5. Proposed database objects

1. **View `public.family_overview`** (`security_invoker=true`): one row per family with `reference_code`, `camp_id`, `camp_name`, `head_name`, `head_tent_type`, `notes`, `created_at`, all `family_stats` counts, and `aid_count`. Under invoker RLS a Camp Admin sees only their camp's families, a Super Admin all. Replaces 3 reads with 1.
2. **Function `public.get_statistics_report(p_tz text default 'UTC')`** returning `jsonb`, `LANGUAGE plpgsql STABLE SECURITY INVOKER`, `search_path=''`, refusing displaced callers (same as `get_family_statistics`). Invoker, **not** definer: RLS scopes the data, so the function cannot reveal anything the caller could not already `SELECT`. `EXECUTE` granted to `authenticated` only.

No `SECURITY DEFINER` is introduced. No RLS policy changes. No index changes.

## 6. RLS / security model

Filtering is never authorisation. `family_overview` and the report function run as the caller; a hand-edited `campId` filter can only narrow. `p_tz` is validated by Postgres (`at time zone` errors on an unknown zone; the client falls back to UTC on error). Anonymous has no grant on either object.

## 7. Pagination & export strategy

The UI keeps client-side pagination and a single `collect()`: the server now returns the **already-filtered** full set (via `fetchAll`, ordered by `reference_code`), so list, result count and Excel export still share one query and export is always the complete filtered set. True server pagination is deferred: the page's result bar, staged-filter preview count and export all need the full filtered count/set, and the row volume does not warrant restructuring.

## 8. Statistics strategy

Page calls `getStatisticsReport()` (new, `supabase/statistics.js`) + `listCampsWithStats()`; `collect()` keeps its return shape (`stats, camps, byMonth, aidByType, …`) and labels are still applied from `config.js`. `selectors.js` statistics aggregations are retained as the **reference oracle** for tests (and are what the report is compared against on the live dataset).

## 9. Testing strategy

* `phase4.24-filtering-verification`: for every migrated family filter, run old JS predicate over the full unfiltered set vs the new server-filtered function; compare id lists (empty, single, multi, boundary sizes 2/3/4/6/7, wildcard chars in search). Independent service-role SQL for counts. Export equivalence = same function result.
* `phase4.24-statistics-verification`: RPC vs (a) legacy JS aggregations over the legacy fetches, (b) independent service-role queries, for every statistic.
* `phase4.24-isolation`: anon denied on view/RPC; displaced refused; Camp Admin family_overview returns only own camp even with `campId` of another camp; RPC scoped to own camp for Camp Admin; Super Admin sees all; invalid `p_tz`.
* `phase4.24-browser`: Playwright at 320/375/768/1024/1280/1440, families + statistics pages, `body.scrollWidth`.
* Full `npm run test:all`; post-run debris check.

## 10. Rollback

Purely additive: one migration adds a view and a function; frontend change is confined to `families.js` (data access + page) and `statistics.js`. Rollback = revert the commit and `drop view family_overview; drop function get_statistics_report(text)`.

## 11. Explicitly deferred

Server-side displaced/aid/documents/registration-request filtering (reasons in §4); true server pagination; SQL views for the per-camp comparison; timezone-exact age for statistics; React migration.
