# Phase 4.4 — Camp Admin Families on Real Data

**Date:** 2026-08-18
**Status:** Approved for implementation

## 1 · Context

Phase 4.1 wired auth/session/roles to real Supabase Auth. Phase 4.2 connected
the Super Admin dashboard. Phase 4.3 connected the Camp Admin dashboard.
Families, displaced persons, aid, documents, messages, notifications and
statistics all still read mock `core/store.js`.

Phase 4.4 connects **only the Camp Admin's slice** of the families flow:
`families.html` (list), `family-create.html`, `family-details.html` — and
only the `camp_admin` role branch of each. The Super Admin families list
(cross-camp, with the `campId` filter and `campName` column) and the
displaced person's "أسرتي" view stay on mock data, unchanged.

Live project verified via Supabase MCP before writing this spec (same
project as prior phases, `qlvftlecwoqmvtagaykr`):

- `family_stats` (view, `security_invoker=true`) already carries
  `members_count, children_under_18, children_under_3, children_under_2,
  children_under_1, orphans, chronic, disability, pregnant, breastfeeding`
  per `family_id` — a near 1:1 match with mock's `familyFacts()`.
  `security_invoker=true` means the view is evaluated under the caller's
  own RLS, not the view owner's — so it is exactly as camp-scoped as
  `family_members` itself, with no extra work.
- `families.head_member_id` has a real FK to `family_members.id`
  (`families_head_member_id_fkey`), so the head's name and tent type can be
  embedded in the same query as the family row — no second round trip.
- `families.reference_code` has its own **unique index**
  (`families_reference_code_key`), independent of the UUID primary key. It
  is safe to use as the sole external identifier — the real data path can
  key every lookup, link and delete on `reference_code` (the human-readable
  `FAM-000001` string), exactly like the mock's `id` field already does.
  This means `resultsView()`, `family-details.js`'s breadcrumb/title, its
  `data-delete` attribute, and every `rowActions` href need **zero
  changes** — they already just read `row.id` / `family.id`.
- `create_family_with_members(p_camp_id, p_head, p_members, p_notes)`'s
  body (`private.insert_family_member`) reads its `jsonb` arguments with
  **snake_case** keys (`full_name`, `birth_date`, `national_id`,
  `tent_type`, `is_pregnant`, …), not the camelCase the mock/UI forms use.
  `family-create.js`'s submit path needs a camelCase → snake_case mapper
  that does not exist yet.
- `family_members.national_id` has a **global unique index**
  (`family_members_national_id_key`, not scoped to camp) — the live
  mechanism behind domain rule 2. No RLS-visible way for a Camp Admin to
  pre-check another camp's national IDs; the 23505 error at insert time is
  the real boundary. `isDuplicateNationalId(error)` in `family-members.js`
  already exists to classify it.
- `family_members.family_id` is **NOT NULL** with `ON DELETE CASCADE`,
  and BACKEND.md §4 already documents this as deliberate: "Families
  cascade to their members." Confirmed live: no way to delete a family
  without also deleting its members — this is the real, intended
  behavior, not a bug to work around.
- RLS confirmed camp-scoped on every table this phase touches:
  - `families`: `families_select_scoped` / `families_delete_camp_admin` /
    `families_insert_camp_admin` / `families_update_camp_admin` — all
    `is_camp_admin() AND camp_id = current_camp_id()` (select also allows
    `is_super_admin()` and a displaced person's own family).
  - `family_members`: identical shape, `is_camp_admin() AND camp_id =
    current_camp_id()` on select/insert/update/delete.
  - `aid_distribution_families`: identical shape via
    `private.distribution_camp_id(distribution_id) = current_camp_id()`.
  - `family_stats` / `family_member_facts`: no policies of their own
    (views), scoped transitively via `security_invoker` + the underlying
    table's RLS.
  - This means **every** query in this phase — list, detail, delete — is
    independently camp-scoped by RLS regardless of what the client passes
    as `campId`. There is no query in this design that fetches
    cross-camp rows and narrows them in JavaScript.
- `mcp__supabase__get_advisors` (security): no new ERROR/WARN findings
  beyond the pre-existing, already-documented ones noted in the Phase 4.3
  spec. Clean baseline.

## 2 · Non-negotiable constraints (from approval)

1. **Super Admin stays mock — no exceptions.** The Super Admin families
   list (mock data, `campId` filter, `campName` column, existing
   render/filter/export behavior) is untouched. The displaced person's
   "أسرتي" view (`family-details.html` with no `id` in the URL) stays
   mock. Only the `camp_admin` branch of each page's `collect()` uses the
   new real-data path.
2. **Delete is authorized by RLS, not client code.** `deleteFamily()`
   issues a plain `.delete()` against `families`; `families_delete_camp_admin`
   (`is_camp_admin() AND camp_id = current_camp_id()`) is the actual
   authorization boundary. No client-side camp-id comparison is added as
   a gate — any such check in the UI is redundant UX only (e.g. choosing
   which "not found" copy to show), never a substitute for the RLS check.
   The cross-camp isolation suite performs a real delete attempt against
   another camp's family and asserts it is rejected or affects zero rows.
3. **Family creation goes through `createFamilyWithMembers()` only.** No
   new client-side sequence of `INSERT`s. `family-create.js` calls the
   existing RPC-backed `createFamilyWithMembers()` (`families.js`) exactly
   once per submit. The database remains authoritative for family
   creation, member creation, national-ID uniqueness, and camp
   authorization (`create_family_with_members`'s own
   `is_camp_admin() AND current_camp_id() = p_camp_id` check). Client-side
   validation (`bindForm`/schema) is UX only — format checks, required
   fields — never a substitute for the DB's constraints.
4. **One export pipeline.** The real flow is `getCampFamilies(campId) →
   matchesFamilyFilters() (shared with mock) → familyExportRow() →
   FAMILY_COLUMNS / exportSheet()` — the existing Excel writer, unchanged.
   No second export implementation. The exported rows are exactly the
   currently-filtered, camp-scoped result set — the same array the table
   renders from, per the existing "one query drives table + count +
   export" rule.
5. **No unnecessary architectural changes.** Live schema/RLS inspected
   before writing this spec (§1). Work happens in an isolated worktree,
   merges to local `main` only after the full verification in §9 passes,
   and is not pushed to any remote. No page, shared component, selector,
   or schema is touched beyond what §1's findings prove necessary (the one
   exception, justified below, is extracting — not changing — the mock
   filter predicate so it can be shared).
6. Displaced-person pages (`displaced.html`, `displaced-details.html`,
   `displaced-create.html`, `displaced-edit.html`) are out of scope
   entirely (Phase 4.5+).
7. `Promise.all` for independent data requests within one page load.
8. No `service_role` or private secret in browser code; no RLS bypass; no
   hardcoded camp id; no client-side role switching.
9. A genuinely empty camp (zero families) renders the real
   `emptyState()` — no fabricated rows, filters still behave, export is
   simply refused the same way it already is for an empty mock result
   (`exportRows()`'s existing `if (!rows.length)` guard, unchanged).
10. Reuse existing loading/skeleton/error/empty-state mechanisms — no new
    UI pattern.
11. Full existing test suite must stay green, plus this phase's new
    suites folded into `test:all`.
12. If a genuine backend blocker is found, STOP and report — do not
    silently work around it.

Four small additions, matching the "one or two new functions" shape of
Phase 4.2/4.3:

Plus one local, page-only piece with no cross-page reuse yet (kept local

5. A camelCase → snake_case payload mapper inside `family-create.js`,
   turning `displacedFields`/`memberFields`' form values into the shape
   `create_family_with_members` actually reads (§1).

## 5 · Data mapping

### 5.1 · `families.js` (list) — `collect(session)`

Mock (`select.getFilteredFamilies(session, {query, ...filterValues()})`)
already is "the one query behind the table, the count and the export."
The Camp Admin branch becomes:

```js
async function collect(session) {
  if (session.role !== ROLES.CAMP_ADMIN) {
    return select.getFilteredFamilies(session, { query: state.q, ...filterValues() });
  }
  const rows = await getCampFamilies(session.campId);
  return rows.filter((family) => select.matchesFamilyFilters(family, { query: state.q, ...filterValues() }));
}
```

Super Admin (`ROLES.SUPER_ADMIN`) keeps calling the mock selector
unchanged — including its own `campId` filter and `campName` column,
which `filterSpec()`/`resultsView()` already gate on `isSuper` and are not
touched.

`getCampFamilies(campId)` (`assets/js/supabase/families.js`):

```js
export async function getCampFamilies(campId) {
  const client = requireClient();
  const families = await run(
    client
      .from('families')
      .select(
        'id, reference_code, camp_id, notes, created_at, ' +
          'head:family_members!families_head_member_id_fkey(full_name, tent_type)'
      )
      .eq('camp_id', campId)
  );
  if (!families.length) return [];

  const ids = families.map((f) => f.id);
  const [stats, aidLinks] = await Promise.all([
    run(client.from('family_stats').select('*').in('family_id', ids)),
    run(client.from('aid_distribution_families').select('family_id').in('family_id', ids)),
  ]);

  const statsByFamily = new Map(stats.map((s) => [s.family_id, s]));
  const aidCountByFamily = new Map();
  aidLinks.forEach((row) =>
    aidCountByFamily.set(row.family_id, (aidCountByFamily.get(row.family_id) || 0) + 1)
  );

  return families.map((family) => {
    const s = statsByFamily.get(family.id) || {};
    return {
      id: family.reference_code,
      headName: family.head?.full_name || '—',
      headTentType: family.head?.tent_type || '',
      notes: family.notes || '',
      membersCount: Number(s.members_count) || 0,
      childrenUnder18: Number(s.children_under_18) || 0,
      childrenUnder3: Number(s.children_under_3) || 0,
      childrenUnder2: Number(s.children_under_2) || 0,
      childrenUnder1: Number(s.children_under_1) || 0,
      orphans: Number(s.orphans) || 0,
      chronic: Number(s.chronic) || 0,
      disability: Number(s.disability) || 0,
      pregnant: Number(s.pregnant) || 0,
      breastfeeding: Number(s.breastfeeding) || 0,
      aidCount: aidCountByFamily.get(family.id) || 0,
      createdAt: family.created_at,
    };
  });
}
```

Every field name matches what `resultsView()` (list columns),
`familyExportRow()` and `FAMILY_COLUMNS` already read — no changes needed
to any of them. `campName` is deliberately absent: the Camp Admin branch
of `resultsView()` never renders that column (`isSuper` gate), so it is
never requested.

`core/selectors.js` — the extracted predicate (behavior-preserving
refactor of the existing `.filter()` block):

```js
export function matchesFamilyFilters(family, filters = {}) {
  const {
    query = '', size = '', hasChildren = '', hasUnder3 = '', hasUnder2 = '',
    hasUnder1 = '', hasOrphan = '', hasChronic = '', hasBreastfeeding = '', hasPregnant = '',
  } = filters;
  const term = query.trim().toLowerCase();
  const bucket = FAMILY_SIZES.find((entry) => entry.value === size);

  if (bucket) {
    if (family.membersCount < bucket.min) return false;
    if (bucket.max !== null && family.membersCount > bucket.max) return false;
  }
  if (!matchesYesNo(hasChildren, family.childrenUnder18)) return false;
  if (!matchesYesNo(hasUnder3, family.childrenUnder3)) return false;
  if (!matchesYesNo(hasUnder2, family.childrenUnder2)) return false;
  if (!matchesYesNo(hasUnder1, family.childrenUnder1)) return false;
  if (!matchesYesNo(hasOrphan, family.orphans)) return false;
  if (!matchesYesNo(hasChronic, family.chronic)) return false;
  if (!matchesYesNo(hasBreastfeeding, family.breastfeeding)) return false;
  if (!matchesYesNo(hasPregnant, family.pregnant)) return false;

  if (!term) return true;
  return (
    family.id.toLowerCase().includes(term) ||
    family.headName.toLowerCase().includes(term) ||
    (family.notes || '').toLowerCase().includes(term)
  );
}
```

`getFilteredFamilies()`'s own `.filter(...)` call site is replaced with
`.filter((family) => matchesFamilyFilters(family, filters))` — same
`filters` object it already receives, identical resulting behavior,
verified by the existing families-page tests continuing to pass unchanged.

### 5.2 · `family-details.js` — `collect(session)`

```js
function collect(session) {
  const { id } = params();
  if (session.role !== ROLES.CAMP_ADMIN) {
    // Existing mock path — Super Admin and Displaced ("أسرتي"), unchanged.
    ...existing body...
  }
  return collectReal(session, id);
}

async function collectReal(session, referenceCode) {
  if (!referenceCode) return { family: null };
  const family = await getFamilyByReferenceCode(referenceCode);
  if (!family || family.campId !== session.campId) return { family: null };

  const [aidRows, docsResult] = await Promise.all([
    getFamilyAidHistory(family._dbId),
    listDocuments({ familyId: family._dbId }),
  ]);

  return {
    family: { ...family, campName: session.campLabel },
    aid: aidRows.map(mapAidHistoryRow),
    documents: docsResult.rows.map(mapDocumentRow),
  };
}
```

`family.campId !== session.campId` here is the same kind of redundant,
UX-only check already present in the mock path (`session.role ===
ROLES.CAMP_ADMIN && family.campId !== session.campId`) — it only chooses
between the normal view and `missingView()`'s copy. The actual boundary is
`families_select_scoped`'s RLS: `getFamilyByReferenceCode()` cannot return
another camp's family in the first place, so this branch is unreachable in
practice for anything but a same-camp `notFound` case (e.g. a typo'd
reference code). It is not a security control and is not required for one
— removing it would not widen access.

`getFamilyByReferenceCode(referenceCode)` (`families.js`):

```js
export async function getFamilyByReferenceCode(referenceCode) {
  const client = requireClient();
  const family = await run(
    client
      .from('families')
      .select(
        'id, reference_code, camp_id, notes, created_at, ' +
          'head:family_members!families_head_member_id_fkey(full_name, tent_type), ' +
          'family_members(*)'
      )
      .eq('reference_code', referenceCode)
      .maybeSingle()
  );
  if (!family) return null;

  const stats = await run(
    client.from('family_stats').select('*').eq('family_id', family.id).maybeSingle()
  );

  const members = (family.family_members || [])
    .map(mapMemberRow)
    .sort((a, b) => (a.relationship === 'head' ? -1 : b.relationship === 'head' ? 1 : 0));

  return {
    id: family.reference_code,
    _dbId: family.id,
    campId: family.camp_id,
    notes: family.notes || '',
    createdAt: family.created_at,
    headName: family.head?.full_name || '—',
    head: members.find((m) => m.relationship === 'head') || null,
    membersCount: Number(stats?.members_count) || 0,
    childrenCount: Number(stats?.children_under_18) || 0,
    orphansCount: Number(stats?.orphans) || 0,
    members,
  };
}

function mapMemberRow(row) {
  return {
    id: row.id,
    fullName: row.full_name,
    relationship: row.relationship,
    gender: row.gender,
    birthDate: row.birth_date,
    nationalId: row.national_id,
    chronicDiseases: row.chronic_diseases,
    disability: row.disability,
    fatherStatus: row.father_status,
    motherStatus: row.mother_status,
  };
}
```

`membersTable()` reads exactly these field names already
(`fullName, relationship, gender, birthDate, nationalId, chronicDiseases,
disability`) plus calls `select.isOrphan(row)`, which reads
`fatherStatus`/`motherStatus` — both mapped above. `view()` reads
`family.membersCount, family.childrenCount, family.orphansCount,
family.headName, family.notes, family.createdAt, family.head.tentType,
family.campName, family.id, family.members` — all present.

**Known, accepted, out-of-scope limitation** (mirrors the Phase 4.2/4.3
precedent): `membersTable()`'s row actions and `aidRow()` link to
`displaced-details.html`/`displaced-edit.html`/`aid-details.html` with a
real id. Those pages are Phase 4.5+ scope and still read mock
`core/store.js`, so following the link currently lands on a
not-found/empty state. Not addressed here.

`mapAidHistoryRow`/`mapDocumentRow` are small local mappers from
`getFamilyAidHistory()`'s/`listDocuments()`'s existing return shapes to
what `aidRow()`/`documentRow()` already render (`typeLabels`,
`organizationName`, `date`, `id` / `name`, `categoryLabel`, `size`, `id`)
— the same style of mapping Phase 4.3 already used for
`mapRequestRow`/`mapAidRow` in `dashboard.js`.

Note the copy change (constraint from the approved delete-semantics
decision): "وجميع أفرادها" ("and all its members") replaces the old
"يبقى أفرادها مسجلين كنازحين دون أسرة" ("its members remain registered
without a family") — the real cascade deletes members, it does not detach
them (§1). `families.js`'s list-row delete handler gets the identical
text change and the identical `await deleteFamily(...)` /
null-check pattern for the Camp Admin branch; the Super Admin branch keeps
calling `select.removeFamily(...)` (mock) unchanged.

`deleteFamily(referenceCode)` (`families.js`):

```js
export async function deleteFamily(referenceCode) {
  const client = requireClient();
  const deleted = await run(
    client.from('families').delete().eq('reference_code', referenceCode).select().maybeSingle()
  );
  return Boolean(deleted);
}
```

No `campId` is passed or checked here at all — `families_delete_camp_admin`
RLS is the entire authorization boundary (constraint 2). If the row
belongs to another camp, or the caller isn't a camp admin, the delete
matches zero rows and `deleted` is `null`/falsy — indistinguishable, from
the client's point of view, from "not found." This is intentional: the
UI cannot and does not need to tell the two apart.

### 5.3 · `family-create.js` — `onSubmit`

```js
onSubmit: async (values) => {
  if (session.role !== ROLES.CAMP_ADMIN) { /* existing mock path, unchanged */ }

  const campId = session.campId;
  try {
    const result = await createFamilyWithMembers({
      campId,
      notes: (values.notes || '').trim(),
      head: toMemberPayload(values, { relationship: 'head', status: 'approved' }),
      members: blocks.map((index) => toMemberPayload(readMember(values, index))),
    });
    toast.success('تم الإنشاء', `تم إنشاء الأسرة ${result.referenceCode} مع ${blocks.length + 1} من الأفراد.`);
    go('family-details.html', { id: result.referenceCode });
  } catch (error) {
    if (isDuplicateNationalId(error)) {
      // The 23505 error identifies the violated unique index, not which
      // form field submitted it (head or one of N member blocks) — with
      // no live pre-check (§5.3's approved trade-off), the honest signal
      // is a general error, not a guessed field-level one.
      toast.error('رقم هوية مكرر', 'أحد أرقام الهوية المدخلة مسجّل بالفعل لدى أسرة أخرى. تحقق من رقم رب الأسرة وكل فرد ثم أعد المحاولة.');
      return;
    }
    console.error(error);
    toast.error('تعذر الإنشاء', 'حدث خطأ أثناء حفظ الأسرة، حاول مرة أخرى.');
  }
},
```

`create_family_with_members` RPC returns only the new family's UUID, not
a row. `createFamilyWithMembers()` has never been called from any page
(§3), so there is no existing caller whose return shape needs preserving.
It is changed to resolve the UUID and immediately read the `reference_code`
back in the same function, returning `{ id, referenceCode }`:

```js
export async function createFamilyWithMembers({ campId, head, members = [], notes = '' }) {
  const client = requireClient();
  const id = await run(
    client.rpc('create_family_with_members', {
      p_camp_id: campId,
      p_head: head,
      p_members: members,
      p_notes: notes,
    })
  );
  const { reference_code: referenceCode } = await run(
    client.from('families').select('reference_code').eq('id', id).single()
  );
  return { id, referenceCode };
}
```

`family-create.js`'s submit handler then does
`go('family-details.html', { id: result.referenceCode })` — matching
§5.2's reference-code-keyed routing with no extra page-level round trip.

`isDuplicateId`'s live per-keystroke cross-camp check (`schema`'s
`isDuplicateId: (value) => isDuplicateId(...)`) is **removed** for the
Camp Admin real path per the approved decision — format/required-field
validation stays (still useful UX), but the "is this ID already taken"
check becomes submit-time only, driven by the DB's 23505 error via
`isDuplicateNationalId()`.

`toMemberPayload(values, overrides = {})` — new, local to
`family-create.js` (§4 item 5):
