# Phase 4.16 — Real Notification Stats on Camp Admin & Super Admin Dashboards — Design

## 1. Goal

Phase 4.15 collapsed the shared header bell/dropdown to one real,
role-agnostic path for all three roles, and explicitly deferred one item
(§4.5.4 of its design doc):

> `dashboard.js`'s own dead `notifications: select.notificationsFor(...)`
> field for Camp Admin/Super Admin — confirmed unused by either view
> function ... Out of scope; left untouched.

Phase 4.16 picks that up: give the Camp Admin and Super Admin dashboards a
real, rendered unread-notification stat, matching what the Displaced
dashboard has already had since Phase 4.12/4.14, without duplicating
`unreadNotificationCount()`'s query logic anywhere.

## 2. Current behavior (confirmed by reading the code, 2026-09-27)

### 2.1 `assets/js/pages/dashboard.js` — `collect(session)`

```js
if (session.role === ROLES.DISPLACED) {
  return getDisplacedDashboard(session);              // real, includes unreadNotifications
}
if (session.role === ROLES.SUPER_ADMIN) {
  const real = await getSuperAdminDashboard();
  return { ...real, notifications: select.notificationsFor(session.id).slice(0, 4) }; // mock, dead
}
const realCampAdmin = await getCampAdminDashboard(session.campId);
return { ...realCampAdmin, notifications: select.notificationsFor(session.id).slice(0, 4) }; // mock, dead
```

`select.notificationsFor(session.id)` (`core/selectors.js:1200`) reads the
mock `store.notifications` localStorage collection filtered by
`row.userId === userId` — `session.id` is a real Supabase Auth UUID, which
never matches a mock `userId`, so this call already returns `[]` for every
real account. It is not merely unused, it is unreachable-in-practice mock
data, exactly as Phase 4.15's investigation found.

**Confirmed dead, not just mock:** `campAdminView(session, data)` and
`superAdminView(session, data)` each destructure only `const { stats } =
data;` — `data.notifications` is never read by either render function.
Grepped the full file: no other reference to `.notifications` exists in
`dashboard.js` outside the two `collect()` branches that produce it. There
is no notification list/card anywhere on the Camp Admin or Super Admin
dashboard today — unlike Displaced, which has an explicit
"الإشعارات غير المقروءة" `statCard` (`dashboard.js:322`) wired to a real
`unreadNotifications` integer since Phase 4.12/4.14.

### 2.2 `assets/js/supabase/dashboard.js` — the three composition functions

`getDisplacedDashboard(session)` already fetches
`unreadNotificationCount()` (imported from `./notifications.js`) in
parallel with its other reads and returns it as a top-level
`unreadNotifications` field, in every branch (including the
no-family-link and no-person branches) — notification ownership is
independent of family resolution.

`getSuperAdminDashboard()` and `getCampAdminDashboard(campId)` do **not**
fetch or return anything notification-related. Today the page module
bolts the (dead, mock) field on externally after calling them. This is an
asymmetry: the Displaced composition function owns its own notification
fetch; the other two don't, and the page module fakes it for them.

### 2.3 `dashboard.html`

Content-free shell (font links, `main.css`, `<script type="module"
src="../assets/js/pages/dashboard.js">`). No notification markup of its
own — confirms the stat card, if any, is entirely a `dashboard.js`
concern, matching every other stat card on the page.

### 2.4 The header (`ui/layout.js`), for contrast

Since Phase 4.15, `mountShell()` calls `resolveNotifications()`
unconditionally for all three roles → `listNotifications({pageSize: 5})` +
`unreadNotificationCount()`, rendering the bell badge + dropdown. This is
a **separate** fetch from whatever the dashboard page itself does — the
two have never shared a request, not even for Displaced today. This
question ("can the dashboard reuse the shell's fetch?") is addressed in
§5.

### 3.3 `unreadNotificationCount()` re-audited (`assets/js/supabase/notifications.js:28`)

Takes no parameters, no client-supplied recipient id anywhere:

```js
export async function unreadNotificationCount() {
  const { count, error } = await client
    .from('notifications')
    .select('id', { count: 'exact' })
    .eq('is_read', false);
  if (error) throw mapError(error);
  return count;
}
```

Relies entirely on RLS (`notifications_select_own`) to scope the count to
`auth.uid()`. Already used by `getDisplacedDashboard()` and
`resolveNotifications()` (header) for all three roles since Phase
4.14/4.15. This phase reuses it a third time — no new data-access
function, no new RPC.

## 4. Decision: add the field to the composition functions, not the page module

Move notification fetching into `getSuperAdminDashboard()` and
`getCampAdminDashboard(campId)` themselves, mirroring
`getDisplacedDashboard()`'s existing shape exactly — an
`unreadNotifications` integer fetched via `Promise.all` alongside every
other read, returned as a top-level field. This makes all three
composition functions symmetric (today only one of three owns its
notification fetch) and keeps every Supabase call inside
`assets/js/supabase/*`, consistent with the codebase's layering rule
(`assets/js/pages/*` stays thin glue — CLAUDE.md, "Architecture").

`assets/js/pages/dashboard.js`'s `collect()` simplifies to:

```js
async function collect(session) {
  if (session.role === ROLES.DISPLACED) return getDisplacedDashboard(session);
  if (session.role === ROLES.SUPER_ADMIN) return getSuperAdminDashboard();
  return getCampAdminDashboard(session.campId);
}
```

The dead `notifications: select.notificationsFor(...)` field and the
`import * as select from '../core/selectors.js'` import (unused anywhere
else in the file, grep-confirmed) are removed as a direct, in-scope
consequence — not a broader mock-data cleanup.

### 4.1 Rendering: a stat card, added to both views

A real `unreadNotifications` integer that nothing ever renders is not
"the dashboard shows the real count" — it's data.md, not a shipped
feature. Since neither `campAdminView()` nor `superAdminView()` has any
existing notification-related markup to "reconnect" (§2.1), and the
phase's literal goal is "camp_admin dashboard → real notification count" /
"super_admin dashboard → real notification count", one stat card is added
to each view, copying Displaced's existing card verbatim (same label,
icon, tone, href — a new visual pattern is not being invented):

```js
${statCard({
  label: 'الإشعارات غير المقروءة',
  value: formatNumber(unreadNotifications),
  iconName: 'bell',
  tone: 'warning',
  href: pageUrl('notifications.html'),
})}
```

Placed as the last card in each role's stat grid (`.grid--4`, a plain
`repeat(4, minmax(0,1fr))` CSS grid with no fixed-count assumption —
confirmed in `responsive.css`/`layout.css` — so an extra card only adds a
partial last row at every breakpoint, no layout change required). Camp
Admin goes from 8 to 9 cards; Super Admin from 10 to 11. No other card,
label, icon, or ordering changes.

This is the smallest change that makes the stated goal ("dashboard shows
the real count") true and independently testable by Playwright, while
touching nothing else in either view function.

### 4.2 Displaced — unchanged

`getDisplacedDashboard()` and `displacedView()`'s existing
"الإشعارات غير المقروءة" card (Phase 4.12/4.14) are not touched. Its
`unreadNotifications` field already has the exact name and shape this
phase gives the other two roles — no rename, no shape change, so no
regression risk to the existing Displaced test suites.

## 5. Duplicate-request investigation (required by the brief)

**Question:** `mountShell()` (header) and `dashboard.js`'s `collect()`
(stat card) each call `unreadNotificationCount()` independently. Can this
be shared?

**Finding:** This duplication already exists today, for Displaced only,
since Phase 4.14 — Phase 4.16 does not introduce it, it extends an
already-accepted pattern to the other two roles.

**Why it is not fixed in this phase:**

- `mountShell()`'s contract (`ui/layout.js:309`) returns only `{ session,
  content }` to the page module. It resolves and renders the header
  *before* the page module's own `init()`/`collect()` runs. Passing the
  header's already-fetched unread count down to the page would require
  either (a) widening `mountShell()`'s return shape — a change to a
  function every single page in the app calls, or (b) module-level shared
  state (a cache/singleton) that every future page would silently depend
  on. Both are the exact "hidden global state" / "shell-page coupling"
  the brief says not to introduce without a clear correctness benefit.
- There is no correctness benefit: both call sites read the identical
  RLS-scoped `unread_count where recipient_id = auth.uid()` at
  effectively the same instant during page load. They cannot disagree in
  any way a user could observe (same session, same table, sub-second
  apart) — the only cost is one extra small `count`-only query per
  dashboard load, already paid today for Displaced with no reported
  issue since Phase 4.14.
- The two numbers are independently verified to agree in this phase's own
  verification suite (§7, "header/dashboard consistency"), so silent
  drift is a tested property, not an assumption.

**Decision: keep both requests, documented here as in Phase 4.14's own
report ("dashboard.html fires two independent unreadNotificationCount()
calls per load — an accepted architectural tradeoff").** This phase makes
that tradeoff uniform across all three roles instead of Displaced-only.

## 6. Security

- Identity chain, unchanged: Supabase Auth session → `auth.uid()` →
  `notifications.recipient_id`, enforced by `notifications_select_own`
  RLS (§3.1). `unreadNotificationCount()` takes no parameters — there is
  no client-provided recipient id anywhere in this call chain to spoof.
- No new RPC, no new Edge Function, no `service_role` in any file under
  `assets/`. Test fixtures (if any are needed) use `service_role` only
  inside `supabase/tests/*.mjs`, the same established pattern as every
  prior phase.
- No new INSERT/DELETE capability is introduced. This phase is read-only
  (`unreadNotificationCount()` is a SELECT).

## 7. Testing strategy

Two new suites, structurally identical to Phase 4.14/4.15's (`.env`
loader, local static file server, `login()` Playwright helper,
service-role client for independent derivation):

- **`supabase/tests/phase4.16-dashboard-notifications-isolation.test.mjs`**
  — RLS-level probes (reused pattern from 4.15: each of the three roles
  can read/count only their own `recipient_id`; a second Camp Admin
  cannot read or count-toward another's notifications; anonymous is
  rejected) plus dashboard-specific isolation: a fabricated
  `?notificationUserId=`/similar query param on `dashboard.html` does not
  change the rendered stat for any role; session preservation
  (`auth.uid()` unchanged after the dashboard's own notification fetch
  resolves, for all three roles, not just the header as 4.15 already
  covers).
- **`supabase/tests/phase4.16-dashboard-notifications-verification.test.mjs`**
  — DB-vs-UI: for `super@camps.ps`, `admin@camps.ps` and `ahmad@camps.ps`,
  an independent service-role count of `recipient_id = X AND is_read =
  false` is compared against the rendered dashboard stat card's value
  (never importing `assets/js/supabase/notifications.js`, per the brief's
  explicit "not against itself" rule). `nour@camps.ps` covers the
  zero-unread render. Header/dashboard consistency is asserted on the
  same page load for all three roles (both numbers read from the DOM,
  both must equal the independent DB count). A disposable Camp Admin
  fixture (no second super_admin — `profiles_single_super_admin_idx` is a
  unique partial index, same constraint Phase 4.15 already worked around)
  exercises `markAllNotificationsRead()` end to end: dashboard stat goes
  from 2 → 0, persists across reload, another account's rows untouched,
  cleaned up in `finally`. Responsive check at the six standard
  breakpoints (320/375/768/1024/1280/1440,
  `scrollWidth > clientWidth + 1`). A service-role-key browser-exposure
  check.

Both suites are added to `supabase/package.json`'s `test:all` chain,
appended after the existing Phase 4.15 entries.

## 8. Deferred / out of scope

- **Sharing the header's and dashboard's `unreadNotificationCount()`
  calls into one request** — investigated in §5, deliberately not done;
  the tradeoff is documented, not silently accepted.
- **A "recent notifications" list card** (as opposed to a count stat) for
  Camp Admin/Super Admin — the mock field this phase replaces was an
  array (`.slice(0, 4)`), but it was never rendered as a list anywhere,
  and Displaced's own equivalent card is a count, not a list. Matching
  Displaced's existing pattern (a count) is the safe, spec-literal
  reading of "real notification count" — not "build a new list widget."
- **Per-item read/unread toggle from the dashboard** — never existed on
  any dashboard card; out of scope, unchanged.
- Everything Phase 4.13/4.14/4.15 already deferred (notification
  delete/dismiss — no DELETE RLS policy; Auth email changes) is untouched
  and still deferred, for the same reasons already documented in those
  phases' docs.
