# Phase 4.27 — Migration History Reconciliation · Design

Date: 2026-09-30 · Scope: database-history hygiene only · Application, schema, RLS, RPCs, Edge Functions, auth and data: **unchanged**.

## 1. Problem

The final audit found that the repository's `supabase/migrations/` and the live project's
`supabase_migrations.schema_migrations` did not describe the same history:

- the repository had **23** migration files; the live project recorded **31** entries;
- **no** local filename carried the version the live project recorded for it (every local file was
  authored under a nominal timestamp such as `20260816120000`, while the project recorded the moment it
  was actually applied, e.g. `20260816132221`);
- eight live entries had no local file at all.

Consequence: the Supabase CLI matches local and remote migrations **by version**, so `supabase db push`
would see 23 "unapplied" local migrations and 31 "unknown" remote ones — an invitation to re-run
already-applied SQL or to "repair" history blindly. The aim of this phase was to make that impossible
without touching the working database.

All evidence was gathered read-only (`list_migrations`, `SELECT` on `supabase_migrations.schema_migrations`,
catalog queries), never by modifying the live database.

## 4. Discrepancy classification

The brief's categories, applied to what was actually found:

- **A — exact (version and content):** none. No local version matched a live version.
- **B — same migration, different version/text:** all 23 local files (rows 1–23). 18 are identical to the live
  text after ignoring comments (one, #14, byte-for-byte); 5 differ textually — #6, #7 and #17 by folded-in
  live-only fixes, #3 and #20 by statements that the live project holds but its recorded history does not
  (C-7). Resolution: §6.
- **C — live-only:** the 8 entries above.
  - C-1…C-3 probes: net zero (create, re-create, drop). Nothing depends on them.
  - C-4 default-privilege fix: live schema depends on it; local #6 already contains the statement.
  - C-5 pgtrgm v1 / C-6 email-cast v1 / C-7: superseded by a later entry that the local file reproduces.
  - C-7 (**unrecorded live changes** — not live-only *entries*, but schema state the recorded history does
    not explain). Two were found, both already reproduced by the local files:
    (a) `policy user_preferences_update_own` exists live (and in the fingerprint) but the recorded
    `rls_policies` statements do not create it — it is in local #3; the settings page depends on it.
    (b) the live ACL of `public.is_orphan(family_members)` is `authenticated` + `service_role` (no `anon`, no
    `PUBLIC`), which is exactly what local #20's two extra statements produce, although the recorded
    `orphan_rule_and_request_demographics` statements lack them. Both were applied outside the
    migration-history mechanism (development-time SQL). Their *effect* is captured by the local files;
    their exact time of application is not recoverable.
  - C-8 `page_only_json`: a real intermediate form of `list_displaced_persons` that #23 replaces.
- **D — local-only (recorded nowhere live):** none. Every local file corresponds to a live entry.
- **E — duplicate/equivalent:** `…_pgtrgm…` (v1 vs `_v2`) — equivalent end state; `…phase4_10…` (v1 vs
  `_fix_email_cast`) — equivalent after the fix; both kept as history, only the later one is the "current"
  file.
- **F — unknown/ambiguous:** none remaining after the evidence in §5.

## 5. Database state comparison

A read-only **schema fingerprint** was taken over the `public` and `private` schemas (columns, tables
incl. RLS flags, constraints, indexes, policies, function definitions + ACL + security mode +
`search_path`, table ACLs, triggers, views, enum types) on the live project and on a clean PGlite
database built by replaying the committed migrations in order (the same harness `schema.test.mjs`
uses). Each kind is reduced to an order-independent MD5 of its object list.

|---|---|---|---|

| constraints | 85 | 85 | **identical** |
| policies | 52 | 52 | **identical** |
| tables (incl. RLS on/force) | 18 | 18 | **identical** |
| triggers | 23 | 23 | **identical** |
| enum types | 17 | 17 | **identical** |
| views | 3 | 3 | **identical** |
| functions | 47 | 46 | 46 identical once comment-only lines are ignored (see below); the 47th is `public.rls_auto_enable()` |
| function ACLs | 47 | 46 | identical once `service_role` grants are ignored and `rls_auto_enable` excluded |
| table ACLs | 18 | 18 | identical once `service_role` grants are ignored |
| indexes | 80 | 80 | identical except trigram opclass rendering (below) |

The residual differences are all explained and none is a schema difference:

1. **`rls_auto_enable()`** — a platform function behind the project's `ensure_rls` event trigger; it predates
   the migrations and `harden_preexisting_objects` already handles it conditionally.
2. **`service_role` grants** — the live project carries platform default privileges
   (`postgres in schema public: f/r/S → service_role`), so every object created live also gets
   `service_role` privileges; a bare replay has no such defaults.
3. **Trigram indexes** — `pg_get_indexdef` prints `gin_trgm_ops` on live (its `search_path` includes
   `extensions`) and `extensions.gin_trgm_ops` in the replay. Same operator class.
4. **Comment-only lines** — `get_statistics_report` and `list_displaced_persons` bodies contain full-line SQL
   comments in the repository files that the live-stored bodies lack. With comment-only lines stripped,
   all 46 function bodies hash identically to live.

Reference data (`aid_types`, from `reference_data`) is the same file on both sides.

Runtime baseline counts (before and after; see §9): `auth.users` 14, `profiles` 14, `families` 16,
`family_members` 39, `aid_distributions` 17, `documents` 14, `registration_requests` 7, `messages` 7,

## 6. Reconciliation strategy (chosen)

**Repository-only reconciliation; the live project is not modified in any way.**

1. `git mv` each of the 23 local files to the **live version and name** of the history entry it
   corresponds to (table in §3). File **contents are not touched**.
2. Add 7 of the 8 live-only entries as files under their live version and name, with the **exact**
   statements recorded by the project (each verified byte-for-byte against the live `md5`), so the live
   history rows have counterparts and replay order equals the order in which the project executed them.
   **The eighth, `20260817081611_phase2_move_pgtrgm_to_extensions_schema`, is deliberately not added.** Its
   whole body is `alter extension pg_trgm set schema extensions;` with no `create schema` guard: it only
   ran live because Supabase pre-creates the `extensions` schema. Replayed verbatim on a bare Postgres
   (the PGlite harness used by `schema.test.mjs`, `phase2-business-logic.test.mjs`,
   `phase4.25-age-rule.test.mjs`) it aborts with `schema "extensions" does not exist` — found when the
   first 31-file replay failed. It cannot be edited (it is history) and the three harness stubs are out of
   scope, and its effect is fully contained in `…090719_…_v2` (same statement preceded by
   `create schema if not exists extensions`), so it is recorded here instead.
3. Document the old→new map (this file) so historical plans/specs that cite the old filenames remain
   traceable. `BACKEND.md` references were updated to the new names.

Result: the repository holds **30** migration files; every one has the version of a live history entry, and
**30 of the 31** live versions have a file. The single live version with no file is `20260817081611`
(above). Its verbatim text, for the record: `alter extension pg_trgm set schema extensions;`.

### Why this and not something else

| Alternative | Why not |
|---|---|
| `supabase migration repair --status reverted/applied …` | Rewrites or deletes live history rows — destroys the only record of the probes and follow-up fixes, and is not needed: aligning the repository achieves the same version match with zero live effect. |
| `supabase db reset` / `db push` against live | Forbidden by the phase rules; would re-run SQL. |
| Rename only, without adding live-only files | Leaves 8 remote versions "unknown" to the CLI; `db push` would still refuse or need repair. |
| Also add `…081611` verbatim and patch the three PGlite harness stubs with `create schema extensions` | Would align 31/31, but edits three unrelated test files to admit a file that is a pure duplicate of `_v2`'s effect; rejected as a larger change than the history gain justifies. One remote-only version is left and documented. |
| Edit local SQL to equal live text | Forbidden (§12 of the brief); would rewrite what each file originally represented. The folded-in fixes are real and current. |
| New corrective migration | No real database change is needed; it would be cosmetic. |
| Do nothing, document only | Leaves `db push` hazardous; the repair-free alignment is safe and cheap. |

### Replay safety of the added files

Replaying in live-version order with the repository's local texts: the three probe files create and drop a
temporary function; `…072946`, `…073414`, `…125425` and `…080411` are idempotent `create or replace` /
`alter default privileges` statements that re-assert a state the surrounding files already reach. The
PGlite replay of the resulting 30-file set is verified to produce the same fingerprint as the original
23-file set (§8).

## 7. Safety constraints honoured

- No DDL, DML, migration-history write, `db reset`, `db push` or `migration repair` against the live
  project; every live interaction was a `SELECT`.
- No change under `assets/`, `pages/`, `supabase/functions/`.
- No schema, RLS, grant, RPC, trigger, view, index or Edge Function change.
- Nothing pushed to `origin`.

## 8. Verification strategy

1. Byte-exact check of each added live-only file against the live `md5`.
2. Replay fingerprint of the new 30-file set equals the replay fingerprint of the old 23-file set
   (proves the additions and renames are schema-neutral), and still matches live per §5.
3. Filename versions vs live versions: 30 present, one live version (`20260817081611`) intentionally absent, none local-only.
4. `npm run test:all` before (baseline) and after.
5. Live read-only re-fingerprint and row counts after: unchanged.
