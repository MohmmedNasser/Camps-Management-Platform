# Phase 4.9 — Donor Organizations (`organizations.html`) on Real Data

**Date:** 2026-09-23
**Status:** Approved — proceeding to implementation

## 1 · Context

Phase 4.9 connects the donors page — `pages/organizations.html`, the only
page for this domain (list, search, create, edit, delete, all in one page
via a modal dialog; there is no separate create/edit/details page) — to
real Supabase data, for both roles that can open it.

Unlike every prior Phase 4.x page, `organizations.html` needs **no mock
branch preserved afterward**. `PAGE_ACCESS['organizations.html']` is
exactly `[SUPER_ADMIN, CAMP_ADMIN]`, and RLS grants both roles identical
full CRUD with **no camp scoping at all** — donors are a platform-wide
list, not a per-camp one. So this phase is a full replacement of the page,
matching the `family-create.html`/`registration-requests.html` precedent
("Camp-Admin-only page, no mock branch to keep") rather than the
`families.js`/`aid.js`/`documents.js` precedent ("real branch alongside an
untouched mock one").

Confirmed before writing any code, via direct inspection of
`assets/js/pages/organizations.js`: no import from `assets/js/supabase/`
anywhere in the file — fully mock today, reading `core/store.js`'s
localStorage `organizations` collection through
`core/selectors.js`'s `searchOrganizations()`/`organizationRow()`/
`organizationInUse()`.

**What already exists, unused.** `assets/js/supabase/organizations.js`
(Phase 2) already has full CRUD — `listOrganizations`, `getOrganization`,
`createOrganization`, `updateOrganization`, `deleteOrganization` — plus
`listOrganizationOptions()` (Phase 4.6), already live in production use by
`aid-create.js`/`aid-edit.js`/`aid.js`'s real Camp Admin branch. This phase
reuses all of them unchanged and adds exactly one new function.

## 2 · Live schema/RLS findings (verified via Supabase MCP against project `qlvftlecwoqmvtagaykr`)

**Table `organizations`** — columns: `id, name, responsible_person
(nullable), phone (nullable), created_at, updated_at`. No `camp_id`
column — confirmed live, matching BACKEND.md §3's "donor is a name plus
optional phone and contact" description exactly.

**Constraints/indexes, confirmed live:**

- `organizations_name_not_blank` — `CHECK (length(btrim(name)) > 0)`.
- `organizations_phone_format` — `CHECK (phone IS NULL OR phone ~
  '^[0-9+\-\s]{6,20}$')`.
- `organizations_name_key` — **`CREATE UNIQUE INDEX ... ON
  organizations (lower(btrim(name)))`**, a functional unique index, not a
  named table constraint. This matters: a first pass at `pg_constraint`
  alone shows no unique constraint on `name` and would wrongly suggest
  duplicate names aren't enforced — the index only surfaces via
  `pg_indexes`. It enforces case- and whitespace-insensitive uniqueness,
  which is *stricter* than the mock's current exact-string duplicate
  check (`row.name.trim() === payload.name`).
- `aid_distributions_organization_id_fkey` — `FOREIGN KEY
  (organization_id) REFERENCES organizations(id) ON DELETE RESTRICT`,
  matching BACKEND.md §3's "Camps and organizations use `ON DELETE
  RESTRICT` — protected while still referenced."

**RLS (4 policies, confirmed live via `pg_policies`):**

- `organizations_select_authorized` — `is_super_admin() OR is_camp_admin()
  OR is_displaced()`. All three roles may read; `organizations.html` is
  simply not in the displaced role's `PAGE_ACCESS`, so this is a route
  restriction, not an RLS gap — donor names are not sensitive data
  (BACKEND.md's existing framing).
- `organizations_insert_admin` / `_update_admin` / `_delete_admin` — all
  three: `is_super_admin() OR is_camp_admin()`, **no `camp_id` predicate
  anywhere**. This is the simplest RLS shape of any table wired so far —
  no camp-isolation test category applies.

**Security advisors** (`mcp__supabase__get_advisors`, type `security`):
identical to the Phase 4.8 baseline — the same 5 expected
`authenticated_security_definer_function_executable` WARNs (unrelated
workflow RPCs) plus the pre-existing `auth_leaked_password_protection`
WARN. **No new finding. No backend/migration change is required or made
by this phase.**

**Live data check** (informational, confirms continuity with Phase 4.6):
7 real organizations exist today, the same 7 rows `listOrganizationOptions()`
already serves to the real Camp Admin aid workflow. A join against
`aid_distributions`/`aid_distribution_families` for their current
`aid_count`/`families_count` was run live and matches the shape this
phase's new query will compute (§4).

## 4 · `listOrganizationsWithUsage()` and row shaping

```js
const ORG_SELECT = '*, aid_distributions(id, aid_distribution_families(family_id))';

export async function listOrganizationsWithUsage() {
  const client = requireClient();
  const rows = await run(
    client.from('organizations').select(ORG_SELECT).order('name', { ascending: true })
  );
  return rows.map(mapOrganizationRow);
}

function mapOrganizationRow(row) {
  const distributions = row.aid_distributions || [];
  const familyIds = new Set();
  distributions.forEach((d) => (d.aid_distribution_families || []).forEach((f) => familyIds.add(f.family_id)));
  return {
    id: row.id,
    name: row.name,
    phone: row.phone || '',
    responsiblePerson: row.responsible_person || '',
    createdAt: row.created_at,
    aidCount: distributions.length,
    familiesCount: familyIds.size,
  };
}
```

Unpaginated — donors are a small, platform-wide list, same "fetch all"
convention `listOrganizationOptions()` already established. The nested
embed works directly (real FKs, `aid_distributions.organization_id` and
`aid_distribution_families.distribution_id`/`family_id`), the same reason
`aids.js`'s embeds already work without the `family_stats`-style
separate-query workaround (BACKEND.md §15). Because the embed is a normal
PostgREST nested select, it is independently subject to RLS on the child
tables: a Camp Admin's `aid_distributions` child rows are already
own-camp-scoped by `aid_distributions`' own RLS, so `aidCount`/
`familiesCount` computed this way are correct per-role by construction —
no extra authorization code needed, and no camp-admin-vs-super-admin
branching in the mapping function itself. (In practice this phase always
calls it as `super_admin` or `camp_admin`, both of whom see the same
`organizations` rows; only the *usage counts* a Camp Admin sees would
differ from a Super Admin's if the same donor is used in two camps — an
accurate, intentional consequence of reusing RLS as the boundary rather
than a bug.)

`mapOrganizationRow(row)` produces exactly the shape the page's existing
`resultsView()`/`summaryView()` already read (`name`, `phone`,
`responsiblePerson`, `aidCount`, `familiesCount` — the same fields
`organizationRow()` computes from the mock store today), so none of that
rendering code needs to change.

## 5 · `organizations.js` — the real page

**No role branch.** Both `PAGE_ACCESS` roles get the same real path; `can('organization:manage')` (unchanged, already `[CAMP_ADMIN, SUPER_ADMIN]`) continues to gate the create/edit/delete controls exactly as today.

**List + search + summary.**

```js
async function load(session) {
  const target = qs('#results');
  if (!target) return;
  target.innerHTML = skeletonTable(5);

  try {
    const allRows = await store.load(() => listOrganizationsWithUsage());
    currentRows = allRows.filter((row) => select.matchesOrganizationFilters(row, { query: state.q }));
    target.innerHTML = resultsView(currentRows);
    const summary = qs('#summary');
    if (summary) summary.innerHTML = summaryView(currentRows);
  } catch (error) {
    console.error(error);
    target.innerHTML = errorState({ retryAttrs: 'data-retry' });
    delegate(target, 'click', '[data-retry]', () => load(session));
  }
}
```

`currentRows` is a module-level array (same "last rendered rows, for
action handlers" convention `documents.js` established in Phase 4.8) —
`data-edit`/`data-delete` handlers resolve their row via
`currentRows.find((r) => r.id === id)` instead of `store.organizations.get(id)`.

**Create/edit.** `openEditor()`'s `onSubmit` calls `createOrganization()`/
`updateOrganization()` instead of `store.organizations.create/update()`,
wrapped in `try/catch`. A duplicate name surfaces as a `DataAccessError`
with `type === ErrorType.DUPLICATE` (the unique index → `23505` →
already-mapped by `errors.js`) — caught and shown via the existing
`toast.error('تعذر الحفظ', ...)` call, same pattern Phase 4.4 established
for `isDuplicateNationalId()`. The mock's live pre-submit duplicate check
(`store.organizations.find(...)`) is removed in favor of catching this
error at submit time, matching that same Phase 4.4 precedent exactly.

**Delete.** The existing `select.organizationInUse(org.id)` pre-check is
replaced by reading the already-fetched `row.aidCount` from `currentRows`
(no extra query — the count needed for this check is the same one already
displayed in the table), preserving the exact current UX (friendly
Arabic "توجد مساعدات مسجلة..." message, no API call attempted when blocked
client-side). If a race lets a delete through the pre-check but the DB's
`ON DELETE RESTRICT` still rejects it (`23503`, generically mapped to
`ErrorType.VALIDATION`), the catch block's fallback
`toast.error('تعذر الحذف', error.message)` still surfaces a Postgres-safe
Arabic message — not the exact "in use" wording, but never a raw SQL
error, and never a silent failure.

## 6 · Security

- Confirmed live: no `camp_id` predicate anywhere on `organizations`'
  four policies — the app's own `can('organization:manage')` check is a
  convenience, RLS is the actual and only boundary.
- No `service_role`/secret key/database password appears anywhere in
  `assets/js/` — nothing in this phase touches Cloudinary or any Edge
  Function, so this check is a formality here, confirmed anyway by grep
  before implementation and again in the diff review step.
- No hand-built trust of client state: `listOrganizationsWithUsage()`
  takes no camp/role argument at all — there is nothing to spoof.
- `ahmad@camps.ps` (displaced) is proven blocked two ways: the route guard
  (Playwright, real server) and, independently, a raw-client
  insert/update/delete attempt rejected by RLS with `42501` — the guard is
  never treated as the security boundary (§8).

## 7 · Testing

**`supabase/tests/phase4.9-role-authorization.test.mjs`** — no camp
partitioning (there is no camp boundary on this table), so this suite
proves the *role* boundary instead, the same rigor every prior phase's
camp-isolation suite applied to a camp boundary:

1. `super@camps.ps` and `admin@camps.ps` (two different roles) each get
   full `select`/`insert`/`update`/`delete` on `organizations` via a raw,
   RLS-scoped client.
2. `ahmad@camps.ps` (displaced): a raw-client `insert`/`update`/`delete`
   attempt is rejected with `42501`. A raw `select` is **allowed** by RLS
   (confirmed intentional, §2/§6) — not asserted as a failure.
3. An anonymous (no session) call to any of the four operations is
   rejected.
4. `organizations.html` loaded as `ahmad@camps.ps` redirects via the route
   guard (Playwright, real server, not jsdom) rather than rendering.
5. No `service_role` key or other private credential reaches the browser
   (same assertion style as every prior phase).

Every fixture this suite creates is deleted in `finally`, regardless of
assertion outcome.

**`supabase/tests/phase4.9-organizations-verification.test.mjs`** — same
DB-vs-UI shape as `phase4.7-registration-requests-verification.test.mjs`:
an independent service-role client recomputes what the rendered page
should show.

1. List: rendered row count/content matches a direct `select`.
2. Search: typing a fixture donor's name filters to exactly that row.
3. Summary stats (donor count, total aid distributions, donors with a
   phone) match a direct computation.
4. Per-row `aidCount`/`familiesCount` match the same join query run live
   during investigation (§2).
5. **Create round trip:** create a donor through the real UI form, assert
   it appears in the list and a direct query shows the row.
6. **Duplicate name rejected:** submitting a name that differs only in
   case/whitespace from an existing donor (`lower(btrim(name))` — §2) is
   rejected with the duplicate message, and no second row is created.
7. **Edit round trip:** update phone/responsible person, assert the DB
   reflects it.
8. **Delete blocked while in use:** attempting to delete one of the 7
   seeded donors with `aidCount > 0` shows the friendly "in use" message
   and leaves the DB row untouched.
9. **Delete round trip:** a fixture donor with zero aid usage is deleted
   successfully; asserted gone from both the rendered list and a direct
   query.
10. Empty-result search case renders the existing `emptyState()`, not a
    blank panel or console error.

Every fixture this suite creates is deleted in `finally` regardless of
assertion outcome.

**Full regression:** `cd supabase && npm run test:all` must stay fully
green. No existing test's assertions are weakened.
