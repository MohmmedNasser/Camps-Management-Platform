# Phase 4.8 — Documents & File Management on Real Data

**Date:** 2026-09-23
**Status:** Approved — proceeding to implementation

## 1 · Context

Phase 4.8 connects the Camp Admin's document workflow — `pages/documents.html`
(the only document page; there is no separate details page and no Excel
export for documents anywhere in this app) — to real Supabase + Cloudinary
data. Unlike every prior Phase 4.x page, most of the backend work already
exists and is already live:

- **Phase 2** built metadata-only CRUD in `assets/js/supabase/documents.js`
  (`listDocuments`, `getDocument`, `createDocumentMetadata`,
  `updateDocumentMetadata`, `deleteDocumentMetadata`) — generic, no
  camp-scoped `getCampX()` function yet, unlike `families.js`/
  `family-members.js`/`aids.js`.
- **Phase 3** built and shipped three Cloudinary Edge Functions
  (`documents-upload`, `documents-access`, `documents-delete`) plus
  `assets/js/supabase/cloudinary.js` (`uploadDocument`, `getDocumentBlob`,
  `deleteDocumentAsset`). Confirmed live via `mcp__supabase__list_edge_functions`:
  all three `ACTIVE` (`documents-upload` v8, `documents-access` v9,
  `documents-delete` v6).
- **Phase 4.1** switched every role's login to real Supabase Auth. This is
  the detail that makes this phase necessary now: `documents.js`'s
  `backendAvailable()` check (`isConfigured && Boolean(await
  currentUserId())`), dormant since Phase 3 because no page ever
  established a real session, has been returning `true` for every real
  session since Phase 4.1 shipped.

**The concrete, currently-live bug this phase fixes.** `documents.js`'s
upload modal builds its person-picker via `peopleFor(session)`, which for
every role still calls the **mock** `select.personOptions({campId})` —
reading `core/store.js`'s localStorage `displaced` collection, whose ids
(`'d-1'`, `'d-2'`, …) and camp ids (`'camp-1'`, …) never match a real
session's UUIDs. Two failure modes follow, both reproducible today against
the live project:

1. For a **real Camp Admin session**, `select.personOptions({campId:
   session.campId})` filters mock rows by a real UUID `campId` that no mock
   row has — the picker returns `[]`, and `openUploader()`'s own guard
   (`if (!people.length) { toast.error(...); return; }`) fires immediately.
   Upload cannot even open.
2. If a mock person were ever selected (e.g. a stale render), submitting
   calls `cloudinary.uploadDocument({ familyMemberId: values.displacedId,
   ... })` with a non-UUID string. `documents-upload`'s ownership-resolution
   query (`select id, family_id, camp_id from family_members where id =
   :familyMemberId`) returns no row for a malformed/nonexistent id, and the
   function returns the generic `403 لا تملك صلاحية رفع مستند لهذا السجل`.

Both are fixed by giving the Camp Admin branch a real person list
(`getCampDisplacedPersons`, already built in Phase 4.5) instead of the mock
one — the same "swap the data source, keep the UI" pattern every prior
phase used.

**A second, independent gap found in the same investigation:**
`openPreview(row)` only renders an `<img>` when `row.dataUrl` is set (the
mock/local-file path). It never calls `cloudinary.getDocumentBlob(id,
{mode:'inline'})` even when `row.backendId` is present, so a real,
image-type, Cloudinary-backed document always falls into the "no preview
available" placeholder today — even though `documents-access` was built
specifically to serve exactly this (BACKEND.md §16.1: "download **and**
preview share this one function"). This phase wires it up for real rows.

**Documents-details / Excel export are correctly out of scope — nothing
exists to connect.** Confirmed: no `document-details.html` anywhere in the
repo, and `documents.js` has no `data-export` handler. `DOCUMENT_CATEGORIES`
already covers every category the real `document_category` enum has
(`id_card`, `passport`, `birth_certificate`, `medical_report`, `other`).

## 2 · Live schema/RLS/Edge-Function findings (verified via Supabase MCP against project `qlvftlecwoqmvtagaykr`)

**Table `documents`** (82 live rows at investigation time — see §6) —
columns: `id, name, category (document_category), camp_id, family_id
(nullable), family_member_id (nullable), registration_request_id
(nullable), original_filename, mime_type, file_size, storage_provider
('pending'|'cloudinary'), file_url, cloudinary_public_id, secure_url,
resource_type, format, uploaded_by, created_at, updated_at`. All of
`family_member_id` → `family_members`, `family_id` → `families`,
`uploaded_by` → `profiles` are **real foreign keys** — unlike
`family_stats`/`family_member_facts` (Phase 4.4/4.5's views), a
PostgREST nested `select` embeds these directly with no separate-query
workaround needed.

**RLS (4 policies, matches BACKEND.md §7/§16 exactly, confirmed live):**

- `documents_select_scoped` — `is_super_admin() OR (is_camp_admin() AND
  camp_id = current_camp_id()) OR (is_displaced() AND family_id =
  current_family_id())`.
- `documents_insert_scoped` — same three-way shape, `WITH CHECK`.
- `documents_update_admin` — super_admin or own-camp camp_admin, both
  `USING` and `WITH CHECK`. (Unused by this phase — no document-edit UI
  exists or is being added; `private.guard_document_privileges()` further
  restricts a plain `UPDATE` to `name`/`category` only, per BACKEND.md
  §16.4.)
- `documents_delete_admin` — same super_admin/own-camp-admin shape.

**Edge Functions — read live, not assumed:**

- `documents-upload/index.ts` resolves `camp_id`/`family_id` **server-side**
  from whichever of `family_member_id` / `family_id` /
  `registration_request_id` was sent, via an RLS-scoped `select` — a
  client-supplied `camp_id` is never trusted. This phase's UI only ever
  sends `family_member_id` (unchanged from today's mock-path behavior),
  exactly like the existing `documents-upload` caller in `cloudinary.js`.
- `documents-access/index.ts` returns a clean, generic `404 لا يتوفر ملف
  مرفوع لهذا المستند` when `storage_provider !== 'cloudinary'` — safe to
  call for a `pending`-storage row, but the UI still gates the
  download/preview icon on `storage_provider === 'cloudinary'` so a Camp
  Admin never sees a button that's guaranteed to fail.
- `documents-delete/index.ts` checks `storage_provider === 'cloudinary' &&
  cloudinary_public_id` before attempting a Cloudinary `destroy` — a
  `pending`-storage row is deleted (metadata only) with **no** Cloudinary
  call attempted. This means delete is always safe to call with just the
  document's own `id`, regardless of `storage_provider` — no branching
  needed in the frontend.

**Security advisors** (`mcp__supabase__get_advisors`, type `security`):
identical to the Phase 4.7 baseline — the same 5 expected
`authenticated_security_definer_function_executable` WARNs (workflow RPCs,
each internally authorized) plus the pre-existing
`auth_leaked_password_protection` WARN (a dashboard toggle, unrelated to
any phase's code). **No backend/migration change is required or made by
this phase.**

## 4 · `getCampDocuments()` and row shaping

```js
const DOCUMENT_SELECT =
  '*, member:family_members(full_name), family:families(reference_code), uploader:profiles!documents_uploaded_by_fkey(full_name)';

export async function getCampDocuments(campId) {
  const client = requireClient();
  const rows = await run(
    client.from('documents').select(DOCUMENT_SELECT).eq('camp_id', campId).order('created_at', { ascending: false })
  );
  return rows.map(mapDocumentRow);
}
```

RLS (`documents_select_scoped`) independently scopes every row to the
caller's own camp regardless of the `campId` argument — the explicit
`.eq('camp_id', campId)` matches the established `getCampFamilies()`/
`getCampDisplacedPersons()` convention (a query hint, not the security
boundary) rather than being one itself.

`mapDocumentRow(row)` produces exactly the shape `resultsView()` /
`openPreview()` / `summaryView()` in `documents.js` already read (so none of
that rendering code needs to change):

```js
function mapDocumentRow(row) {
  return {
    id: row.id,
    name: row.name,
    category: row.category,
    categoryLabel: labelOf(DOCUMENT_CATEGORIES, row.category),
    categoryIcon: (DOCUMENT_CATEGORIES.find((c) => c.value === row.category) || {}).icon || 'folder',
    personName: row.member?.full_name || '—',
    familyId: row.family?.reference_code || '',
    campId: row.camp_id,
    size: row.file_size || 0,
    mime: row.mime_type || '',
    uploadedAt: row.created_at,
    uploaderName: row.uploader?.full_name || '—',
    dataUrl: '',
    // Reuses the EXISTING backendId convention: everywhere in documents.js
    // a truthy backendId already means "this row has a Cloudinary asset,
    // addressable through the Edge Functions by this id." A pending-storage
    // row (no real asset yet) gets '' so the existing, unmodified
    // `row.dataUrl || row.backendId` check in resultsView()/openPreview()
    // correctly disables its download/preview icon.
    backendId: row.storage_provider === 'cloudinary' ? row.id : '',
  };
}
```

`DOCUMENT_CATEGORIES`/`labelOf` are imported from `core/config.js`, same as
the mock's own `documentRow()` in `selectors.js` — no new label list.

## 5 · `documents.js` — the real Camp Admin branch

**Person picker.** `init()` becomes `async`. For Camp Admin only, it awaits
`getCampDisplacedPersons(session.campId)` (Phase 4.5, `family-members.js`,
reused unchanged) once, before the first `load()`, caching
`{value: id, label: fullName}` pairs module-level as `campPeople` — same
"fetch real option lists once in `init()`" convention `aid.js`'s
`campAdminOptions` already established, needed here because `peopleFor()`
must stay callable synchronously from `openUploader()`.

```js
function peopleFor(session) {
  if (session.role === ROLES.CAMP_ADMIN) return campPeople;
  if (session.role === ROLES.DISPLACED) { /* unchanged mock path */ }
  return select.personOptions({ campId: '' }); // unchanged mock path (Super Admin)
}
```

**List + filters + summary stat.**

```js
async function collect(session) {
  if (session.role !== ROLES.CAMP_ADMIN) {
    return { rows: select.searchDocuments({ query: state.q, category: state.category, campId: state.campId, session }), allRows: null };
  }
  const allRows = await getCampDocuments(session.campId);
  const rows = allRows.filter((row) => select.matchesDocumentFilters(row, { query: state.q, category: state.category }));
  return { rows, allRows };
}
```

`load(session)` calls `collect()`, keeps the resulting `rows` in a
module-level `currentRows` array (§ below), and passes `allRows` into
`summaryView(session, rows, allRows)`. `summaryView` computes the "أنواع
المستندات" (distinct-category) stat from `allRows ?? select.documentsFor(session)`
so the count still reflects every one of the camp's documents regardless of
the active search/category filter — exactly what `select.documentsByCategory()`
already guarantees for the mock branch (it calls `documentsFor(session)`,
not the filtered `rows`).

**Row lookups for actions.** `data-preview` / `data-download` / `data-delete`
currently resolve their row via `store.documents.get(id)` — which does not
contain real Camp Admin rows at all once the list stops mirroring into
localStorage. All three handlers switch to `currentRows.find((r) => r.id ===
id)` instead. This is a **single change that needs no role branching**: both
`documentRow()` (mock) and `mapDocumentRow()` (real) already produce the same
field shape, so the same lookup and the same `downloadDocument()`/`openPreview()`
functions work unmodified for either branch.

**Delete.** Camp Admin: `await cloudinary.deleteDocumentAsset(row.id)` (not
`row.backendId` — confirmed live in §2 that delete is safe to call
regardless of `storage_provider`) then `load(session)`. No
`store.documents.remove()` — the row was never mirrored into the mock
store. Every other role's path (`store.documents.remove(row.id)`) is
unchanged.

**Upload.** Camp Admin: `await cloudinary.uploadDocument({file, name,
category, familyMemberId})` (unchanged call — now finally reachable with a
real UUID) then `load(session)`. **No more `store.documents.create({...,
backendId})` mirroring** — the real row is already the source of truth and
`load()` re-fetches it, removing the bridging hack Phase 3 built for a world
where no page had a real session yet. Every other role's mock-create path
is unchanged.

**Preview.** `openPreview(row)`: when `row.backendId` is truthy and
`row.mime` starts with `image/`, fetch `await
cloudinary.getDocumentBlob(row.backendId, {mode:'inline'})`, build an object
URL, and swap the placeholder markup for an `<img>` (revoking the URL via
`modal.onClose`). A real PDF (`row.backendId` set, `row.mime` not an image
type) keeps today's existing, still-accurate "no preview available, use
download" copy. Mock rows with `row.dataUrl` are completely unchanged.

## 6 · Data-hygiene finding: Phase 3 test debris

Confirmed live via `execute_sql` grouping `documents` by `camp_id,
storage_provider, category`: 82 total rows = the 12 legitimate
`storage_provider='pending'` seed rows (BACKEND.md §11) **plus 70 leftover
`storage_provider='cloudinary'` rows** — 35 `id_card` in مخيم الرحمة and 35
`medical_report` in مخيم النور, each with a real Cloudinary asset still
live. Root cause, confirmed by reading `supabase/tests/phase3-documents.test.mjs`
in full: it uploads real files through the live Edge Functions (18
assertions, "18/18 pass") but has **no `finally`/cleanup block anywhere in
the file** — every `npm run test:phase3` run, including every `npm run
test:all` run across Phases 4.1–4.7's own regression checks, has been
adding more debris to the live project.

**Fix (in scope for this phase):**

1. Add a `finally`-based teardown to `phase3-documents.test.mjs`: track
   every document id its `upload()` helper creates across all `test()`
   blocks in a module-level array, and after the suite's tests finish,
   delete each row via the service-role client and destroy its Cloudinary
   asset (reusing the same signed-`destroy` request shape as
   `_shared/cloudinary.ts`, called directly with `fetch` since the test
   runs in Node, not Deno).
2. One-time cleanup of the 70 already-existing leftover rows/assets: a
   small local Node script (run once, not committed) that selects exactly
   the two identified batches (`storage_provider='cloudinary' AND category
   IN ('id_card','medical_report')` scoped to the two camp ids found in
   §investigation), destroys each `cloudinary_public_id` via the Cloudinary
   Admin API (secret from `.env`, never touching frontend code), then
   deletes the rows via the service-role client. The 12 legitimate
   `pending`-storage seed rows are untouched by construction (the query
   filters on `storage_provider='cloudinary'`).

## 7 · Security

- No `service_role`/secret key/database password/Cloudinary secret appears
  anywhere in `assets/js/` — confirmed by grep before implementation and
  again in the diff review step. The Cloudinary secret is used only inside
  Edge Functions (unchanged, Phase 3) and the one-off local cleanup script
  in §6 (Node, run locally, not committed, not imported by anything under
  `assets/js/`).
- No client-side-only authorization: upload/download/delete all go through
  the three Edge Functions, each of which re-derives `camp_id`/ownership
  server-side from an RLS-scoped query (§2) — never from a client-supplied
  value. The frontend's own gating (`can('document:upload')`,
  `can('document:delete')`, the download-icon `backendId` check) are
  conveniences, not the boundary.
- No hand-built `?campId=` trust: `getCampDocuments(session.campId)` is
  session-derived, matching every other `getCampX()` function; RLS
  independently re-scopes every row regardless of what's passed.
- Camp isolation is proved by tests (§8), not just by reading the policy
  text.

## 8 · Testing

**`supabase/tests/phase4.8-camp-isolation.test.mjs`** — same shape as
`phase4.6-camp-isolation.test.mjs`/`phase4.7-camp-isolation.test.mjs` (two
seeded Camp Admins, `admin@camps.ps` / مخيم النور and `nour@camps.ps` /
مخيم الرحمة):

1. Each admin's RLS-scoped `select` on `documents` returns only their own
   camp's rows (raw client).
2. A raw `.update()`/`.delete()` on another camp's document row matches
   zero rows.
3. Uploading (via the real `documents-upload` function) with a
   `family_member_id` that belongs to another camp is rejected with `403`
   — the ownership-resolution query itself returns nothing under RLS.
4. The rendered list at `documents.html` for one admin never contains the
   other camp's document names or person names.

Fixtures (a small real image upload per test, reusing
`phase3-documents.test.mjs`'s existing tiny fixture files) are deleted —
row **and** Cloudinary asset — in a `finally` block, per the test-debris
finding in §6.

**`supabase/tests/phase4.8-documents-verification.test.mjs`** — same shape
as `phase4.7-registration-requests-verification.test.mjs`: an independent
service-role query recomputes what the rendered page should show:

1. List: rendered row count and content match a direct `count(*)`/`select`
   scoped to `camp_id`.
2. Search: typing a fixture document's name filters to exactly that row.
3. Category filter: matches a direct per-category count.
4. Summary stat ("أنواع المستندات"): matches a direct distinct-category
   count over the **whole** camp, independent of the active filter.
5. **Upload round trip:** drive the real upload form (a tiny real JPEG
   fixture) through `admin@camps.ps`, assert the new row appears in the
   list with the correct name/category/person, and that a direct query
   shows `storage_provider='cloudinary'` with a real `cloudinary_public_id`.
6. **Preview:** fetch the same document's blob via
   `getDocumentBlob(id,{mode:'inline'})` directly and assert the returned
   bytes match the uploaded fixture's bytes.
7. **Delete round trip:** delete via the UI, assert the row is gone from
   both the rendered list and a direct query, and that the Cloudinary asset
   no longer resolves.
8. Empty-result case (a filter combination matching nothing) renders the
   existing `emptyState()`, not a blank panel or console error.

Every fixture this suite creates is deleted in `finally` regardless of
assertion outcome, and the suite's own teardown asserts zero leftover rows
for the ids it tracked — directly enforcing the test-debris decision from
§6 for all future runs.

**Full regression:** `cd supabase && npm run test:all` (now including the
fixed `test:phase3` and the two new suites) must stay fully green. No
existing test's assertions are weakened.
