# Phase 4.18 — Test Stabilization (Pre-Existing Regression Failures) — Design

## 1. Goal

Bring `npm run test:all` back to 0 failures by fixing three pre-existing,
already-documented test defects — not application defects — without
changing any application behavior, schema, RLS, Edge Function, or seed
data. No new phase of feature work is in scope.

Phase 4.17 (family activation) is complete and its own suites are green
(40/40). Its final regression run already named these three failures as
pre-existing and out of scope for that phase (see `BACKEND.md` §31 / the
Phase 4.17 entry in `CLAUDE.md`). This phase closes them out properly.

## 3. Root cause of each

### 3.1 Phase 4.5 — pagination-blind assertion, not a filter bug

`assets/js/core/config.js` sets `PAGE_SIZE = 10`; `displaced.js` filters
first, then slices the filtered array into pages
(`resultsView(session, rows)`, `assets/js/pages/displaced.js:456-461`) — the
gender filter itself is applied before pagination, so a correct UI can
still fail a test that only reads page 1.

The **same test file** already has a correct pattern for this: the sibling
subtest `"unfiltered list (across every page)"` calls a helper,
`collectAllPagesText(page, base, path)` (`phase4.5-displaced-
verification.test.mjs:88-102`), which reads the `"عرض X–Y من N"` pagination
string, computes how many pages exist, and walks all of them. The
`"gender=male filter"` subtest (lines 142-157) does **not** use this helper
— it does a single `page.goto` + `body.innerText()` and checks membership
directly. This is the exact trap the file's own comment above
`collectAllPagesText` (line 83-87) already calls out, and the exact
reasoning `BACKEND.md`'s Phase 4.5 entry used to explain the equivalent
unfiltered-list subtest.

**Independently confirmed via a service-role query** (bypassing the app and
the test entirely): camp مخيم النور currently has 19 `family_members` rows,
12 of them `gender = 'male'`. 12 > `PAGE_SIZE` (10), so 2 males land on
page 2. `محمد جميل ناصر` (created `2026-09-27T11:35:35Z`, alongside two
other family members from the same manual/dev session) is one of the two
that don't fit on page 1. `nour@camps.ps`'s camp has far fewer members, so
its copy of the same subtest never crosses the pagination boundary and
passes.

**This is a test defect, not an application defect:** the filter itself is
proven correct — every rendered male name across *all* pages would match
(confirmed by the working `collectAllPagesText` pattern used elsewhere in
the same file), and no female name renders on any page. The single-page
subtest simply never looked at page 2.

### 3.2 / 3.3 Phase 4.15 / 4.16 — stale hardcoded live-account baseline, not an application defect

Both isolation suites contain a `"Displaced (ahmad) regression"` subtest
that hardcodes ahmad@camps.ps's expected unread-notification count as the
literal string `'2'`. That number was correct the day Phase 4.14 first
wrote the check.

**Independently confirmed via a service-role query:**

```
ahmad total notifications: 3
ahmad unread count: 3
 - 4c94178d… UNREAD info    2026-08-05  لديك رسالة جديدة من إدارة المخيم
 - c87cfe3d… UNREAD info    2026-08-10  تمت إضافة مساعدة جديدة إلى ملفك
 - 619b3b72… UNREAD success 2026-08-11  تم قبول طلب التسجيل
```

All three rows are dated in August 2026 — long before this session's test
runs (2026-09-28) or Phase 4.17's work (2026-09-27) — and read as ordinary
seeded content, not test debris (no "اختبار"/test-fixture naming, no
recent timestamps). This is legitimate accumulated seed/dev state: a third
notification was added for ahmad at some point after Phase 4.14 hardcoded
`'2'`, and the isolation tests were never updated to match.

The same class of hardcode exists for other live seeded accounts in the
same two files, all currently passing only because their underlying counts
happen to still match:

| File | Line(s) | Account | Hardcoded | Live (confirmed) |
|---|---|---|---|---|
| phase4.15-notifications-isolation | 184 | admin@camps.ps | `'2'` | 2 (passes today) |
| phase4.15-notifications-isolation | 256 | ahmad@camps.ps | `'2'` | 3 (**fails**) |
| phase4.16-dashboard-notifications-isolation | 112 | admin@camps.ps | `'2'` | 2 (passes today) |

Every one of these shares the identical fragility: a live seeded account's
notification count can legitimately change over time (more seed rows, more
manual dev testing against these accounts), and a hardcoded expectation
will eventually drift and fail for a reason that has nothing to do with
the behavior under test. Only the two ahmad assertions have drifted so
far, but fixing only those two would leave five identical time bombs in
the same two files, still asserting on a mutable live number.

**This is a test defect, not an application defect:** in every case, the
app is rendering the account's *true* current unread count (proven by the
already-existing, already-passing `phase4.16-dashboard-notifications-
verification.test.mjs`, which computes `expectedUnread` from an independent
`serviceClient` query per account rather than hardcoding it — see
`tests/phase4.16-dashboard-notifications-verification.test.mjs:119-148`).
The isolation suites just never adopted that pattern for these particular
assertions.

## 4. Proposed correction

### 4.1 Phase 4.5

Change the `"gender=male filter"` subtest
(`phase4.5-displaced-verification.test.mjs:142-157`) to build its assertion
text from `collectAllPagesText(page, base, '/pages/displaced.html?gender=male')`
instead of a single `page.goto` + `body.innerText()`. `collectAllPagesText`
already exists in this file, is already proven correct by the passing
unfiltered-list subtest, and needs no change itself — `path.includes('?')`
already makes it emit `&page=2` when the path already carries `?gender=male`,
so no dedicated support for combining filters and pagination needs to be
added. This is the smallest change consistent with the file's existing
convention; no other subtest in the file needs this treatment (only this
one reads a filtered result set that can exceed one page for at least one
seeded camp).

Not changed: `PAGE_SIZE`, `displaced.js`, any pagination or filter logic.

### 4.2 / 4.3 Phase 4.15 / 4.16

For every hardcoded live-account unread count listed in §3.2/3.3's table
(both ahmad assertions, and the five currently-passing ones sharing the
same fragility), replace the literal string with a value derived
independently, in the same subtest, from the `serviceClient` that both
files already construct at the top of their `test(...)` block:

```js
const { data: authUser } = await serviceClient.auth.admin.listUsers();
const user = authUser.users.find((u) => u.email === email);
const { count: expectedUnread } = await serviceClient
  .from('notifications')
  .select('id', { count: 'exact', head: true })
  .eq('recipient_id', user.id)
  .eq('is_read', false);
```

then assert the rendered badge/stat equals `expectedUnread` (numeric
compare) instead of a literal. This is the exact pattern the sibling
verification suites already use and have already proven correct
(`phase4.15-notifications-verification.test.mjs`,
`phase4.16-dashboard-notifications-verification.test.mjs`) — no new pattern
is invented, and no shared helper is extracted across files (each suite
stays self-contained, matching the existing convention of duplicated
boilerplate across these test files rather than a shared test-utils
module).

For the `nour@camps.ps` (`'0'`) case specifically, the fix additionally
asserts the independently-queried count is `0` as a precondition (mirroring
`phase4.16-dashboard-notifications-verification.test.mjs:151-153`) before
asserting the UI renders `'0'` — this is strictly stronger than today's
version, not weaker: it now fails loudly (with a clear precondition
message) if that account ever legitimately stops being the zero-notification
control, instead of failing with a confusing UI-vs-expectation mismatch.

No production code, RLS policy, or notification query changes. These are
read-only `select(... , { count: 'exact', head: true })` queries against a
service-role client the tests already hold; they add no new database
round-trip pattern beyond what the verification suites already exercise.

## 5. Why this is a test issue, not an application defect (summary)

- The displaced list, its gender filter, and its client-side pagination
  are all independently proven correct by the passing
  `collectAllPagesText`-based subtest in the same file and by
  `phase4.5-camp-isolation.test.mjs`. No change to `displaced.js`,
  `core/selectors.js`, or `core/config.js` is needed or made.
- The notification badge/stat rendering is independently proven correct by
  the passing `phase4.15-notifications-verification.test.mjs` and
  `phase4.16-dashboard-notifications-verification.test.mjs`, which compute
  their expectation the same way this phase adopts for the isolation
  suites. No change to `ui/layout.js`, `dashboard.js`, or
  `assets/js/supabase/notifications.js`/`dashboard.js` is needed or made.
- In both cases the failure is the test asserting a specific, stale,
  point-in-time number instead of the behavior ("the filter shows exactly
  the matching records," "the badge shows the account's real unread
  count") the test was written to protect.

## 6. Data-safety strategy

- No seed row is inserted, deleted, or permanently modified by this phase.
- Camp مخيم النور's 19 `family_members` rows (including the
  Phase 4.17-era `اختبار مهمة سبعة` row from an earlier, unrelated phase)
  are left untouched — deleting or renaming any of them is investigation
  of a different, out-of-scope issue and is explicitly not this phase's
  job (see §7).
- ahmad@camps.ps's three notification rows are left untouched — the fix
  makes the test read the real count, not force the count to match the
  test.
- The new `serviceClient` queries added to the isolation subtests are all
  read-only (`select`), so no `finally`/restore block is needed for them —
  no new mutation is introduced. The existing mark-all-read subtests in
  both files already correctly do capture → mutate → assert → restore, and
  are unmodified by this phase.
- No `.env`, credential, or RLS policy changes.

## 7. Regression strategy

1. Fix Phase 4.5's subtest; run `npm run test:phase4.5-displaced` alone
   until green.
2. Fix Phase 4.15's subtests; run
   `npm run test:phase4.15-notifications-isolation` alone until green.
3. Fix Phase 4.16's subtests; run
   `npm run test:phase4.16-dashboard-notifications-isolation` alone until
   green.
4. Run the three affected suites' sibling verification suites
   (`test:phase4.5-camp-isolation` already covers gender/camp-scoping from
   another angle; `test:phase4.15-notifications-verification`,
   `test:phase4.16-dashboard-notifications-verification`) to confirm no
   regression from editing adjacent code in the same files.
5. Run the full `npm run test:all` and require exit code 0 / 0 failures
   before considering the phase done. If any *other* suite fails, treat it
   as a new investigation (systematic debugging from Phase 1), not
   something to paper over — out of scope for this phase's fix unless it
   is a genuine regression caused by this phase's own edits.
6. Re-run the independent DB verification queries (ahmad's notification
   count, camp النور's member counts) after the full suite to confirm
   nothing was mutated.

## 8. Explicit out-of-scope items

- The `اختبار مهمة سبعة` leftover record in camp مخيم النور (created
  2026-08-19, predates this phase, unrelated to Phase 4.17 or this phase) —
  flagged here for visibility, not remediated. Removing pre-existing test
  debris from earlier, unrelated phases is a separate cleanup task, not
  part of "fix these three named test failures without unnecessary
  behavior change."
- The `رنا عصام قديح` row's gender ("male") looking inconsistent with a
  typically-female given name — a possible seed-data quality issue,
  unrelated to any of the three failures, not touched.
- Any React/Next.js migration work.
- Any schema, RLS, or Edge Function change.
- Any change to `displaced.js`, `PAGE_SIZE`, `ui/layout.js`,
  `dashboard.js`, or any notification query module.
- Extracting a shared test-utilities module across the affected files —
  the existing convention in `supabase/tests/` is self-contained files
  with duplicated boilerplate; introducing shared infrastructure here
  would be scope creep beyond "stabilize these three assertions."
