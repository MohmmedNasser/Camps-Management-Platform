# Phase 4.17 — Displaced Family Account Activation & Secure First Login

Design doc. Companion implementation plan:
`docs/superpowers/plans/2026-09-27-phase-4.17-family-account-activation.md`.

## 1 · The gap

A Camp Admin registers a family through `family-create.html` →
`create_family_with_members()` (Phase 4.4/2). That call creates
`families`/`family_members` rows only — no `auth.users` row, no `profiles`
row. There is no path today for that family's head to ever sign in: they
have no email/password anywhere, and `register.html` creates a *new*,
unrelated family via `registration_requests`/`approve_registration_request`.
This phase adds the missing link: **Camp Admin generates a one-time
activation link for an existing family → the head opens it, proves they are
who the family record says the head is, chooses a password → a real
Supabase Auth account is created and linked to that exact `family_members`
row.**

## 2 · Identity model recap (from live schema, not assumed)

- `family_members` **is** the displaced-person table (Phase 4.5's own
  finding, re-confirmed by reading `20260816120000_initial_schema.sql`
  directly). `families.head_member_id` names the head; a deferred
  constraint trigger (`private.enforce_family_head`) guarantees every family
  has exactly one head who is one of its own members — "family has no valid
  head" is a live DB invariant, not just a state this phase must defend
  against defensively.
- `profiles.family_member_id` is the ONLY link between an Auth account and a
  person (Phase 4.12/4.13's identity chain: `auth.uid() → profiles →
  family_member_id → family_members → families`). This phase's whole job is
  populating that link for a family that was never routed through
  `registration_requests`.
- `family_members.national_id` is `unique` platform-wide, format
  `^[0-9]{9}$` (domain rule 2). `families.reference_code` is `unique`,
  format `FAM-######`. `family_members.birth_date` is `NOT NULL` in every
  record the app's own forms can produce (`record-forms.js` requires it for
  both the head and member forms — verified by reading the validation
  schema, not assumed), even though the column itself is nullable at the DB
  level.
- `profiles.role` defaults to `'displaced'` and is hard-coded by
  `private.handle_new_user()` on every `auth.users` insert — a freshly
  created account is already the right role before this phase writes
  anything. `profiles.status` defaults to `'pending'`; this phase must set
  it to `'approved'` (the only status that reaches the dashboard —
  `core/router.js`'s `guard()` sends `pending`/`rejected` to their own
  screens) since the identity check IS the approval.

## 3 · Login identifier — the one architecture question with real options

`assets/js/supabase/auth.js` calls `client.auth.signInWithPassword({email,
password})`. This project's Supabase Auth is configured for email/password
only (no phone provider, confirmed by every existing account —
seed/admin-create-camp-admin/self-registration — carrying a real email).
Two options were evaluated for the newly-activated account's login
identifier:

**Option A (rejected): synthetic email + national-ID login.** Generate an
internal, non-deliverable email at activation time and let the head log in
by typing their national ID, resolved to the synthetic email by a public
RPC before calling `signInWithPassword`. Rejected because:
- It requires a secret-keyed derivation (HMAC pepper, e.g. via Supabase
  Vault) so the synthetic email isn't guessable from the national ID alone
  — real complexity for a project with no other secret-management code path.
- The resolve-by-national-ID RPC is unavoidably a partial oracle: even
  returning a same-shaped fake result for a non-existent ID only closes the
  gap if implemented perfectly, and it is one more anonymously-callable
  endpoint whose only job is to be probed. The spec explicitly warns against
  building exactly this kind of "does X exist" surface for the *activation*
  fields; building an equivalent one for login just moves the risk.
- It requires changing `login.html`'s UX (spec: "do not change the login
  UX until the underlying Auth mechanism is verified... adapt only as much
  as necessary").

**Option B (chosen): collect a real, unique email at activation time.** The
activation form asks for the email the head wants to log in with —
pre-filled from `family_members.email` when the head's record already has
one, editable otherwise. This is passed straight to
`auth.admin.createUser({email, password, email_confirm: true})`, exactly
like every other account in this project. **No email is ever sent** — the
`email_confirm: true` flag (used identically by Phase 4.11's
`admin-create-camp-admin` and by `supabase/seed/seed.mjs`) means the address
never leaves the Camp Admin/head's own conversation and is used purely as a
Postgres-unique login identifier, satisfying "no email delivery service
required." `auth.admin.createUser()`'s own uniqueness check is the
duplicate-email guard, mapped to a friendly `email_taken` error. **Zero
changes to `login.html`/`login.js`.**

This is "the smallest safe architecture change" the phase brief asks for
when the ideal (a non-email identifier) can't be built safely without new
secret-management infrastructure this project doesn't have.

## 4 · Identity verification fields (activation only, never login)

Chosen: **`families.reference_code` + head's `national_id` + head's
`birth_date`.** Reasoning:
- The activation *token* already scopes the request to one specific
  family/head — identity verification exists only to catch a leaked/
  forwarded/misdelivered link, not to "find" the family.
- All three fields are already collected by the existing registration form
  and are never present in the activation URL (which carries only the
  opaque token) or guessable from it.
- `reference_code` is semi-public (may be written on a physical file/receipt
  handed to the family) — alone it is not a secret. `national_id` is the
  person's own legal identifier. `birth_date` is a second, independent fact.
  Together they are a meaningfully strong three-factor check without
  collecting anything the schema doesn't already hold (no new field, no
  "head name" — a name is public-ish knowledge and adds little).
- Rejected: file/tent number (does not exist, domain rule 3), phone (not
  reliably collected, and reused elsewhere as a contact channel — weaker
  discriminator), full name (guessable/public).

All three must match exactly or the endpoint returns one generic message —
**`بيانات التفعيل غير صحيحة`** — regardless of which field(s) were wrong,
whether the token is expired/revoked/used, or whether the family/token
doesn't exist at all. The one deliberate exception is "already activated"
(§8, case 2): once the correct token + correct identity are both proven,
telling that specific caller "this account already exists, log in instead"
leaks nothing beyond what they already demonstrated they're entitled to
know.

## 5 · Token design

- **Table:** `private.family_activation_tokens` — in the `private` schema
  (never `public`), matching this project's existing convention that
  anything that must never be reachable via PostgREST lives there (the
  schema is not in `supabase/config.toml`'s `api.schemas`, so no accidental
  future `GRANT` can expose it — stronger than "public table + RLS with no
  policies"). Columns: `id`, `family_id` (FK, cascade), `head_member_id`
  (FK, cascade), `token_hash` (text, unique), `expires_at`, `used_at`,
  `revoked_at`, `failed_attempts` (int, default 0), `created_by` (FK to
  `profiles`), `created_at`. State is derived from the three timestamp
  columns + `now()`, the same convention `registration_requests` and
  `messages` already use (no redundant status enum to fall out of sync).
- **Generation:** `token = encode(extensions.gen_random_bytes(32), 'hex')`
  — 256 bits of entropy from `pgcrypto` (already installed, schema
  `extensions`, already used project-wide via `extra_search_path`). Stored
  as `token_hash = encode(extensions.digest(token, 'sha256'), 'hex')` — the
  raw token is returned to the caller exactly once and never persisted,
  per the spec's own preference.
- **Lifetime:** 7 days. Long enough for a Camp Admin to hand a physical/
  WhatsApp link to a family that may not check it same-day; short enough
  that a token nobody used stops being a live secret after a week.
- **One active token per family:** a partial unique index on `family_id`
  `where used_at is null and revoked_at is null`. Generating a new link
  first revokes any still-active token for that family in the same
  statement, then inserts the new row — so the index is a backstop, not the
  only thing enforcing the rule.
- **Failed-attempt lockout:** `failed_attempts` increments on every identity
  mismatch; at 10 the token is auto-revoked (same generic error is
  returned, so the caller cannot tell a lockout just happened) — bounds a
  brute-force attempt against `national_id` + `birth_date` by anyone who
  did obtain a valid token, beyond what token secrecy alone provides.
- **Single-use / race safety:** see §6.

## 6 · Why the flow is split SQL-function / Edge-Function, and how races are closed

`auth.admin.createUser()` is a GoTrue Admin API operation — it cannot be
called from SQL, and it does not participate in a Postgres transaction.
Perfect cross-system atomicity ("consume token AND create the Auth user as
one unit") is therefore not achievable here, the same constraint
`admin-create-camp-admin` already lives with (its own design note: "the
sole failure window is the profiles UPDATE that follows [createUser]").
This phase follows the exact same shape:

1. **`public.verify_family_activation(p_token, p_reference_code,
   p_national_id, p_birth_date)`** — `SECURITY DEFINER`, granted to `anon`
   AND `authenticated` (the caller has no session at this point — this is
   the same trust model as any password-reset-confirm link: a possession-
   secret plus a knowledge-factor, not an authenticated request). Looks up
   the token by hash, checks not expired/revoked/used, compares the three
   identity fields, increments `failed_attempts`/auto-revokes at 10 on
   mismatch. Returns `(family_id, head_member_id, camp_id, full_name,
   already_activated)` on success — **does not mark the token used**, so an
   identity typo or a "the email I wanted is taken" retry never burns the
   Camp Admin's link.
2. Edge Function calls `service.auth.admin.createUser(...)`. A duplicate-
   email failure here is fully recoverable — token is still untouched, the
   head can resubmit with a different email on the same link.
3. **`public.consume_family_activation(p_token, p_new_user_id)`** —
   `SECURITY DEFINER`, granted to `service_role` ONLY (never `anon`/
   `authenticated`: calling this directly with an arbitrary
   `p_new_user_id` would let any caller re-point an unrelated profile's
   `family_member_id`, so unlike step 1 this one function must never be
   reachable by a browser key at all). Re-locks the token row `FOR UPDATE`,
   re-validates it is still unused/unexpired/unrevoked (closes the actual
   race window between two concurrent activations of the same family), sets
   `used_at = now()`, and performs the one `profiles UPDATE` (`status =
   'approved'`, `camp_id`, `family_member_id`, `full_name`) atomically with
   the token consumption. If two requests race past step 1 together, only
   one wins this `FOR UPDATE` lock and successfully consumes; the loser's
   `consume_family_activation` call raises, and the Edge Function responds
   to the rollback by calling `service.auth.admin.deleteUser()` on the
   Auth user IT just created (mirroring `admin-create-camp-admin`'s own
   documented rollback), leaving no orphaned account.
4. Frontend calls the ordinary `login(email, password)` (existing
   `core/auth.js`) to establish the normal Supabase session — **no parallel
   session mechanism.**

## 7 · Authorization: generation is Camp-Admin-only, own camp only

`public.generate_family_activation_token(p_family_id)` and
`public.get_family_activation_status(p_family_id)` are plain `SECURITY
DEFINER` RPCs (no Edge Function needed — they never touch
`auth.admin.*`), granted to `authenticated`, and each independently checks
`private.is_camp_admin() and private.current_camp_id() = (select camp_id
from public.families where id = p_family_id)` — the exact authorization
predicate `create_family_with_members`/`create_aid_distribution` already
use, re-derived from the database on every call, never trusting a
client-supplied camp id. A Camp Admin cannot generate a link for another
camp's family; RLS on `families` already means such a family isn't even
visible to them, but the explicit check makes the boundary a hard error
rather than an accidental `not found`.

**Super Admin is deliberately excluded from this phase.** Every existing
family-mutating action (`family:create`/`family:update`/`family:delete` in
`core/auth.js`'s `PERMISSIONS`, and the matching `families_insert/update/
delete_camp_admin` RLS policies) is Camp-Admin-only; Super Admin's role in
this app is camps/camp-admins/statistics, not day-to-day family
administration. Activation is a day-to-day family operation, so it follows
the same boundary as create/update/delete rather than being carved out as
an exception. If a future phase needs Super Admin oversight (e.g., an
audit view of activation status across camps), that is a new, additive
read-only capability — not a reason to widen who can *generate* a link
today.

## 8 · Case handling

1. **No Auth account** → normal path, §6.
2. **Account already exists** (`profiles.family_member_id = head_member_id`
   already set) → `verify_family_activation` returns `already_activated =
   true` (checked right after identity match succeeds, so this is not an
   independent oracle — see §4). Response: `409 already_activated`,
   `"هذا الحساب مفعل بالفعل"`, frontend shows a link to `login.html`. No
   account created, no token state change.
3. **Token already used** → collapsed into the generic `bad_activation`
   error (§4).
4. **Token expired** → same generic error. (The generic message is
   intentionally uninformative about *which* problem occurred — see §4 for
   why — so the UI copy also suggests "اطلب رابطًا جديدًا من إدارة المخيم"
   as a catch-all next step rather than branching UI copy per cause.)
5. **Token revoked** → same generic error.
6. **Identity mismatch** → same generic error, `failed_attempts += 1`.
7. **Family has no valid head** → cannot occur via the normal generation
   path (`generate_family_activation_token` reads `head_member_id` off
   `families` and that column is enforced non-null by a deferred
   constraint trigger at every commit); handled defensively anyway —
   `head_member_id is null` at generation time raises a clean `عملية غير
   صالحة` error rather than creating an unusable token.

## 9 · What's deferred

- **Password/account recovery.** Out of scope by the phase brief itself
  ("this phase is for first account activation, not full account
  recovery"). A displaced user who forgets their password today has the
  same option every other role has: none yet (`forgot-password.html` is
  pre-existing mock UI, unchanged by this phase, unchanged by any prior
  Phase 4.x either).
- **Super Admin activation-link visibility/regeneration** — see §7.
  Deliberately not built, not merely postponed by oversight.
- **Changing an existing activated account's login email** — same
  Admin-API-only limitation Phase 4.11/4.13 already documented and
  deferred for Camp Admin/self accounts; this phase does not touch it.
- **Rate limiting at the network layer** (e.g., capping activation attempts
  per IP). The `failed_attempts` lockout (§5) bounds the specific
  identity-guessing risk this phase introduces; a general network-level
  rate limiter is infrastructure this project has never had for any
  endpoint and is out of scope here.
