# Phase 4.2 — Super Admin Dashboard on Real Data

**Date:** 2026-08-18
**Status:** Approved for implementation

## 1 · Context

Phase 4.1 wired authentication, session and route guarding to real Supabase
Auth. Every dashboard, and all domain data, stayed on mock `core/store.js`.
`BACKEND.md` §14 places "dashboards" next in the connection order, and the
Super Admin variant is the one with the richest already-built backend
support: `get_dashboard_statistics(p_camp_id)` (Phase 2, §28), the
`family_stats` view, and full `camps`/`profiles` data-access modules
(`listCamps`, `listProfiles`) already exist and are already verified
independently (`supabase/tests/phase2-business-logic.test.mjs`,
`schema.test.mjs`).

Phase 4.2 connects **only the Super Admin dashboard** (`assets/js/pages/
dashboard.js`'s `superAdminView`/`campComparisonBar` path) to that real
backend. Camp Admin and Displaced-person dashboards, and every other page,
stay on mock data — later phases.

Live project verified via Supabase MCP before writing this spec:
`qlvftlecwoqmvtagaykr` (same project as Phase 4.1). RLS grants
`private.is_super_admin()` unrestricted `select` on every table this phase
reads (`camps`, `profiles`, `families`, `family_members`, `family_stats`,
`aid_distributions`, `organizations`, `registration_requests` — all
confirmed in `supabase/migrations/20260816120200_rls_policies.sql`), so a
Super Admin session can source every figure below through the anon/
publishable client with no `service_role` involvement.

## 2 · Non-negotiable constraints (from approval)

1. Reuse the existing `get_dashboard_statistics(p_camp_id)` RPC and existing
   data-access modules without modifying the backend.
2. Reuse the existing `family_stats` view, `listCamps()`, and
   `listProfiles()`.
3. Create `assets/js/supabase/dashboard.js` only for the additional
   dashboard-specific SELECT/composition functions that are genuinely
   missing.
4. No new/modified tables, columns, views, RPCs, functions, triggers, RLS
   policies, or migrations. Frontend integration only.
5. Keep existing dashboard UI rendering functions unchanged wherever
   possible.
6. Preserve the existing object shape consumed by `statistics()`,
   `campBreakdown()`, `superAdminView()`, `drawCharts()` and existing
   card/chart rendering.
7. `campAdminView`, `displacedView`, and their mock-data paths stay
   completely untouched.
8. `Promise.all` for independent Super Admin data requests where
   appropriate.
9. No `service_role` or private secret in browser code.
10. No RLS bypass.
11. Donor-organization count = distinct organizations that actually appear
    in aid distributions, not all registered organizations.
12. No fabricated data; a genuinely empty database renders the real
    zero/empty state.
13. Monthly registrations use real `created_at` values and the existing
    application's registration/member semantics — no invented business
    rule.
14. New data-access functions are parameterized by `campId` where
    practical, for reuse by a future Camp Admin Dashboard phase.
15. Reuse existing loading/skeleton/error/empty-state mechanisms — no new
    UI pattern.
16. Automated verification comparing rendered Super Admin statistics
    against direct Supabase/database results for the same metrics.
17. No `service_role` key, Cloudinary API secret, DB password, or other
    private credential reaches the browser.
18. Full existing test suite must stay green; baseline is 98/98.
19. No push to the remote repository.
20. Work in an isolated worktree; merge to `main` only after tests and
    browser verification pass.
21. This document is written, and the schema/code re-reviewed, before
    implementation. A conflict with this design is reported, not silently
    worked around.
22. No Phase 4.3+ scope (Camp Admin dashboard, Displaced dashboard, or
    any other page) is implemented here.

## 3 · Reused, already-built backend/data-access pieces

| Piece | Used for |
|---|---|
| `get_dashboard_statistics(p_camp_id uuid default null)` RPC (`assets/js/supabase/statistics.js`'s `getDashboardStatistics`) | `total_families`, `total_members`, `children_under_18`, `orphans`, `chronic`, `disability`, `aid_distributions`, `pending_requests` — global (`null`) for the headline stat row, per-camp for the camps list/chart. |
| `family_stats` view | Family size buckets (`members_count` per family). |
| `listCamps()` (`assets/js/supabase/camps.js`) | The camp list backing the "المخيمات" card list and `campComparisonBar`. |
| `listProfiles()` (`assets/js/supabase/profiles.js`) | Camp-admin counts, both platform-wide (`campAdmins` stat) and per camp (`adminsCount` in the camp breakdown) — `count: 'exact'` is independent of `pageSize`, so `{ role: 'camp_admin', campId, pageSize: 1 }` returns an accurate total without fetching rows. |
| RLS (`private.is_super_admin()`) | The only authorization boundary; every query below goes through the publishable-key client already in `core/supabase-client.js`. |

## 4 · What is genuinely missing

`get_dashboard_statistics` does not (and per constraint 4, must not) exist
in a shape that reads:

- **Gender split.** Not returned by the RPC or `family_stats` at all.
- **Distinct donor-organization count.** The RPC's `organizations` field is
  `count(*) from organizations` — every *registered* organization,
  regardless of whether it ever distributed anything. Constraint 11
  requires counting only organizations that appear in
  `aid_distributions`, which is a different query, not a reinterpretation
  of the existing field.
- **Monthly registration buckets.** Neither the RPC nor any view buckets
  `family_members.created_at` by month.
- **Family-size distribution buckets.** `family_stats` gives per-family
  `members_count`; nothing buckets it into the four UI ranges.
- **The Super-Admin-shaped composition itself** — the object literal
  `{ stats, byMonth, familySizes, camps }` that `dashboard.js`'s
  `collect()` currently builds from `select.*` (mock) calls, matching
  exactly what `superAdminView()`/`drawCharts()` already read.

These become `assets/js/supabase/dashboard.js`. Nothing else is missing —
every other figure comes directly from an existing RPC call or an existing
data-access function.

## 5 · Data mapping (mock shape → real source)

`dashboard.js`'s `collect(session)` builds, for a Super Admin,
`{ stats, byMonth, familySizes, camps }` (the `aidByType`/`recentAid`/
`requests`-list fields `collect()` also builds are Camp-Admin-only —
`superAdminView()`/`drawCharts()` never read them for this role, confirmed
by inspection of `assets/js/pages/dashboard.js`).

### `stats` (read by `superAdminView()`'s stat cards)

| Field | Mock source (`select.statistics`) | Real source |
|---|---|---|
| `camps` | `store.camps.count()` | `listCamps({}).length` |
| `campAdmins` | `store.users.count(role=camp_admin)` | `listProfiles({ role: 'camp_admin', pageSize: 1 }).total` |
| `displaced` | `people.length` | `getDashboardStatistics(null).total_members` |
| `families` | `familyRows.length` | `getDashboardStatistics(null).total_families` |
| `children` | `people.filter(isChild).length` | `getDashboardStatistics(null).children_under_18` |
| `orphans` | `people.filter(isOrphan).length` | `getDashboardStatistics(null).orphans` |
| `aid` | `aidRows.length` | `getDashboardStatistics(null).aid_distributions` |
| `donors` | `new Set(aidRows.map(organizationId)).size` | new: distinct `organization_id` over `aid_distributions` (constraint 11 — **not** the RPC's `organizations` field) |
| `disability` | `people.filter(disability).length` | `getDashboardStatistics(null).disability` |
| `chronic` | `people.filter(chronicDiseases).length` | `getDashboardStatistics(null).chronic` |
| `males` / `females` | `people.filter(gender=…).length` | new: gender count over `family_members` |
| `requests` | `pendingRequestCount(session)` | `getDashboardStatistics(null).pending_requests` |

(`documents` is part of the mock `statistics()` shape but is never read by
`superAdminView()`; not computed here — nothing in constraint 6 requires
supplying an unread field, and computing it would not be "genuinely
missing" work in service of anything on screen.)

### `camps` (read by `campRow()` list and `campComparisonBar()`)

Per camp, from `listCamps()` plus one `getDashboardStatistics(camp.id)`
call and one `listProfiles({ role: 'camp_admin', campId: camp.id,
pageSize: 1 })` call:

| Field | Source |
|---|---|
| `id`, `name`, `city`, `governorate`, `status` | `listCamps()` row, verbatim |
| `displacedCount` | `getDashboardStatistics(camp.id).total_members` |
| `familiesCount` | `getDashboardStatistics(camp.id).total_families` |
| `aidCount` | `getDashboardStatistics(camp.id).aid_distributions` |
| `adminsCount` | `listProfiles({ role:'camp_admin', campId: camp.id, pageSize:1 }).total` |
| `disabilityCount` | `getDashboardStatistics(camp.id).disability` |
| `childrenCount` | `getDashboardStatistics(camp.id).children_under_18` |
| `orphansCount` | `getDashboardStatistics(camp.id).orphans` |

`campRow()`/`campComparisonBar()` only read `id`, `name`, `city`, `status`,
`displacedCount`, `familiesCount` — the remaining fields are carried for
object-shape parity with mock `campBreakdown()` (constraint 6) and for
reuse by a later phase (constraint 14), at effectively no extra cost since
they come from the same RPC call already being made per camp.

### `byMonth` (read by `monthlyLine()`)

Mock `displacedByMonth(session, 8)` buckets `store.displaced` rows by
`createdAt` month. The real equivalent, per constraint 13, is the same
registration semantics applied to the real table that models a displaced
person: `family_members.created_at`, i.e. **when the person's record was
created**, exactly mirroring what `store.displaced`'s `createdAt` already
meant in the mock model — not `families.created_at` (household creation)
and not `profiles.created_at` (account creation, which only exists for the
subset of people with a login). No new bucketing rule is invented; the
same "last 8 months, one bucket per month, count of matching rows" logic
moves from filtering an in-memory array to filtering a Supabase query.

### `familySizes` (read by `familySizeBar()`)

Mock `familySizeDistribution(session)` counts `familyMembers(family.id)
.length` per family into 4 fixed buckets (1–2, 3–4, 5–6, 7+). The real
source for "members in this family" is exactly `family_stats
.members_count` — the view that already exists to answer this question
(its own comment: "the SQL equivalent of `selectors.familyFacts()`"). Same
4 buckets, same boundaries, applied to `members_count` instead of an
in-memory array length.

## 6 · `assets/js/supabase/dashboard.js` — new module

```js
// assets/js/supabase/dashboard.js
// Super Admin dashboard composition — reuses get_dashboard_statistics(),
// family_stats, listCamps() and listProfiles(). Adds only the handful of
// SELECT/composition queries those don't already answer (§4 of the spec).

import { requireClient } from '../core/supabase-client.js';
import { run } from './errors.js';
import { getDashboardStatistics } from './statistics.js';
import { listCamps } from './camps.js';
import { listProfiles } from './profiles.js';

const FAMILY_SIZE_BUCKETS = () => [
  { label: '1–2 أفراد', min: 1, max: 2, count: 0 },
  { label: '3–4 أفراد', min: 3, max: 4, count: 0 },
  { label: '5–6 أفراد', min: 5, max: 6, count: 0 },
  { label: '7 فأكثر', min: 7, max: Infinity, count: 0 },
];

/** Gender split over family_members, optionally scoped to one camp. */
export async function getGenderBreakdown(campId = null) { … }

/** Distinct organizations that appear in aid_distributions (constraint 11) —
 *  never all registered organizations. */
export async function getDonorOrganizationsCount(campId = null) { … }

/** Registrations per month for the last `months` months, by
 *  family_members.created_at (constraint 13). Same bucket shape as the
 *  mock's displacedByMonth(): { date, key, value }. */
export async function getMonthlyRegistrations(campId = null, months = 8) { … }

/** Family-size distribution via family_stats.members_count. */
export async function getFamilySizeDistribution(campId = null) { … }

/** Per-camp breakdown (§5's `camps` table), one get_dashboard_statistics +
 *  one listProfiles call per camp, run concurrently. */
async function buildCampBreakdown(camps) { … }

/** The full Super Admin dashboard composition: { stats, byMonth,
 *  familySizes, camps } — the exact shape collect() already builds for
 *  every other role, now from real data. */
export async function getSuperAdminDashboard() {
  const camps = await listCamps({});
  const [globalStats, campAdmins, gender, donors, byMonth, familySizes, campRows] =
    await Promise.all([
      getDashboardStatistics(null),
      listProfiles({ role: 'camp_admin', pageSize: 1 }),
      getGenderBreakdown(null),
      getDonorOrganizationsCount(null),
      getMonthlyRegistrations(null, 8),
      getFamilySizeDistribution(null),
      buildCampBreakdown(camps),
    ]);

  return {
    stats: { …§5 mapping… },
    byMonth,
    familySizes,
    camps: campRows,
  };
}
```

No new Supabase client, no `service_role`, no raw SQL — every function
above is a `client.from(table).select(...)` or a call to an already-
granted RPC, run through the existing `requireClient()`/`run()` plumbing
(`assets/js/supabase/errors.js`) so errors map to the same Arabic messages
and the same `errorState()`/retry path every other page already uses.

`getDonorOrganizationsCount`/`getGenderBreakdown` cannot use PostgREST's
`count: 'exact'` for a *distinct* count — PostgREST has no `COUNT(DISTINCT
…)` shorthand and constraint 4 forbids adding an RPC that would. They
`select()` the one relevant column (`organization_id` / `gender`) and
dedupe/count in JS. At this prototype's data volumes (seed data, a demo
deployment) this is the correct trade-off; a future phase with real
production volume would revisit it as a view, not as scope creep here.

## 7 · `assets/js/pages/dashboard.js` — the one changed function

Only `collect(session)` changes, and only its Super-Admin branch. Today:

```js
return {
  stats: select.statistics(session),
  byMonth: select.displacedByMonth(session),
  aidByType: select.aidByType(session),
  familySizes: select.familySizeDistribution(session),
  camps: select.campBreakdown(),
  requests: store.registrationRequests.list(…).filter(…).slice(0, 4),
  recentAid: select.searchAid({ scope: select.scopeFilter(session) }).slice(0, 5),
  notifications: select.notificationsFor(session.id).slice(0, 4),
};
```

`aidByType`, `requests`, `recentAid` are Camp-Admin-only fields (confirmed:
`superAdminView()` never reads them; `campAdminView()` does). `notifications`
is read by neither role's view (only the header badge, computed separately
inside `mountShell()`) — stays mock, unchanged, matching Phase 4.1's
explicit note that notification data migrates in a later phase.

`collect()` becomes:

```js
async function collect(session) {
  if (session.role === ROLES.DISPLACED) {
    return { …unchanged, byte-for-byte… };
  }

  if (session.role === ROLES.SUPER_ADMIN) {
    const real = await getSuperAdminDashboard();     // new import
    return {
      ...real,                                        // stats, byMonth, familySizes, camps
      notifications: select.notificationsFor(session.id).slice(0, 4),
    };
  }

  return { …camp-admin branch, unchanged, byte-for-byte… };
}
```

`init()`, `loadingView()`, `viewFor()`, `drawCharts()`,
`superAdminView()`, `campAdminView()`, `displacedView()`, every `*Row()`
helper — **zero changes**. `store.load(() => collect(session))` already
resolves whatever `collect()` returns, sync or async (`Promise` executor
`resolve(producer())` adopts a returned promise's eventual state), so
making `collect()` `async` requires no change to its caller either. A real
query failure (network, RLS denial, malformed response) throws inside
`getSuperAdminDashboard()`, which `store.load()`'s existing rejection path
already turns into `content.innerHTML = errorState({ retryAttrs: 'data-retry' })`
— the same error/retry UI every other page uses (constraint 15), with no
new code.

## 8 · Explicit non-goals

- Camp Admin dashboard (`campAdminView`, `aidByType`, `recentAid`,
  registration-request list) stays on mock data.
- Displaced-person dashboard (`displacedView`) stays on mock data.
- `camps.html`, `statistics.html`, `camp-admins.html` and every other page
  that also calls `select.statistics()`/`select.campBreakdown()` are out
  of scope — only `assets/js/pages/dashboard.js` is touched.
- Notifications and the header badge counts stay mock (Phase 4.1's
  existing note applies unchanged).
- No backend change of any kind (constraint 4).
- No realtime, no Excel export change, no visual/CSS change.

## 9 · Verification (constraint 16)

A new Playwright suite, matching the `phase4-auth-frontend.test.mjs`
pattern (inline static server + real Chromium — the frontend imports the
CDN-hosted `supabase-js`, which Node cannot resolve directly):

1. Log in as `super@camps.ps`, load the dashboard, read every stat-card
   value and the camps-list row values from the rendered DOM.
2. Independently query the *same* live database — via a second, plain
   `@supabase/supabase-js` client authenticated as the same user (not
   through `assets/js/supabase/dashboard.js`, so the test does not simply
   re-run the code under test) — for each of those figures, and assert
   DOM value === DB value.
3. Assert the network trace of the whole run contains no `service_role`
   key, no Cloudinary API secret, no DB password (constraint 17 — same
   assertion style as Phase 4.1's test #10).
4. If the seeded project happens to have zero rows for a given metric
   (not expected given the existing seed, but asserted rather than
   assumed), the corresponding stat card must render `0`/the existing
   `emptyState()`, never be skipped or throw (constraint 12).
