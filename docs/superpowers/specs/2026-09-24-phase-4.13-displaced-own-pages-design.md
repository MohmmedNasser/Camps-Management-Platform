# Phase 4.13 — Displaced Person Own Pages on Real Data — Design

## 1. Goal

Connect the displaced person's own pages — `family-details.html` ("أسرتي"), `profile.html`, `documents.html`, `aid.html`, `notifications.html` — to real Supabase data, using the identity chain Phase 4.12 established (`auth.uid() → profiles.family_member_id → family_members → families`). Never reintroduce `session.displacedId`. Preserve Camp Admin and Super Admin behavior exactly.

## 2. Current mock behavior (what's broken today)

Every one of these five pages still reads `core/store.js` (localStorage mock) for a real, authenticated displaced session:

- **family-details.js**: `session.role === ROLES.DISPLACED` branch resolves the family via `store.displaced.get(session.displacedId)`. `session.displacedId` does not exist on a real session (Phase 4.1's session shape is `{id, email, name, role, status, campId, campLabel, familyMemberId}`) — this branch has been silently dead for every real displaced account since Phase 4.1, always falling through to "family not found".
- **profile.js**: `store.users.get(session.id)` — a real session's `id` is a Supabase Auth UUID that never matches a seeded mock user id. `user` is `undefined`, and `view()` dereferences `user.name` — **this crashes `profile.html` for every real account of every role**, not just displaced. This is a pre-existing, previously-undiscovered bug blocking the whole page, found during this phase's investigation.
- **documents.js**: the displaced branch falls into the same code path as Super Admin (`select.searchDocuments()`, mock). The upload person-picker (`peopleFor()`) reads `store.displaced.get(session.displacedId)` — always empty for a real session, so upload was silently unreachable ("لا يوجد نازحون مرتبطون بحسابك").
- **aid.js**: the displaced branch reads `select.searchAid({ scope: select.scopeFilter(session) })`, and `scopeFilter()` resolves `store.displaced.get(session.displacedId)` — always `undefined`, so `scopeFilter` always returns a false predicate. A real displaced account's aid history has always rendered empty.
- **notifications.js**: `select.notificationsFor(session.id)` — mock, keyed by mock user ids. Always empty for a real session, of **any** role (this page has no role branch at all — see §7).

None of these crash except profile.js; the rest silently render empty states. All five are fixed by this phase.

## 3. Identity resolution (unchanged from Phase 4.12, reused everywhere)

```
auth.uid()  →  profiles.id (=auth.uid()) / profiles.family_member_id
            →  family_members.id  (getDisplacedPerson(familyMemberId))
            →  family_members.family_id  (person.familyId = family reference_code)
            →  families  (getFamilyByReferenceCode(referenceCode))
```

`session.familyMemberId` (from `core/auth.js`'s `getSession()`, sourced from `profiles.family_member_id`) is the only identity input. No page in this phase reads a URL parameter, localStorage, or `session.displacedId` to determine "whose data is this."

**New composition helper** — `getOwnFamily(session)` in `assets/js/supabase/families.js`:

```js
export async function getOwnFamily(session) {
  if (!session?.familyMemberId) return null;
  const person = await getDisplacedPerson(session.familyMemberId);
  if (!person || !person.familyId) return null;
  return getFamilyByReferenceCode(person.familyId);
}
```

This is the exact three-step resolution `getDisplacedDashboard()` (Phase 4.12, `assets/js/supabase/dashboard.js`) already does inline. It is extracted here because three *new* call sites in this phase need it (family-details.js, documents.js, aid.js); `dashboard.js` is deliberately **left untouched** — it already works, and touching Phase 4.12 code adds regression risk for no behavior change (identical logic, byte-for-byte). `profile.js` does not use this helper: it needs the `person` object on its own (for the read-only camp-file card) in addition to the family, so it calls `getDisplacedPerson()` directly and reuses `person.familyId` itself, avoiding a redundant second fetch of the person row `getOwnFamily()` would otherwise perform internally.

Every RLS policy exercised below independently re-derives the caller's own family/camp from `auth.uid()` (via `private.current_family_id()`/`private.current_camp_id()`, both `SECURITY DEFINER`, reading `profiles`). A page's own logic is UX convenience only — a hand-edited `?id=`/`?familyId=` on any of these five pages cannot widen what the RLS-scoped query returns, and `family-details.js`'s displaced branch (unlike its Camp Admin branch) never reads `params()` at all.

## 4. Page-by-page

### 4.1 `family-details.html` — "أسرتي"

`collect(session)` gains a third branch (Camp Admin's `collectReal(session, id)` is untouched; Super Admin's inline mock lookup is untouched):

```js
function collect(session) {
  const { id } = params();
  if (session.role === ROLES.CAMP_ADMIN) return collectReal(session, id);
  if (session.role === ROLES.DISPLACED) return collectOwn(session);
  // Super Admin — unchanged mock path
  ...
}

async function collectOwn(session) {
  const family = await getOwnFamily(session);
  if (!family) return { family: null };
  const [aidRows, docsResult] = await Promise.all([
    getFamilyAidHistory(family._dbId),
    listDocuments({ familyId: family._dbId }),
  ]);
  return {
    family: { ...family, campName: session.campLabel },
    aid: aidRows.map(mapAidHistoryRow),
    documents: docsResult.rows.map(mapDocumentRow),
  };
}
```

`getFamilyAidHistory()` and `listDocuments()` are already imported and already used by `collectReal()` for the Camp Admin branch; `mapAidHistoryRow`/`mapDocumentRow` are the same local mappers `collectReal()` already defines — `collectOwn()` is structurally the same function with the identity source swapped (own session instead of a URL reference code) and no cross-camp check (not needed: RLS + the identity chain already guarantee it's the caller's own family). `missingView()` already has a displaced-specific empty copy ("لم يتم ربط حسابك بأسرة بعد") that fires automatically when `collectOwn()` returns `{family: null}`.

Members table, aid list, documents list, head/tent-type definition list, and every stat card (`membersCount`, `childrenCount`, `orphansCount`) all come from the real `family_stats`/`family_member_facts` views already wired into `getFamilyByReferenceCode()` — no new fields invented.

### 4.2 `profile.html`

Fixes the pre-existing crash for all three roles (§2) as a prerequisite, then wires the displaced-specific "camp file" card to real data.

`collect(session)` becomes:

```js
async function collect(session) {
  const profile = await getOwnProfile();
  const person = profile.family_member_id ? await getDisplacedPerson(profile.family_member_id) : null;
  const family = person && person.familyId ? await getFamilyByReferenceCode(person.familyId) : null;
  const [aidRows, docsResult] = family
    ? await Promise.all([getFamilyAidHistory(family._dbId), listDocuments({ familyId: family._dbId })])
    : [[], { total: 0 }];
  return {
    user: { name: profile.full_name, email: session.email, phone: profile.phone || '', status: profile.status, createdAt: profile.created_at },
    person,
    family,
    aidCount: aidRows.length,
    documentCount: docsResult.total,
  };
}
```

`getOwnProfile()` (already exported, already used by `core/auth.js`) is called directly rather than widening `core/auth.js`'s session shape — `session` only carries what `PAGE_ACCESS`/`can()`/`inScope()` need; `phone`/`created_at` are profile.html-specific and stay local to this page, same convention `getDisplacedDashboard()` set (compose from existing exported functions, never touch the shared auth module for a single page's needs).

`user.email` comes from `session.email` (Supabase Auth's own field) — `profiles` has no `email` column (confirmed, same finding Phase 4.10 already documented for `get_camp_admin_accounts()`).

**Writes:**
- **Account form (name/phone):** `updateOwnProfile({ full_name, phone })` (already exists, already restricts to these two columns server-side per RLS + `profiles_guard_privileges` trigger). The email field is set `disabled aria-readonly="true"` with the hint `"لا يمكن تغيير البريد الإلكتروني من هنا."` — the exact convention `record-forms.js` already uses for a Camp Admin's email on edit (`6f01f65`). Changing a Supabase Auth email is a separate, more privileged Admin-API operation this phase does not add (mirrors Phase 4.11's explicit deferral of Camp-Admin-email changes). This fix applies to **all three roles** since the bug and the missing email-edit capability are identical for all three — see §7.
- **Password form:** new `assets/js/supabase/auth.js` function `updatePassword(newPassword)` → `client.auth.updateUser({ password })`. "Current password" is verified first by calling the existing `signIn(session.email, currentPassword)` — a wrong password throws a mapped `UNAUTHORIZED` error (`mapAuthError`'s existing "البريد الإلكتروني أو كلمة المرور غير صحيحة." message), which is shown on the `currentPassword` field exactly like the old mock flow did. Re-signing-in as the same account does not change `auth.uid()` (verified by the session-preservation test, §9).
- The old mock code also mirrored the new phone value onto `store.displaced.update(session.displacedId, {phone, email})` — dropped. `family_members.phone` (camp-file contact) and `profiles.phone` (account contact) are separate real fields; RLS gives a displaced caller no `family_members` UPDATE policy at all (confirmed live — `family_members_update_camp_admin` is the only UPDATE policy on that table), so this was never something the real backend could support, and the two phones are legitimately independent data.

### 4.3 `documents.html` — displaced branch

RLS confirms the exact shape of what's supported (`documents_insert_scoped`/`documents_select_scoped` include a `is_displaced() AND family_id = current_family_id()` clause; `documents_update_admin`/`documents_delete_admin` do **not** include displaced at all):

| Operation | RLS-authorized for displaced? |
|---|---|
| List / preview / download own family's documents | Yes (`documents_select_scoped`) |
| Upload a document for a member of own family | Yes (`documents_insert_scoped`) |
| Edit document metadata | No |
| Delete a document | No |

New `getFamilyDocuments(familyId)` in `assets/js/supabase/documents.js`, exact structural sibling of the existing `getCampDocuments(campId)` — same `DOCUMENT_SELECT`, same (currently module-private) `mapDocumentRow()`, filtered by `family_id` instead of `camp_id`:

```js
export async function getFamilyDocuments(familyId) {
  const client = requireClient();
  const rows = await run(
    client.from('documents').select(DOCUMENT_SELECT).eq('family_id', familyId).order('created_at', { ascending: false })
  );
  return rows.map(mapDocumentRow);
}
```

`init()` resolves `ownFamily = await getOwnFamily(session)` once (module-level state var, same pattern as the existing `campPeople` cache), used by both `collect()` (list) and `peopleFor()` (upload person-picker — real family members instead of the currently-broken mock lookup).

`collect()` gains a displaced branch identical in shape to the Camp Admin branch (`getFamilyDocuments()` + the existing, already-role-agnostic `select.matchesDocumentFilters()` predicate — no new filter logic needed, Phase 4.8 already built one shared predicate for real rows).

**Upload** gets its own dedicated branch (mirroring the Camp Admin branch exactly — no mock mirroring): today's generic fallback branch would, after the person-picker fix, call `cloudinary.uploadDocument()` with a real `family_member_id` (this already works end-to-end — the Edge Function's own RLS-scoped resolution handles it, see §5) but then also write an orphaned mock-store row keyed by a UUID `store.displaced.get()` can never resolve. The dedicated branch skips that: real upload, real row on next `load()`, no mock write.

**Delete** stays absent for displaced: `can('document:delete')` already excludes `ROLES.DISPLACED` (existing `PERMISSIONS` table, unchanged), so the trash icon never renders and the delete handler is already unreachable for this role — no code change needed there, confirmed by re-reading `resultsView()`'s `rowActions()` call.

**Preview/download** need no changes: `openPreview()`/`downloadDocument()` already work off the row shape alone (`row.dataUrl`/`row.backendId`/`row.mime`), which `getFamilyDocuments()`'s rows satisfy identically to `getCampDocuments()`'s.

### 4.4 `aid.html` — displaced branch (read-only)

`getFamilyAidHistory(familyId)` (existing, used by `family-details.js`/`dashboard.js`) returns the minimal `{id, typeLabels, organizationName, date}` shape — not enough for `aid.html`'s summary stats (`row.organizationId`, `row.types`, `row.familyIds`) or its search/filter (`select.matchesAidFilters()`, which reads the richer shape). Rather than reshape a function two other pages already depend on, a new sibling is added — exact structural counterpart to `getCampAidDistributions(campId)`, minus the camp filter:

```js
export async function getFamilyAidDistributions(familyDbId) {
  const client = requireClient();
  const rows = await run(
    client.from('aid_distributions').select(DISTRIBUTION_SELECT).order('distributed_on', { ascending: false })
  );
  return rows.map(mapAidDistributionRow);
}
```

No `.eq()` filter is needed at the top level: RLS (`aid_distributions_select_scoped`'s `is_displaced() AND private.family_receives_distribution(id)` clause) already returns exactly — and only — distributions the caller's family received. The nested `aid_distribution_families` embed is *also* RLS-scoped per row (`aid_distribution_families_select_scoped`'s displaced clause), so `mapAidDistributionRow()`'s `beneficiaries`/`familyDbIds`/`beneficiaryCount` naturally end up containing **only the caller's own family's link row**, never any other beneficiary of a shared distribution — a displaced viewer must not learn who else received the same aid (this is a stronger, more private reading of "N أسرة مستفيدة" than the mock ever gave; the mock leaked the full cross-family count). The `familyDbId` argument is kept for symmetry with `getCampAidDistributions(campId)` and as an explicit, redundant, UX-only narrowing (never a security boundary — the same convention `family-details.js`'s `collectReal()` already documents for its own `campId` check).

`aid.js`'s `collect()` gains a displaced branch reusing the **existing** `select.matchesAidFilters()` predicate unchanged (it already targets exactly this row shape — Phase 4.6 built it for `getCampAidDistributions()`'s rows, and `getFamilyAidDistributions()` returns the identical shape). The organization filter's option list is fetched once via the existing `listOrganizationOptions()` (already imported, already used by the Camp Admin branch — organizations are not camp-scoped, Phase 4.9). No familyId filter is offered to a displaced session (unchanged — `filterSpec()` already omits it when `isOwn`).

Create/edit/delete/export stay absent for displaced: `can('aid:create'/'aid:update'/'aid:delete')` already exclude `ROLES.DISPLACED`, and the export button is already gated on `!isOwn`. RLS independently confirms no INSERT/UPDATE/DELETE policy exists on `aid_distributions`/`aid_distribution_families` for a displaced caller — this was never reachable and stays that way.

### 4.5 `notifications.html`

**Schema** (live, confirmed): `notifications(id, recipient_id → profiles.id CASCADE, type, title, body, href, is_read, read_at, created_at)`.

**RLS** (confirmed, exhaustive — only two policies exist on this table):

| Policy | Effect |
|---|---|
| `notifications_select_own` (SELECT) | `recipient_id = auth.uid()` |
| `notifications_update_own` (UPDATE) | `recipient_id = auth.uid()`, same `with_check` |

**No INSERT policy and no DELETE policy exist.** A row's `is_read`/`read_at` are the only columns a browser session may change — enforced independently by the `notifications_guard_update` trigger (`private.guard_notification_update()`), which raises `42501` if `recipient_id`/`title`/`body`/`type`/`href`/`created_at` are touched, and auto-stamps `read_at` when `is_read` flips to `true`. This means:

- **Read/unread toggle and "mark all as read" are safe** — `is_read` is exactly the column the trigger permits.
- **Delete/dismiss is not supported** — there is no DELETE grant of any kind. The "حذف المقروءة" header button and each row's per-item delete button are **removed** from the real page rather than left calling a mutation that RLS would reject (or, worse, that silently "succeeds" with zero rows affected while the UI reports success). This is the one write this phase intentionally defers; §7 records it plainly for the final report.

`assets/js/supabase/notifications.js` already has `listNotifications()`, `markNotificationRead()`, `markAllNotificationsRead()`. One addition — `markNotificationUnread(id)`, the exact symmetric counterpart:

```js
export async function markNotificationUnread(id) {
  const client = requireClient();
  return run(client.from('notifications').update({ is_read: false, read_at: null }).eq('id', id).select().single());
}
```

`notifications.js` (page) maps DB rows to the shape its existing `row()`/`filterChips()` renderers already expect (`{id, type, title, text, createdAt, read, href}`) and calls `listNotifications({ pageSize: 100 })` (`MAX_PAGE_SIZE`, `assets/js/supabase/query.js` — no unpaginated variant exists for this table, and 100 is a generous ceiling for a personal notification list; the page has never offered pagination UI, mock or real, so this is not a regression). Every other piece of the page (filter chips, unread badge, relative/absolute timestamps, empty-state copy) is unchanged.

## 5. Cloudinary (documents upload/download for a displaced user)

No Edge Function changes. Re-verified against the live source (`supabase/functions/documents-upload/index.ts`, `-access`, `-delete`):

- **Upload** (`documents-upload`): authorization is the caller-scoped Supabase client itself — when the request carries `family_member_id`, the function does an RLS-scoped `select` against `family_members` before trusting it; for a displaced caller this only ever resolves a member of *their own* family (RLS), so a spoofed `family_member_id` belonging to another family returns nothing and the function answers a generic 403. The subsequent `documents` insert goes through the *same* caller-scoped client, so `documents_insert_scoped` re-checks independently (defense in depth, already documented in the function's own header comment). **Already fully correct for a displaced caller with no changes** — the only reason it looked unreachable was the frontend's broken person-picker (§2/§4.3).
- **Access** (`documents-access`, preview + download): authorization is `documents_select_scoped` alone — already includes displaced. No change needed.
- **Delete** (`documents-delete`): explicitly checks `profile.role === 'super_admin' || (profile.role === 'camp_admin' && ...)` — a displaced caller is **never** authorized, independent of RLS. Confirms §4.3's decision to leave delete unavailable to this role.

No Cloudinary secret is ever visible to the browser through any of this — confirmed by the existing repo-wide grep convention from Phase 4.11 (§9).

## 6. Dashboard unread-notifications stat

Phase 4.12 deliberately left `dashboard.js`'s `displacedView()` "الإشعارات غير المقروءة" stat on the mock `select.unreadNotificationCount(session.id)` specifically to avoid disagreeing with a still-mock `notifications.html`. Now that `notifications.html` is fully real and the exact matching real function (`unreadNotificationCount()`, already exported from `assets/js/supabase/notifications.js`, unused until now) exists:

**Decision: still deferred, `dashboard.js` is not touched in this phase.**

Rationale: the phase brief requires this be done only when it can be "explicitly documented and tested" as its own change, on top of everything else in scope. `dashboard.js` is flagged in this phase's own review-focus list as code that must not regress; the safest way to guarantee that is to not touch it. The change, when done, is a one-line swap (`select.unreadNotificationCount(session.id)` → a value added to `getDisplacedDashboard()`'s return, mirroring how `myAid`/`myDocuments` are already composed there) — left as the natural first task of a future micro-phase, not invented here.

Separately — **not** in scope for this phase regardless of the decision above — `ui/layout.js`'s `mountShell()` calls the same mock `notificationsFor(session.id)`/`unreadNotificationCount(session.id)` to render the header bell dropdown, on **every** page, for **all three roles**. This is a shared component outside the five pages this phase touches, and fixing it would require sourcing real data into a path Camp Admin and Super Admin also render — squarely the "broad application-wide rewrite" this phase must not do. It stays mock (silently empty for any real session, all roles, exactly as today) and is recorded as a known limitation in §7.

## 7. Deferred / known limitations (final report will restate these)

1. **Notification delete/dismiss** — no DELETE RLS policy exists on `notifications`. Both delete controls are removed from the real page.
2. **Document edit / delete for a displaced user** — `documents_update_admin`/`documents_delete_admin` and the `documents-delete` Edge Function both exclude the `displaced` role outright. Already correctly unreachable via `can('document:delete')`; not changed.
3. **Auth email change** (profile.html, all roles) — needs the Supabase Admin API, same deferral Phase 4.11 already made for Camp Admin. Field is read-only with an explanatory hint.
4. **Dashboard unread-notification stat** — stays on mock data this phase; see §6.
5. **Header bell dropdown** (`ui/layout.js`) — stays on mock data for all roles; shared component, out of this phase's page scope.
6. **`family_members` fields on the displaced person's own record** (birth date, chronic disease text, disability text, etc.) are **not** editable by the account itself — confirmed by RLS (`family_members_update_camp_admin` is the only UPDATE policy; no displaced-scoped UPDATE policy exists at all). `profile.html`'s existing "طلب تحديث البيانات" (message the Camp Admin) flow is the only path — already correct in the current UI, unchanged.

## 8. Scope discipline — what does NOT change

- Camp Admin behavior on all five pages: untouched (`collectReal()` branches, `getCampDocuments()`, `getCampAidDistributions()`, etc. — all pre-existing, none of their call sites are edited).
- Super Admin behavior: untouched on `family-details.html`, `documents.html`, `aid.html` (still mock, unchanged code paths). `notifications.html` and `profile.html`'s account section go real for Super Admin too, because — as documented in §4.2/§4.5 — neither page has, or ever had, role-differentiated *code* for that portion; the alternative (adding an artificial role branch just to keep Super Admin fake) would be worse engineering for no behavioral benefit, and both were equally broken for every real account before this phase.
- `dashboard.js`, `ui/layout.js`: untouched (§6).
- No RLS policy, trigger, RPC, or Edge Function is modified. No migration is applied. `PAGE_ACCESS` is unchanged (all three roles already listed for all five pages).

## 9. Testing strategy

Two new suites, following the exact structure Phase 4.12's isolation suite (`supabase/tests/phase4.12-displaced-dashboard-isolation.test.mjs`) and Phase 4.8's verification suite (`supabase/tests/phase4.8-documents-verification.test.mjs`) already established — same `.env` loader, same local static server, same `login()` Playwright helper, same service-role client for independent derivation:

- **`supabase/tests/phase4.13-displaced-isolation.test.mjs`** — cross-user isolation across all five pages, reusing the four seeded displaced accounts (`ahmad@camps.ps`, `yousef@camps.ps` — same camp, different family — `ibrahim@camps.ps`, `omar@camps.ps`) Phase 4.12 already verified. Direct RLS probes (family, family_members, aid, documents, notifications — each queried as one account trying to read/touch another's rows) plus URL-spoofing attempts (`family-details.html?id=<other-family-reference-code>` must still render the caller's own family) plus a rendered-page assertion (another account's name/family id/aid/document/notification content never appears). Also verifies Camp Admin/Super Admin sessions are unaffected and a session-preservation check (`auth.uid()` unchanged after visiting every page, including after a password-form current-password re-auth).
- **`supabase/tests/phase4.13-displaced-verification.test.mjs`** — DB-vs-UI: every rendered value on all five pages checked against an **independent** service-role query (never importing the same `assets/js/supabase/*.js` functions the page uses) — family reference/head/members/relationships/genders/ages/characteristics/aid/documents; profile name/gender/birth date/phone and a real permitted update (name+phone, cleaned up after) plus a real password change + revert (cleaned up); document count/names/categories/dates/filters/search and a real upload (+ preview/download where practical) cleaned up afterward via `documents-delete` called as the seed's Camp Admin (never as the displaced test account, matching §4.3's finding that displaced cannot delete); aid rows/types/organizations/dates/filters/search; notification rows/read-unread/timestamps/mark-read/mark-unread/mark-all-read, cleaned up by resetting state back to what was seeded rather than by deleting (no delete capability exists, §7 item 1).

Both suites assert zero test debris is left in `profiles`/`family_members`/`documents`/Cloudinary/`notifications` afterward (a `finally` block per fixture, mirroring every prior phase's convention).

`npm run test:all` (all pre-existing suites) must stay green; both new suites are added to it.
