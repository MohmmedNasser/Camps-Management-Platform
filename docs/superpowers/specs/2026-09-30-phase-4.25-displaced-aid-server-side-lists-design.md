# Phase 4.25 — Server-Side Displaced Persons & Aid Lists (design)

## 1. Current architecture (post-4.24), verified in the repo

`displaced.html` (`pages/displaced.js`): `collect(session)` → `getCampDisplacedPersons(campId)` / `getAllDisplacedPersons()`
(whole `family_members` scope via `fetchAll`, embedded family reference + camp name, mapped by `mapDisplacedRow`) →
optional `getFamilyIdsForAidFilter()` (a second whole-scope read of `aid_distributions`) → JS `matchesDisplacedFilters()`.
Pagination is `rows.slice()` of `PAGE_SIZE = 10`; the result count, the filter-sheet live preview (`onPreview`) and
the Excel export all call the same `collect()`. Order: `created_at asc, id asc`.

`aid.html` (`pages/aid.js`): `collect(session)` → `getCampAidDistributions` / `getAllAidDistributions` /
`getFamilyAidDistributions` (whole scope, nested embed of types + beneficiary families + head names) → JS
`matchesAidFilters()`. Same slicing pagination, same `collect()` for the four summary cards and the export.
Order: `distributed_on desc, id desc`. Displaced role reads its own family's history through the same page.

Live facts (project `qlvftlecwoqmvtagaykr`, before this phase): family_members 39 (1 without a birth date), aid_distributions 17.
A distribution's camp always equals each beneficiary family's camp — not just today's data: the `aid_distribution_families_same_camp`
trigger (`private.enforce_aid_family_camp`) rejects anything else, so the displaced list's aid-type/donor filter needs no camp condition. RLS on `family_members`, `families`,
`aid_distributions`, `aid_distribution_families`, `aid_distribution_types` is scoped (super admin all / camp admin own camp /
displaced own family) — unchanged by this phase.

## 2. Canonical age rule

> **age = completed years between the birth date and *today*, where *today* is the database's `current_date`.**
> Birthday boundary: a person is `n` on the day they turn `n`, and `n-1` the day before.

Implemented once in SQL as `public.age_in_years(p_birth_date date, p_on date)` (`extract(year from age(p_on, p_birth_date))`,
immutable) and `public.age_in_years(p_birth_date date)` = the two-argument form at `current_date` (behaviour-preserving
refactor of the existing function; its ACL is unchanged). Used by: `family_stats`, `family_member_facts`, `is_orphan()`,
`get_statistics_report()` (unchanged — it already called the one-argument form) and the new `list_displaced_persons()`.
The two-argument form makes the boundary testable without touching shared rows (`birthday yesterday / today / tomorrow`).

**Filtering uses the rule's inverse, not the rule, per row.** `age_in_years` carries `SET search_path`, which blocks SQL-function inlining and adds a GUC
save/restore per call; called per row (twice, via the delegation) it cost ~30 µs/row — 390 ms for an unfiltered page at 12,039 members (§10).
`public.age_cutoff_date(n, on) = on - n years` is computed **once per call** and the list compares `birth_date > cutoff`, which
is exactly `age_in_years(birth_date, on) < n`. That equivalence is *proved*, not assumed: `phase4.25-age-rule.test.mjs` sweeps > 600,000
(birth date × reference day × n∈{1,2,3,18}) combinations — every day of 26 years of birth dates against reference days around ordinary and leap
Februaries, the non-leap 2100, and a year end — offline in PGlite, with negative controls (a cutoff shifted by one day, and `n*365`) that the same
sweep must reject. `age_years` on the returned rows still comes from `age_in_years` itself, for the page's rows only.

*Known, documented divergence:* the browser's `ageFrom()` (detail pages, forms) uses the browser-local date, the database uses its
own `current_date` (UTC on Supabase). They differ only for the few hours around local midnight on a person's birthday. On
the two migrated lists this cannot show: the RPC returns `age_years` per row and `ageOf()` prefers it, so the row badges, the Excel
"العمر" column and the filters all use the one database value.

## 3. Decision: RPC returning `{ total, rows }`, not a view

Phase 4.24's pattern (view + PostgREST filters) works for families because a family has no free-text search across joined
tables. Here a view + PostgREST cannot express the required semantics **exactly**:

* search is a literal, case-insensitive *substring* over several columns (JS `includes`). `ilike` needs wildcard escaping and PostgREST
  rewrites `*`; 4.24 solved that by keeping the whole result client-side (`refineFamilyRows`) — impossible once rows are paginated on the server.
  In SQL `position(term in lower(col)) > 0` is the exact equivalent with no escaping questions.
* aid-type + donor must match the **same** distribution (existing semantics); a view cannot express that pairing.
* aid search spans arrays of beneficiaries (reference code / head name) and the type-label string.
* the aid page summary cards aggregate over the whole filtered set.

Therefore two narrowly scoped `SECURITY INVOKER` functions (`search_path = ''`, `EXECUTE` to `authenticated` only). They run as the caller,
so RLS is the only authorisation boundary; a supplied `p_camp_id` can only narrow. They add **no** `SECURITY DEFINER`, no RLS change, no index.

| Function | Roles | Returns |
|---|---|---|
| `list_displaced_persons(p_query, p_camp_id, p_gender, p_status, p_tent_type, p_age_under, p_is_child, p_is_orphan, p_has_chronic, p_is_pregnant, p_is_breastfeeding, p_aid_type, p_organization_id, p_limit, p_offset)` | super admin, camp admin (displaced refused `42501`, like `get_statistics_report`) | `{ total, rows[] }` — each row is `to_jsonb(family_members)` + `family.reference_code` + `camp.name` + `age_years`, i.e. exactly what `select('*, family:…, camp:…')` returned, so `mapDisplacedRow` is reused unchanged |
| `list_aid_distributions(p_query, p_type, p_organization_id, p_family_id, p_limit, p_offset)` | any signed-in role (RLS scopes: all / own camp / own family) | `{ total, summary{organizations,families,types}, rows[] }` — rows have the embed shape `DISTRIBUTION_SELECT` produced, so `mapAidDistributionRow` is reused unchanged |

Implementation notes: the filtering CTE carries only `id, created_at, family_id, camp_id`; the wide row (`to_jsonb`), the family reference, the camp name and
`age_years` are built for the requested page alone. The family reference is searched through an `exists` that only runs when a term was given.
`is_orphan()` is guarded by the cheap necessary condition (a deceased parent) so it is called only for rows where it could be true.

Pagination: `p_limit` clamped to `0..1000`, `p_offset ≥ 0`; **fixed total order** ending in the unique `id`
(`created_at, id` / `distributed_on desc, id desc`). `total` is computed for the same filtered set in the same statement, so it is
present even when the requested page is past the end (the client then clamps to the last page — the old `Math.min(page, pages)` behaviour).
`p_limit = 0` returns just the count — used by the filter sheet's live preview.

## 4. Filter-equivalence matrix — displaced

| Filter | Old JS (`matchesDisplacedFilters`) | SQL | Class |
|---|---|---|---|
| search | lowercase substring over `fullName`, `fullNameEn`, `nationalId`, `phone`, family reference code | `position(lower(trim(q)) in …)`; nationalId/phone not lowered (as JS) | **A** exact |
| camp (super admin) | `campId ===` | `m.camp_id = p_camp_id` | A |
| gender / status / tent type | `===` | `col::text = p` (unknown value → no rows, as JS) | A |
| age band `under_1/2/3` | `isUnder(person, max)`: `age !== null && age < max` | client maps band→`p_age_under` from `AGE_BANDS`; `age_in_years(dob) < p_age_under` (null age excluded) | **B** (uses §2 rule) |
| under 18 | `isChild` yes/no; `no` = not a child incl. unknown age | `coalesce(age < 18,false)` tri-state | B |
| orphan | `isOrphan`: parent deceased ∧ single ∧ under 18 | `public.is_orphan(m)` (the DB rule JS documents itself as mirroring) | B |
| chronic | `Boolean(chronicDiseases)` | `chronic_diseases <> ''` | A |
| pregnant / breastfeeding | female only; `yes`→flag, other→not flag | `gender='female' and coalesce(flag,false)` (tri-state) | A |
| aid type / donor | family reference ∈ set from one distribution matching **both** | `exists(adf ⋈ ad where family = m.family ∧ org ∧ exists(type))` | B (same-distribution pairing kept) |
| yes/no tri-state parsing | `''`→all, `'yes'`→fact, anything else→not fact | same | A |
| malformed uuid in `campId`/`organizationId` | matches nothing | client guard returns the empty page without calling the server | A |

Nothing displaced-related stays client-side except UI pagination *state* (page number in the URL) and rendering.

## 5. Filter-equivalence matrix — aid

| Filter | Old JS (`matchesAidFilters`) | SQL | Class |
|---|---|---|---|
| type | code ∈ `row.types` | `exists(type link ⋈ aid_types code = p)` | A |
| donor | `organizationId ===` | `organization_id = p` | A |
| family (UUID) | `familyDbIds.includes` (RLS-visible beneficiaries) | `exists(link family_id = p)` under RLS | A |
| search | lowercase substring over any beneficiary reference code, any head name (`'—'` when none), donor name, `typeLabels` (labels joined with `، `) | identical via `exists`/`position`, label string ordered by `sort_order, code` | A (type-label *order* was arbitrary embed order; now deterministic) |
| summary cards (count / donors / families / types) | `Set` sizes over all filtered rows | `summary` object computed over the same filtered set | A |
| camp / date | not a UI filter on this page | not added (YAGNI); camp scope = RLS | — |

## 6. Export

Existing documented behaviour: *exactly the filtered result set, empty file refused*. Kept: `collect()` becomes
"fetch all pages of the current filters in 1000-row batches" (`fetchAllPages`, deterministic order ⇒ no overlap/gap) and the page
uses `collect()` only for export; the table uses one page request. Limitation: the browser still materialises the *filtered* set to write
the `.xlsx` (client-side writer); page 1 and the count no longer do.

## 7. UI states

Loading skeleton, empty (filtered / unfiltered), error+retry, invalid filter (malformed uuid → empty), page beyond end (clamped to last page and
re-requested), filter change → page 1 (already in `onChange`). Delete refreshes the current query without touching filters.
`resultBar` shows `slice.length` of the DB `total`.

## 8. Security

* No `SECURITY DEFINER`; both functions `security invoker`, `search_path=''`, `revoke all … from public, anon`, `grant execute … to authenticated`.
* RLS unchanged; isolation tests call the RPCs with real sessions (camp admin ↔ other camp filter, displaced refused, anon denied, arbitrary ids).
* `service_role` is used only by tests (independent oracle and fixtures) — never in `assets/`.

## 9. Testing strategy

* `phase4.25-displaced-verification` — RPC vs legacy `matchesDisplacedFilters` over the unfiltered set for every filter + combos + search wildcards;
  pagination first/middle/last/beyond, count, order stability; `age_in_years` boundaries (pure function and via fixture rows, cleaned up in `finally`); export batches.
* `phase4.25-aid-verification` — same for aid, summary cards.
* `phase4.25-displaced-isolation`, `phase4.25-aid-isolation` — direct RPC calls per role/anon, spoofed camp/family/member ids, session preservation, no service key in browser code.
* `phase4.25-browser` — Playwright, six widths, both pages, roles; request payload proof that page 1 fetches one page.
* Performance: a rolled-back `DO` block seeds ≥ 5,000 members / aid rows, runs the RPC as an `authenticated` user and reports timings — nothing persists.

## 10. Measured performance (rolled-back seed, `authenticated` role, RLS active)

Seeded inside one transaction and rolled back by a final `RAISE` (verified afterwards: identical row counts and notification hash): 3,000 families,
12,000 members, 3,000 distributions on top of the live rows → **members = 12,039, aid_distributions = 3,017**.

| Call (super admin unless noted) | first version | final |
|---|---|---|
| displaced page 1, no filter | 703 ms | **16 ms** |
| displaced offset 5000 | 709 ms | 17 ms |
| displaced search (family reference / name fragment) | 35 / 698 ms | 22 / 23 ms |
| displaced `isChild=yes` / age band `<3` | 707 ms / – | 7 ms / 3 ms |
| displaced `isOrphan` yes / no | 195 ms / – | 148 / 157 ms |
| displaced aid type + donor | 387 ms | 25 ms |
| displaced count only | 661 ms | 8 ms |
| displaced export batch of 1000 rows | 746 ms | 93 ms |
| aid page 1 / search head-name fragment | 53 / 67 ms | 26 / 54 ms |
| camp admin displaced page 1 (3,019 rows in scope) | 190 ms | 9 ms |

Browser payload (real pages, seed data): page 1 = **one** `list_*` request, 1.5–11.9 KB response, and **no** read of `family_members` / `aid_distributions`.
These are database-side timings at ~12k rows; end-to-end latency, `max_connections` behaviour and > 100k-row behaviour were **not** tested.

## 11. Deviations from the first draft of this design

* `age_cutoff_date` (above) was added after the scale test showed the per-row `age_in_years` cost; not in the initial plan.
* The displaced RPC's first version built `to_jsonb` for every matching row (a 700 ms unfiltered page); fixed before the phase closed (migration `…000100`).
* The aid page no longer fetches the displaced account's family (`getOwnFamily`) — RLS already narrows the RPC to that family.
* The superseded whole-scope readers (`getCampDisplacedPersons`, `getAllAidDistributions`, …) and the JS `matchesXFilters` predicates stay: other pages (documents, phase 4.23 tests) use the readers and the predicates are the tests' legacy oracle.
