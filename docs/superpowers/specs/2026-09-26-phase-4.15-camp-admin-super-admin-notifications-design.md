# Phase 4.15 — Camp Admin & Super Admin Header Notifications — Design

## 1. Goal

Remove the last remaining mock notification path in the shared Header
(`ui/layout.js`'s `resolveNotifications()`): the bell badge and dropdown for
**Camp Admin** and **Super Admin**, still hard-coded to Phase 4.14's
`session.role !== ROLES.DISPLACED` mock branch. Displaced behavior
(Phase 4.14) and `notifications.html` (Phase 4.13, already real for all
three roles) must be unaffected.

## 2. Current mock behavior (confirmed by reading the code)

`assets/js/ui/layout.js`'s `resolveNotifications(session)`:
```js
async function resolveNotifications(session) {
  if (session.role !== ROLES.DISPLACED) {
    return { notifications: notificationsFor(session.id), unread: unreadNotificationCount(session.id) };
  }
  try {
    const [{ rows }, unread] = await Promise.all([
      listNotifications({ pageSize: 5 }),
      fetchUnreadNotificationCount(),
    ]);
    return { notifications: rows.map(mapNotificationRow), unread };
  } catch (error) {
    console.error(error);
    return { notifications: [], unread: 0 };
  }
}
```
For Camp Admin/Super Admin this calls `core/selectors.js`'s mock
`notificationsFor(userId)` / `unreadNotificationCount(userId)`
(`store.notifications.list/count(row => row.userId === userId, ...)`), which
never matches a real Supabase Auth UUID — the header bell has been silently
empty for every real Camp Admin/Super Admin account since Phase 4.1, exactly
as it was for Displaced before Phase 4.14.

`wireUserMenu()`'s mark-all-read handler has the identical role branch,
writing to the mock `store.notifications` collection for non-displaced
roles — a no-op against real data.

`assets/js/pages/dashboard.js`'s Camp Admin/Super Admin branches of
`collect()` still compute a dead `notifications: select.notificationsFor(session.id).slice(0, 4)`
field (confirmed unused by `campAdminView()`/`superAdminView()`, same as
Phase 4.14 found for the displaced branch before its own fix). **This is a
separate, out-of-scope surface** — the brief explicitly excludes "Dashboard
notification stat again" / "unrelated dashboard statistics." Left untouched.

`assets/js/pages/notifications.js` and `assets/js/supabase/notifications.js`
are unchanged since Phase 4.13/4.14 — already role-agnostic, already used by
all three roles on `notifications.html`.

## 3. Live backend investigation (executed against project `qlvftlecwoqmvtagaykr`, 2026-09-26)

### 3.1 Schema (`information_schema.columns`, live — unchanged from Phase 4.14)
```
notifications(id uuid pk, recipient_id uuid not null references profiles(id) on delete cascade,
  type notification_type not null default 'info', title text not null,
  body text not null default '', href text, is_read boolean not null default false,
  read_at timestamptz, created_at timestamptz not null default now())
```
Constraints: `notifications_read_consistent` (`is_read OR read_at IS NULL`),
`notifications_title_not_blank`. RLS enabled (`relrowsecurity = true`,
`relforcerowsecurity = false`).

### 3.2 RLS policies (`pg_policies`, live)

| Policy | cmd | roles | qual / with_check |
|---|---|---|---|
| `notifications_select_own` | SELECT | `{authenticated}` | `recipient_id = auth.uid()` |
| `notifications_update_own` | UPDATE | `{authenticated}` | `recipient_id = auth.uid()` (both) |

**Critically: neither policy is restricted to a specific application role.**
`roles = {authenticated}` means any signed-in Supabase Auth user — displaced,
camp_admin, or super_admin alike — is bound by the identical
`recipient_id = auth.uid()` predicate. There is no `camp_admin`/`super_admin`
carve-out, no camp-scoping, no "see all recipients in my camp" policy. No
INSERT or DELETE policy exists for any role. This directly answers the
brief's Step 3 ("verify role semantics"): **notifications are
user-specific via `recipient_id`, uniformly across all three roles** — never
camp-scoped, never system-wide, never role-conditional.

### 3.3 Guard trigger (`notifications_guard_update` → `private.guard_notification_update()`, live function body re-read)

```sql
if not private.is_browser_session() then
  return new;
end if;
if new.recipient_id is distinct from old.recipient_id or new.title ... or new.type ... or new.href ... or new.created_at ... then
  raise exception 'لا يمكن تعديل محتوى الإشعار' using errcode = '42501';
end if;
if new.is_read and new.read_at is null then new.read_at := now(); end if;
```
`private.is_browser_session()` = `session_user = 'authenticator' AND jwt role <> 'service_role'` —
**this check is about transport (browser/PostgREST vs. service-role/seed
script), not about `profiles.role`.** It fires identically for a
camp_admin's or super_admin's browser session as it does for a displaced
one: only `is_read`/derived `read_at` are writable from any browser,
regardless of app role. Re-verified live, not assumed from the Phase 4.14
doc.

### 3.5 `profiles` constraints relevant to test fixtures

- `profiles_single_super_admin_idx`: **unique partial index** —
  `CREATE UNIQUE INDEX ... ON profiles (role) WHERE role = 'super_admin'`.
  Domain rule 1 ("exactly one Super Admin") is enforced at the database
  level, not just the UI. **A second super_admin fixture account cannot be
  created — this phase's tests must reuse the single real `super@camps.ps`
  account (capture/restore its state) rather than fabricate a second one.**
- `profiles_camp_scope_valid`: `camp_admin` rows require a non-null
  `camp_id`; `super_admin` rows require a null `camp_id`. A disposable
  camp_admin fixture must be given a valid `camp_id` (any existing camp;
  notifications are not camp-scoped, so which camp is immaterial).
- `handle_new_user()` (the `auth.users` insert trigger) always inserts
  `role = 'displaced'`, `status = 'pending'` — user metadata is **never**
  read for role. A fixture with a non-displaced role requires a follow-up
  `service_role` `UPDATE profiles SET role=..., camp_id=..., status=...`
  after `auth.admin.createUser()`, exactly as `guard_profile_privileges()`
  anticipates (`is_browser_session()` is false for `service_role`, so this
  update bypasses the trigger's role-change guard legitimately, the same
  way the seed script does).

### 3.6 Existing data-access functions (`assets/js/supabase/notifications.js`) re-audited for role-safety

| Function | Role-dependent? | Notes |
|---|---|---|
| `listNotifications({page, pageSize})` | No | No `.eq(recipient_id, ...)` — relies entirely on `notifications_select_own` RLS. Safe for any role as-is. |
| `unreadNotificationCount()` | No | Same — RLS-derived count, no client-side filter beyond `is_read=false`. Safe for any role as-is. |
| `markNotificationRead(id)` / `markNotificationUnread(id)` | No | RLS-scoped `UPDATE ... eq('id', id)`; a foreign id resolves to zero affected rows under RLS, not an error and not another user's row. Already used identically by all three roles on `notifications.html`. |
| `markAllNotificationsRead()` | No | `UPDATE ... eq('recipient_id', await currentUserId()).eq('is_read', false)` — `currentUserId()` is `auth.uid()`, not read from any role-specific source. |
| `mapNotificationRow(item)` | No | Pure row-shape mapper, no identity/role logic at all. |

**Conclusion: every function in `assets/js/supabase/notifications.js` is
already role-agnostic and correct for Camp Admin and Super Admin, exactly as
it already is for Displaced and already proven by `notifications.html`
serving all three roles since Phase 4.13.** No new data-access function, no
new RPC, no schema/RLS/migration change is required.

## 4. Decision

### 4.1 Collapse `resolveNotifications()` to a single, role-agnostic path

Since RLS itself is the only real authorization boundary and it already
treats all three roles identically, the frontend's role branch in
`ui/layout.js` is now unnecessary special-casing, not a required safety
control. `resolveNotifications()` becomes:

```js
/** Real Supabase notification data for every role — RLS alone scopes both
 * reads and writes to the signed-in account (`recipient_id = auth.uid()`),
 * verified live for camp_admin/super_admin exactly as it already was for
 * displaced (Phase 4.14) and notifications.html (Phase 4.13). */
async function resolveNotifications() {
  try {
    const [{ rows }, unread] = await Promise.all([
      listNotifications({ pageSize: 5 }),
      unreadNotificationCount(),
    ]);
    return { notifications: rows.map(mapNotificationRow), unread };
  } catch (error) {
    console.error(error);
    return { notifications: [], unread: 0 };
  }
}
```

Failure fallback (empty list / zero badge, logged error) is unchanged from
Phase 4.14 — still never a thrown exception that would blank the shared
header for any role.

`mountShell()`'s call site changes from
`await resolveNotifications(session)` to `await resolveNotifications()` —
identity is `auth.uid()` alone; the function never needed `session` for
anything except the role check being removed.

### 4.2 Mark-all-read: same collapse

```js
const readAll = qs('[data-read-all]');
if (readAll) {
  on(readAll, 'click', async () => {
    try {
      await markAllNotificationsRead();
    } catch (error) {
      console.error(error);
    }
    window.location.reload();
  });
}
```
`markAllNotificationsRead()` is RLS-scoped (`notifications_update_own`,
`recipient_id = auth.uid()`) and trigger-guarded exactly as re-verified in
§3.3 — safe to call unconditionally for any role.

### 4.3 Dead imports removed, nothing else

After 4.1/4.2, `ui/layout.js` no longer calls the mock
`notificationsFor()`/`unreadNotificationCount()` (from `core/selectors.js`)
or `store.notifications` (from `core/store.js`) anywhere — both imports are
removed as dead code directly created by this fix (not a gratuitous,
unrelated cleanup). `core/selectors.js` itself is untouched: `dashboard.js`
still imports the whole module (`import * as select`) and still calls
`select.notificationsFor(session.id)` in its own (separately dead, out of
scope) Camp Admin/Super Admin branches — removing dead imports from
`layout.js` cannot and does not affect that unrelated file.

`ROLES` stays imported in `layout.js` (still used for the
`session.role === ROLES.SUPER_ADMIN` camp-label branch in `shellMarkup()`).

### 4.4 Why not a role-specific RPC/query instead

The brief's Step 5/"Important role decision rule" asks whether Camp
Admin/Super Admin need a *different* backend query. They do not: nothing
about "camp admin's own notifications" or "super admin's own notifications"
differs in shape from "displaced person's own notifications" — all three
are rows where `recipient_id = auth.uid()`. Introducing a role-specific
function here would be inventing a distinction the schema, RLS, and
existing seed data do not support, which the brief explicitly forbids
("Do not invent new notification functionality merely to make the Header
appear complete").

### 4.5 What stays deferred (unchanged, restated)

1. **Delete/dismiss** — no DELETE RLS policy on `notifications` for any
   role. Not implemented anywhere (unchanged from Phase 4.13/4.14).
2. **Insert** — no INSERT RLS policy for `authenticated`. Notifications are
   created server-side only (e.g. `approve_registration_request()`).
   Test fixtures use `service_role`, which bypasses RLS entirely and is the
   documented, already-used pattern (Phase 4.14's fixture account) — not a
   new backend capability.
3. **Per-item read/unread toggle and click-to-mark-read in the header
   dropdown** — never existed there (only on `notifications.html`), not
   added; adding either would be a UI behavior change beyond "replace the
   data source," which the brief forbids.
4. **`dashboard.js`'s dead `notifications: select.notificationsFor(...)`
   field** for Camp Admin/Super Admin — confirmed unused by both view
   functions, same as Phase 4.14 found for displaced. Out of scope
   ("Dashboard notification stat again"); left untouched.
5. A second super_admin account can never exist (§3.5) — not a limitation
   of this phase, a permanent domain invariant; noted so the test design
   doesn't fight it.

## 5. Identity model (unchanged, reused as-is)

`session.id` (`core/auth.js`'s `getSession()`, sourced from Supabase Auth's
`auth.uid()`) is real for **every** role — confirmed by reading
`getSession()`: `id: raw.user.id` is set identically regardless of
`profile.role`. Neither the header nor any notification query ever reads a
URL parameter, `localStorage` value, or DOM attribute to decide whose
notifications to fetch. RLS (`recipient_id = auth.uid()`) is the actual
boundary in both directions for all three roles — the (now-removed) role
check in the frontend never was the security boundary, only a
UX/scope-of-work switch.

## 7. Security boundaries (verified, not assumed)

1. **User isolation** — proven by RLS predicate alone
   (`recipient_id = auth.uid()`), independent of `profiles.role`. A Camp
   Admin cannot see another Camp Admin's rows; a Super Admin cannot see any
   other account's rows by any client-side maneuver, because the database
   never evaluates `profiles.role` when deciding row visibility for this
   table.
2. **Identity spoofing** — no notification query anywhere in the codebase
   accepts a recipient id from a URL parameter, `localStorage`, or a DOM
   attribute; every call resolves identity via the Supabase client's own
   session (`auth.uid()` server-side). Confirmed by reading every call site
   in `assets/js/supabase/notifications.js`, `assets/js/pages/notifications.js`,
   and (post-fix) `assets/js/ui/layout.js`.
3. **Write boundary** — `markAllNotificationsRead()`'s `UPDATE` carries its
   own `.eq('recipient_id', await currentUserId())` *and* is independently
   re-scoped by RLS's `with_check`; an UPDATE targeting another user's row
   id affects zero rows (Postgres RLS semantics: silently filtered, not a
   thrown error) — tests must assert on affected-row-count/unchanged state,
   not on a thrown exception.
4. **service_role** — test fixtures use `service_role` only inside the
   Node test process (`supabase/tests/*.mjs`, already the established
   pattern for every prior phase's fixtures); it never appears in any file
   under `assets/`.

## 8. Testing strategy

Two new suites, structurally identical to Phase 4.14's (`.env` loader,
local static file server, `login()` Playwright helper, service-role client
for independent derivation), covering Camp Admin and Super Admin with a
Displaced regression pass:

- **`supabase/tests/phase4.15-notifications-isolation.test.mjs`** —
  direct RLS probes: `admin@camps.ps` (Camp Admin A) and `super@camps.ps`
  each see/count only their own `recipient_id`; `nour@camps.ps` (Camp Admin
  B, real, zero rows) cannot read `admin@camps.ps`'s notification row by id
  and an UPDATE attempt against it affects zero rows; the same
  read/UPDATE-zero-rows probe run with `super@camps.ps` attempting another
  account's row; anonymous rejection; no notification-related URL
  parameter exists to spoof (asserted directly against `dashboard.html` and
  one other page per role); mark-all-read exercised once for real via the
  browser as `admin@camps.ps` and once as `super@camps.ps`, each wrapped in
  a full capture/restore of **both** the acting account's own state and a
  second account's state in a `finally` (the exact fix Phase 4.14 had to
  apply retroactively after its own test mutated seed data — this phase
  gets it right the first time); a Displaced regression subtest
  (`ahmad@camps.ps`) proving Phase 4.14 behavior is untouched; session
  preservation (`auth.uid()` unchanged after opening the header dropdown)
  for both new roles.
- **`supabase/tests/phase4.15-notifications-verification.test.mjs`** —
  DB-vs-UI: for `admin@camps.ps` and `super@camps.ps`, an independent
  service-role query (`count(*) where recipient_id = X and not is_read`,
  and the 5 most recent rows ordered by `created_at desc`) is compared
  against the rendered header badge and dropdown (titles, read/unread
  indicator, ordering) on `dashboard.html` **and** one other representative
  page per role (`families.html` for Camp Admin, `camps.html` for Super
  Admin) — proving the header is correct everywhere it mounts, not just on
  one page. `nour@camps.ps` (real, zero rows) verifies the real empty
  dropdown state renders correctly with no fabricated fallback. A
  disposable **camp_admin** fixture account (`service_role`
  `auth.admin.createUser` + a follow-up `profiles` UPDATE promoting it to
  `camp_admin` with a real `camp_id`, `status: 'active'`) gets 2 fixture
  notification rows inserted directly as `service_role` (bypassing the
  browser-only trigger guard per §3.3) to exercise the full mark-all-read
  cycle end to end: initial badge count → mark-all-read → immediate
  post-reload count 0 → an independent second reload confirming
  persistence → the DB itself shows 0 unread → another account's rows
  untouched. **No second super_admin fixture is created** (§3.5 — the
  unique partial index forbids it); Super Admin's mark-all-read is instead
  exercised in the isolation suite directly against the real
  `super@camps.ps` account with capture/restore. Cleanup in a `finally`:
  delete the fixture's notification rows, `profiles` row, and Auth user;
  responsive checks at the six standard breakpoints
  (`document.documentElement.scrollWidth > clientWidth (+1)`, the metric
  every prior phase — including 4.14 — already established as
  authoritative for this app's layout); a service-role-key
  browser-exposure check.

`npm run test:all` (`supabase/package.json`) is extended with both new
suites and must stay green end-to-end, including every pre-existing suite
back through Phase 2.
