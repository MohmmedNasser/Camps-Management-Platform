# Phase 4.12 — Displaced Person Dashboard on Real Data

**Date:** 2026-09-24
**Status:** Approved — proceeding to implementation

## 1 · Context

`assets/js/pages/dashboard.js` is one route with three role variants. Phase
4.2 (Super Admin) and Phase 4.3 (Camp Admin) already read real data. The
displaced-person variant (`displacedView()`) is the last one still mock —
the final item on CLAUDE.md's running Phase 4.x list.

Confirmed before writing any code, via direct inspection of
`assets/js/pages/dashboard.js`'s `collect()`:

```js
if (session.role === ROLES.DISPLACED) {
  return {
    person: session.displacedId ? store.displaced.get(session.displacedId) : null,
    family: session.displacedId ? select.familyOfPerson(session.displacedId) : null,
    myAid: session.displacedId ? select.aidForPerson(session.displacedId) : [],
    myDocuments: session.displacedId
      ? store.documents.list((row) => row.displacedId === session.displacedId)
      : [],
    notifications: select.notificationsFor(session.id).slice(0, 4),
  };
}
```

**This branch is not merely "mock" — it is dead for a real session.**
`session.displacedId` was a mock-era field. The real session object built by
`assets/js/core/auth.js`'s `getSession()` (Phase 4.1) has no such field; it
carries `familyMemberId` instead (`profile.family_member_id`). So today,
signed in as a real displaced account, `session.displacedId` is `undefined`
on every branch above, and the dashboard silently renders as if the account
had no person, no family, no aid and no documents — regardless of what is
actually in the database. This phase's job is exactly that swap: real
identity in, real rows out, same view code.

**What already exists, unused for this purpose.** No new backend
capability is needed. Four functions, already shipped and proven by earlier
phases, cover every real value this dashboard needs:

| Function | Phase | Already proven by |
|---|---|---|
| `getDisplacedPerson(id)` — `assets/js/supabase/family-members.js` | 4.5 | `displaced-details.js` (Camp Admin) |
| `getFamilyByReferenceCode(code)` — `assets/js/supabase/families.js` | 4.4 | `family-details.js` (Camp Admin + the displaced "أسرتي" URL shape) |
| `getFamilyAidHistory(familyId)` — `assets/js/supabase/aids.js` | 4.4 | `family-details.js`, `displaced-details.js` |
| `listDocuments({ familyId })` — `assets/js/supabase/documents.js` | 2 | `family-details.js` |

All four are RLS-scoped by the caller's own identity already (§2) — none of
them take a role/scope argument to get right or wrong.

## 2 · Live schema/RLS findings (verified via Supabase MCP against project `qlvftlecwoqmvtagaykr`)

**Identity chain, confirmed live and matching BACKEND.md §4/§6:**

```
auth.uid()
  -> profiles.id            (role='displaced', status='approved' required to reach this page — router guard, §3)
  -> profiles.family_member_id
       -> family_members.id  (== "the signed-in person's own file")
            -> family_members.family_id
                 -> families.id  (== "their family")
                      -> families.camp_id -> camps
```

`private.current_family_id()` (migration `20260816120100`) is this exact
join, `security definer`, used by every policy below. `profiles.family_member_id`
is set **only** by `approve_registration_request()`, in the same statement
that sets `status = 'approved'`:

```sql
update public.profiles
set status = 'approved', camp_id = v_request.camp_id, family_member_id = v_member_id
where id = v_request.user_id;
```

So for any session that can reach `dashboard.html` as `displaced`
(`private.is_displaced()` requires `status = 'approved'`, and
`core/router.js`'s `guard()` already redirects `pending`/`rejected` before
any page renders), `family_member_id` is guaranteed non-null by
construction. "Profile approved but no family" is not a reachable state
through the app — only through direct, out-of-band database manipulation —
and is still handled defensively (§6, Step 16 of the brief) rather than
assumed impossible.

**RLS matrix relevant to this dashboard (all confirmed live via
`pg_policies`, migration `20260816120200`):**

| Table | Displaced policy | Predicate |
|---|---|---|
| `profiles` | `profiles_select_own_or_admin` | `id = auth.uid()` |
| `family_members` | `family_members_select_scoped` | `is_displaced() AND family_id = current_family_id()` |
| `families` | `families_select_scoped` | `is_displaced() AND id = current_family_id()` |
| `aid_distributions` (+2 junctions) | `..._select_scoped` | `is_displaced() AND family_receives_distribution(id)` / `family_id = current_family_id()` |
| `documents` | `documents_select_scoped` | `is_displaced() AND family_id = current_family_id()` |
| `camps` | `camps_select_authenticated` | `status = 'active'` (any authenticated role) |
| `notifications` | `notifications_select_own` | `recipient_id = auth.uid()` |

Every row this dashboard needs is already reachable through the caller's
own RLS-scoped client with **zero new policies, zero schema change, zero
Edge Function**. This satisfies Step 7/22 of the brief directly: the
existing architecture provides the safe mechanism; nothing further is
required.

## 4 · `getDisplacedDashboard(session)`

Added to `assets/js/supabase/dashboard.js`, alongside the existing
`getSuperAdminDashboard()`/`getCampAdminDashboard()`, same file because it
is the third per-role dashboard composition, not a fourth new concern.

```js
import { getDisplacedPerson } from './family-members.js';
import { getFamilyByReferenceCode } from './families.js';
import { getFamilyAidHistory } from './aids.js';
import { listDocuments } from './documents.js';

/** Same mapping `family-details.js` already applies to this exact raw shape. */
function mapAidHistoryRow(row) {
  const d = row.distribution;
  const labels = (d.aid_distribution_types || []).map((t) => t.aid_type?.label_ar).filter(Boolean);
  return {
    id: d.id,
    typeLabels: labels.join('، '),
    organizationName: d.organization?.name || '—',
    date: d.distributed_on,
  };
}

const EMPTY = { person: null, family: null, myAid: [], myDocuments: [] };

/**
 * The full displaced-person dashboard composition: { person, family, myAid,
 * myDocuments } — the exact shape collect() already builds for this role
 * from mock selectors, now from real data, RLS-scoped to the caller's own
 * identity throughout (§2). session.familyMemberId is real Auth identity
 * (profiles.family_member_id, Phase 4.1) — never a URL/localStorage value.
 */
export async function getDisplacedDashboard(session) {
  if (!session.familyMemberId) return EMPTY; // not reachable via the app (§2); handled, not assumed impossible

  const person = await getDisplacedPerson(session.familyMemberId);
  if (!person || !person.familyId) return { ...EMPTY, person };

  const family = await getFamilyByReferenceCode(person.familyId);
  if (!family) return { ...EMPTY, person };

  const [aidRows, docsResult] = await Promise.all([
    getFamilyAidHistory(family._dbId),
    listDocuments({ familyId: family._dbId }),
  ]);

  return {
    person,
    family: { ...family, campName: session.campLabel },
    myAid: aidRows.map(mapAidHistoryRow),
    myDocuments: docsResult.rows,
  };
}
```

Notes:

- **Sequential, not parallel, between person -> family -> (aid, docs).**
  Each step's id comes from the previous step's result
  (`person.familyId` -> `family._dbId`), so it cannot be otherwise — same
  shape `family-details.js`'s `collectReal()` already uses. Aid and
  documents *are* fetched in parallel once the family is known, matching
  Step 12's "safe parallel loading where the schema allows it."
- **`getFamilyAidHistory`/`listDocuments` are both unpaginated, single-family
  queries** — the same convention `family-details.js` already relies on in
  production for the same two calls. A family's own aid/document count is
  small by construction (max seen live: 3); `listDocuments`'s
  `DEFAULT_PAGE_SIZE` (20) is not a real truncation risk here, exactly as
  it already isn't for `family-details.js` today.
- **No new mapping shape.** `getDisplacedPerson()` already returns the
  camelCase shape `profileCompletion()`/the "بياناتي" card read
  (`fullName`, `nationalId`, `phone`, `birthDate`, `gender`,
  `maritalStatus`, `campId`, `originGovernorate`, `displacementDate`,
  `workStatus`). `getFamilyByReferenceCode()` already returns `id`
  (=`reference_code`), `headName`, `membersCount` — everything
  `displacedView()`'s "أسرتي" card and stat cards read, plus `_dbId` (the
  UUID `getFamilyAidHistory`/`listDocuments` need — never surfaced to the
  UI). `campName` is the one field it doesn't carry (families don't embed
  a camp name); overridden from `session.campLabel`, same one-line pattern
  `family-details.js`'s own `collectReal()` already uses for the identical
  reason.
- **Three defensive returns, one used in practice.** `EMPTY` covers "no
  `family_member_id`" (architecturally unreachable, §2, still handled —
  Step 15); `{ ...EMPTY, person }` covers "person row deleted/RLS-hidden
  after login" and "person exists but its family embed is empty" (Step
  16) — both surface the existing `family ? … : emptyState(...)` branch
  `displacedView()` already has, unmodified.

## 6 · Loading, error and edge-case behavior

- **Loading state.** Unchanged — `init()`'s existing `content.innerHTML =
  loadingView()` (skeleton stats + two skeleton charts) renders before
  `collect()` resolves, exactly as today. Because `collect()` is `await`ed
  before any `innerHTML` write, there is no intermediate frame where mock
  or another user's data could appear (Step 13) — this was already true of
  the Super Admin/Camp Admin branches and required no dashboard.js change.
- **Error state.** Unchanged — the existing `try/catch` in `init()` already
  renders `errorState({ retryAttrs: 'data-retry' })` (fixed, generic Arabic
  copy, §"errorState" — no `error.message` interpolated anywhere in it) on
  any thrown error, and only `console.error(error)`s the real one. A
  thrown `DataAccessError` from any of the four new calls (network
  failure, unexpected RLS denial) is caught by this existing block
  unmodified.
- **Missing/invalid profile.** Already fully handled *before* `dashboard.js`
  runs: `core/router.js`'s `guard()` -> `core/auth.js`'s `getSession()`
  throws `ProfileError` for a missing or unrecognized-role profile, and
  `guard()` redirects to `auth-error.html`. No dashboard-level change
  needed or made (Step 15).
- **Wrong role / not authenticated.** Already fully handled by the same
  `guard()` — no session -> `login.html`; `pending`/`rejected` -> their
  status screen; role missing from `PAGE_ACCESS['dashboard.html']` (not
  reachable today — all three roles are listed) -> `404.html`. Step 9's
  "a user must not gain access simply by navigating to dashboard.html" is
  already true and independently re-verified in §7's role-authorization
  suite, not re-implemented.
- **Missing family** (§2: unreachable via the app, still coded
  defensively). `getDisplacedDashboard()` returns `family: null` in this
  case; `displacedView()`'s existing `family ? … : emptyState({ title:
  'لم يتم ربط حسابك بأسرة بعد', … })` branch renders unmodified. Verified
  live with one disposable fixture (§7, Test G) since seed data cannot
  express this state (§2's live-data table — every seeded account has a
  family).
- **Session preservation.** `getDisplacedDashboard()` performs reads only
  (`select` through `requireClient()`'s already-authenticated client) — no
  `auth.signIn`/`signUp`/`signOut` call anywhere in it or in anything it
  calls. Verified directly (§7, Test H).

## 8 · Follow-up (explicitly out of scope, documented not fixed)

lands on a page whose own displaced branch is **still mock**, and in three
of those five cases (`family-details.js`, `profile.js`, and — by the same

still-mock branch, not a regression this phase introduces" precedent

- `family-details.html` (via "أسرتي" / the family card's "تفاصيل الأسرة"
  link) — displaced branch still reads `store.displaced.get(session

  no read of mock or real state).
