## A. Aid-test notification cleanup

**Finding: already solved by Phase 4.26; no further change.** The audit's "≈3 leaked notifications per run" predates `supabase/tests/helpers/aid-fixture-cleanup.mjs`.

- Root cause (4.26): `private.notify_aid_beneficiary_family()` (an `AFTER INSERT` trigger on `aid_distribution_families`) writes notifications that carry no reference to their distribution, and deleting a distribution does not delete them. Notifications have no DELETE policy for any role by design, so only `service_role` can clean up.
- Existing strategy (kept): snapshot notification + distribution ids before the fixture; in `finally`, delete only rows whose id is new **and** that carry the trigger's exact title + href signature. Used by `phase4.6-aids-verification` and `phase4.25-aid-isolation`.
- Evidence this phase: baseline `notifications` = 13 (2 aid notifications), fingerprint `md5(id||is_read)` = `2f458527…`, 17 aid distributions. After running 12 suites that create aid (phase2, rls, 4.3-isolation, 4.4-isolation, 4.6 ×2, 4.12, 4.13, 4.24-stats, 4.25 ×3) the count, aid-notification count, fingerprint and distribution count were identical. The two existing aid notifications are seed content and were not touched.
- Failure path: cleanup runs in `finally` (4.26 `phase4.26-test-data-cleanup-verification` proves it removes only the fixture's rows and leaves unrelated ones).

## D. Password security

- **Before:** frontend `rules.password(6)` in five places; two Edge Functions `password.length < 6`; hosted Auth `minimum_password_length = 6` (`config.toml`, mirrors the hosted setting); leaked-password protection disabled (advisor `auth_leaked_password_protection`).
- **Changed (application level only):** one constant `PASSWORD_MIN_LENGTH = 8` in `assets/js/utils/validators.js`; `rules.password()` defaults to it; register, activate-family, reset-password, profile (change password) and the Camp-Admin create form use it, and their hints are generated from it. `activate-family-account` (anonymous, `verify_jwt:false`) and `admin-create-camp-admin` enforce the same 8 server-side and were redeployed (v2→v3 each) with `verify_jwt` unchanged.
- **Existing users:** untouched. Sign-in never checks length; demo accounts (`123456`) still log in (asserted).
- **Not changed, and why:** the hosted Auth minimum and leaked-password protection are project settings reachable only through the dashboard/Management API; this environment has no Management-API access token and the brief forbids inventing a workaround. Consequence, stated plainly: a caller using supabase-js directly (`signUp`, `updateUser`) can still set a 6–7 character password, because hosted Auth still enforces 6. The app UI, activation and camp-admin creation enforce 8; closing the gap needs the dashboard setting (Authentication → Policies → minimum length 8, leaked-password protection on if the plan supports it).
- Reset-password flow: uses the same validator, hosted Auth accepts ≥ 8 trivially; verified by unit assertions, not by a live email round-trip (no email is sent in this project's test setup).

## E. Sign-out scope

- `signOut()` used supabase-js's default, which is `global` (revokes every session of the account). This was implicit. Decision: **keep global, make it explicit.**
- Rationale: displaced families and camp staff share devices; a user signing out on a shared or lost phone must also lock out other sessions. The cost (signing out on one device signs out the others) is acceptable and was never reported as a defect.
- Change: `signOut({ scope: 'global' })` plus a doc comment. Behaviour identical. Tests prove global revokes a second session and local does not (contrast case). The test suites' own `signOut()` calls on shared demo accounts already rely on, and phase 4.8's comment documents, the global behaviour.

## F. Age rule

- **Authoritative rule (unchanged since 4.25, now documented as the single rule):** age = completed years as of the **UTC calendar day** = the database's `current_date` (DB timezone UTC) = `public.age_in_years(dob[, on])`. Statistics (`get_statistics_report`), list filters and `ageYears` already followed it. `p_tz` exists **only** to bucket *month* charts in the viewer's calendar; it does not influence age.
- **Found:** the browser fallback `utils/format.js` `ageFrom` (used when a row has no server `ageYears`: family/displaced detail members, the age chart fallback) and `formatAge` read **local** date parts. That made them disagree with the DB around midnight (UTC+2/+3 for the camps) and, because `new Date('YYYY-MM-DD')` is UTC midnight, could mis-read the birth *day* in zones west of UTC.
- **Fix:** both read UTC parts via one function; `ageFrom(birthDate, now = new Date())` (injectable for tests); `formatAge` delegates to it. A birth date after "today" is invalid input and out of scope (Postgres truncates its negative age toward zero, JS floors).
- **Tests:** birthday today/tomorrow/yesterday, leap-day baby, midnight edges, year end — every pair compared with the DB's `age_in_years(dob, on)` (live RPC); identical outputs under `TZ=Pacific/Kiritimati` (UTC+14), `Pacific/Pago_Pago` (UTC−11), `Asia/Gaza`, `America/Los_Angeles`, `UTC` in child processes; live `get_statistics_report().stats.children` equals an independent count from raw rows. Negative control: the old `ageFrom` fails these tests.
