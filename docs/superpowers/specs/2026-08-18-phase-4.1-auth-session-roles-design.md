# Phase 4.1 — Frontend Authentication, Session & Role-Based Access

**Date:** 2026-08-18
**Status:** Approved for implementation

## 1 · Context

Phases 1–3 built a complete Supabase backend (schema, RLS, RPCs, Cloudinary
document storage) and, unused so far, a full frontend data-access layer at
`assets/js/supabase/*.js` plus a client singleton at
`assets/js/core/supabase-client.js`. Nothing under `assets/js/pages/` or
`core/auth.js`/`core/router.js` imports any of it. The prototype still runs
entirely on `core/store.js` (localStorage) and a mock session in
`core/auth.js`.

`BACKEND.md` §14 already prescribes the order of work for connecting the
frontend, and item 1 is exactly this phase: *"`core/auth.js` → Supabase Auth
(`signInWithPassword`, `signUp`, `signOut`, `getUser`), keeping `can()` for
rendering decisions."*

Phase 4.1 wires **authentication, session management, role detection and
route/page protection** to the real backend. It does not touch dashboards,
families, displaced persons, aid, documents, messages, notifications, or
statistics — those stay on mock data until later Phase 4 stages.

Live project verified via Supabase MCP before writing this spec:
`qlvftlecwoqmvtagaykr`. Roles in the live `app_role` enum
(`super_admin`, `camp_admin`, `displaced`) are byte-for-byte identical to
`core/config.js`'s `ROLES`. Seeded accounts
(`admin@camps.ps` / `super@camps.ps` / `ahmad@camps.ps`, password `123456`)
already exist as real, email-confirmed Supabase Auth users — the same
emails the login page's demo buttons already use. Email confirmation is off
project-wide, so `signIn`/`signUp` return an active session immediately.

## 2 · Non-negotiable constraints (from approval)

1. No backend schema/RLS/RPC/business-logic changes unless strictly
   required for auth to function. (None are expected to be required.)
2. `switchRole()` is removed completely — no client-side role switching,
   anywhere, post-login.
3. Role, `campId`, `familyMemberId` and identity are never trusted from
   localStorage, URL parameters or other client-side state as an
   authorization source.
4. Role always comes from the authenticated user's real `profiles` row.
5. An authenticated user with no profile row or an unrecognized role fails
   closed: a typed `ProfileError` is thrown and the UI redirects to
   `auth-error.html`. No guessed/default role, ever.
6. Frontend guards are UX/navigation only. RLS and backend authorization
   remain the actual security boundary — restated in code comments at every
   guard point.
7. Mock dashboard data (`core/store.js`, `data/mock-data.js`) is untouched.
   Only authentication/session/role logic is replaced.
8. Existing UI/visual design is preserved; only the minimum necessary
   additions (a loading indicator, one new status page) are made.
9. No Phase 4.2+ functionality (families, displaced persons, aid,
   documents, messages, notifications, statistics, Excel export, realtime)
   is implemented.
10. A full verification pass (§8 below) runs for all three roles before
    this phase is reported done.

## 4 · `core/auth.js` — rewritten in place

Stays the single module for identity/session/permissions (existing
convention; no new `js/auth/` tree — satisfies "reuse existing structure").
Every session-touching export becomes `async`.

```js
export class ProfileError extends Error {
  constructor(reason) { // 'missing' | 'invalid_role'
    super('auth profile error: ' + reason);
    this.reason = reason;
  }
}

export async function getSession() {
  const raw = await supabaseAuth.getSession();       // assets/js/supabase/auth.js
  if (!raw) return null;                              // truly signed out

  const profile = await getOwnProfile();               // assets/js/supabase/profiles.js
  if (!profile) throw new ProfileError('missing');
  if (!Object.values(ROLES).includes(profile.role)) throw new ProfileError('invalid_role');

  const campLabel = profile.role === ROLES.SUPER_ADMIN
    ? 'كل المخيمات'
    : profile.camp_id
      ? await campLabelFor(profile.camp_id)  // listCamps()/getCamp(), small cache
      : '—';

  return {
    id: raw.user.id,
    email: raw.user.email,
    name: profile.full_name,
    role: profile.role,               // <- the ONLY source of role
    status: profile.status,
    campId: profile.camp_id,          // <- the ONLY source of camp scope
    campLabel,
    familyMemberId: profile.family_member_id,
  };
}

export async function isSignedIn() { return Boolean(await getSession()); }

export async function login(email, password) {
  try {
    await supabaseAuth.signIn(email, password);       // throws DataAccessError, Arabic message
  } catch (error) {
    return { ok: false, error: error.message };
  }
  return { ok: true, user: await getSession() };
}

export async function logout() {
  await supabaseAuth.signOut();
}

export async function register(data) {
  try {
    await supabaseAuth.signUp({
      email: data.email, password: data.password,
      fullName: data.fullName, phone: data.phone,
    });
  } catch (error) {
    return { ok: false, field: 'email', error: error.message };
  }
  try {
    await createRegistrationRequest({
      fullName: data.fullName, nationalId: data.nationalId,
      phone: data.phone, email: data.email, campId: data.campId,
    });
  } catch (error) {
    // Duplicate national ID (23505) etc. — already Arabic via mapError.
    return { ok: false, field: 'nationalId', error: error.message };
  }
  return { ok: true, user: await getSession() };
}

// can()/inScope(): unchanged logic, still pure & sync, still keyed on the
// same role strings. inScope()'s displacedId reference becomes familyMemberId.

export { ROLES, STATUS };
// switchRole() — REMOVED.
```

`campLabelFor()` is a tiny module-level memoized lookup (camp list rarely
changes within a session) built on `listCamps()`, not on mock `store.camps`.

Login error mapping (spec §6): `assets/js/supabase/errors.js`'s
`mapAuthError()` is extended (additive, same `DataAccessError` shape) to
distinguish, by GoTrue `error.code`/`error.message`:
- invalid credentials → "البريد الإلكتروني أو كلمة المرور غير صحيحة."
- email not confirmed → "يرجى تأكيد بريدك الإلكتروني أولاً."
- network/fetch failure → "تعذر الاتصال بالخادم. تحقق من اتصالك بالإنترنت."
- anything else → existing generic fallback ("حدث خطأ غير متوقع، حاول مرة أخرى.")

No raw Postgres/GoTrue error text ever reaches the UI; the original error is
still `console.error`-logged for development.

## 5 · `core/router.js`

`guard()` and `guestOnly()` become `async`:

```js
export async function guard({ page = currentPage() } = {}) {
  let session;
  try {
    session = await getSession();
  } catch (error) {
    if (error instanceof ProfileError) {
      console.error('[auth] profile error', error.reason);
      replace('auth-error.html');
      return null;
    }
    throw error;
  }
  if (!session) { replace('login.html'); return null; }
  // pending / rejected / PAGE_ACCESS checks: unchanged logic
  ...
}
```

`guestOnly()` gets the same `ProfileError` → `auth-error.html` handling
(an authenticated-but-broken profile must not fall through to the login
form as if it were a guest). `homeFor()`, `pageUrl()`, `currentPage()`,
`PAGE_ACCESS`, `NAVIGATION` are unchanged.

## 6 · `ui/layout.js`

- `mountShell()` becomes `async`, `await guard()`.
- `userMenu()`: the "تبديل الدور (للمراجعة فقط)" block and its `data-role`
  wiring in `wireUserMenu()` are deleted outright. Name/email/role/camp
  label continue to render from `session`, now sourced from the real
  profile instead of mock `store.users`.
- Logout handler becomes `await logout()` before redirecting (the handler
  is already an `async` arrow function, so this is a one-line change).

## 7 · Page modules (~28 files under `assets/js/pages/`)

Mechanical, one pattern each:

- Pages using `mountShell()`: `const shell = mountShell(...)` →
  `const shell = await mountShell(...)`. Top-level `await` is valid here —
  every page script is `type="module"`.
- Pages using `guestOnly()` (`login.js`, `register.js`,
  `forgot-password.js`): `if (!guestOnly())` → `if (!(await guestOnly()))`.
- Pages calling `getSession()`/`homeFor()` directly (`index.js`,
  `pending.js`, `rejected.js`, `404.js`): wrapped to `await` the now-async
  call; `ProfileError` bubbles the same way `guard()` handles it (redirect
  to `auth-error.html`).
- `register.js`: `campOptions()` switches from `store.camps.list(...)` to
  `listCamps({ status: 'active' })`. The client-side national-ID
  duplicate pre-check (`nationalIdTaken()`, which reads mock
  `store.displaced`) is removed; the database's unique constraint is
  authoritative and its `23505` already surfaces as a friendly Arabic
  duplicate message through `register()`'s error path (§4).

## 8 · New: `auth-error.html` / `assets/js/pages/auth-error.js`

A fifth status screen, same visual family as `pending.html` /
`rejected.html` / `404.html` (built on the existing `statusLayout()` /
`ui/auth-layout.js` primitives — no new visual components). Covers: no
profile row, unrecognized role, unexpected session-fetch failure. Copy:
"تعذر تحميل بيانات حسابك. يرجى التواصل مع إدارة النظام." One action:
logout (no retry loop, no guessed role, no partial content rendered).

## 9 · Loading state

`guard()`/`mountShell()` now do a real network round trip before any
protected page can render. To avoid a jarring blank flash (and per the
requirement that protected content never render before the check
resolves), each `pages/*.html` shell shows a small centered loading
indicator by default in `<body>`, replaced wholesale by `mountShell()`'s
`document.body.innerHTML = shellMarkup(...)` once the guard resolves. This
reuses existing spacing/color tokens — no new component, no visual
redesign.

## 10 · Explicit non-goals (restated)

- No changes to `core/store.js`, `data/mock-data.js`, or any page's
  dashboard/domain rendering logic.
- No changes to Supabase migrations, RLS policies, RPCs, or Edge
  Functions.
- Badge counts in the header (`unreadNotificationCount`,
  `pendingRequestCount`, `unreadMessageCount`) keep reading mock
  `core/store.js`. Once session `id`/`campId` are real UUIDs they will not
  match any mock row, so these will render as `0`/empty rather than error
  — expected, and left for the phase that connects notifications/messages.
- `documents.js`'s existing `backendAvailable()` branch (§16.6 of
  `BACKEND.md`) activates automatically once a real session exists; no
  code change to `documents.js` is needed or made in this phase.
