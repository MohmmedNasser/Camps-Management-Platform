# Phase 4.3 — Camp Admin Dashboard on Real Data

**Date:** 2026-08-18
**Status:** Approved for implementation

## 1 · Context

Phase 4.1 wired authentication/session/roles to real Supabase Auth. Phase 4.2
connected only the Super Admin dashboard variant
(`assets/js/pages/dashboard.js`'s `superAdminView`/`campComparisonBar` path)
to real data via the new `assets/js/supabase/dashboard.js`. Camp Admin and
Displaced-person dashboards were explicitly left on mock `core/store.js`
(Phase 4.2 spec §8, non-goal).

Phase 4.3 connects **only the Camp Admin dashboard**
(`assets/js/pages/dashboard.js`'s `campAdminView` path) to real data. The
Displaced-person dashboard, and every other page, stay on mock data.

Live project verified via Supabase MCP before writing this spec (same
project as Phase 4.1/4.2, `qlvftlecwoqmvtagaykr`):

- `get_dashboard_statistics(p_camp_id uuid default null)`'s exact body was
  pulled with `pg_get_functiondef`. It contains a strict authorization
  check specific to `camp_admin`:

  ```sql
  if private.is_camp_admin() and p_camp_id is distinct from private.current_camp_id() then
    raise exception 'لا تملك صلاحية الاطلاع على إحصائيات مخيم آخر' using errcode = '42501';
  end if;
  ```

  A camp_admin caller must pass `p_camp_id` equal to their own
  `current_camp_id()` — **including that passing `null` also throws** for
  them (only a Super Admin may pass `null` for a platform-wide read). This
  is the concrete backend mechanism behind objective item 10
  ("`getDashboardStatistics(session.campId)`, not `null`, for Camp Admin").
- RLS confirmed camp-scoped, via `private.current_camp_id()` /
  `private.is_camp_admin()`, on every table this phase reads:
  `family_members`, `families`, `aid_distributions` (own `camp_id` column),
  `aid_distribution_types`/`aid_distribution_families` (via
  `private.distribution_camp_id(distribution_id) = current_camp_id()`),
  `registration_requests` (own `camp_id` column). `family_stats` view also
  carries its own `camp_id` column.
- Seed data: 3 camps, 3 `camp_admin` profiles — `admin@camps.ps` (مخيم
  النور, **active**), `nour@camps.ps` (مخيم الرحمة, **active**),
  `raed@camps.ps` (مخيم الأمل, **disabled** — `is_camp_admin()` requires
  `status='active'`, so this account cannot authenticate for camp-scoped
  checks and is not used by this phase's tests).
- `mcp__supabase__get_advisors` (security): no ERROR-level findings, and no
  WARN touching any table/function this phase reads beyond the pre-existing,
  already-documented `SECURITY DEFINER`-reachable-by-`authenticated`
  warnings on unrelated RPCs (`create_aid_distribution`,
  `approve_registration_request`, etc.) and the unrelated
  leaked-password-protection toggle. Clean baseline.

## 2 · Non-negotiable constraints (from approval)

1. Reuse the existing `get_dashboard_statistics(p_camp_id)` RPC and the
   Phase 4.2 data-access functions (`getGenderBreakdown`,
   `getDonorOrganizationsCount`, `getMonthlyRegistrations`,
   `getFamilySizeDistribution`) — all already parameterized by `campId`,
   all already used with `campId = null` only by the Super Admin path.
2. Reuse `listRegistrationRequests()` and `listAidDistributions()`
   (`assets/js/supabase/registration-requests.js` /
   `assets/js/supabase/aids.js`) — built in Phase 2, never yet called from
   any page.
3. Add exactly one new data-access function,
   `getAidTypeBreakdown(campId)`, for the one genuinely missing metric
   (Phase 4.2 explicitly left `campAdminView`'s `aidTypeBar` on mock).
4. Add exactly one new composition function, `getCampAdminDashboard(campId)`,
   mirroring `getSuperAdminDashboard()`'s shape and structure.
5. No new/modified tables, columns, views, RPCs, functions, triggers, RLS
   policies, or migrations.
6. `campAdminView()`, `drawCharts()`, every `*Row()` helper, and all CSS —
   byte-for-byte unchanged. Only `collect()` in
   `assets/js/pages/dashboard.js` gains a new branch.
7. `superAdminView`/`getSuperAdminDashboard` and `displacedView` stay
   completely untouched.
8. `session.campId` (from the authenticated profile, via `core/auth.js`) is
   the only source of the Camp Admin's camp scope passed into the new
   functions — never a URL param, localStorage, or any other client state.
   RLS + the RPC's internal check remain the actual authorization boundary.
9. `Promise.all` for independent Camp Admin data requests.
10. No `service_role` or private secret in browser code; no RLS bypass.
11. No fetching another camp's protected data and filtering client-side —
    every query is issued with the camp scope already applied, and RLS
    independently enforces the same boundary.
12. Donor-organization count = distinct organizations that actually appear
    in the camp's `aid_distributions`, not all registered organizations
    (already the Phase 4.2 behavior of `getDonorOrganizationsCount`).
13. `aidByType` reflects real `aid_distribution_types`/`aid_types` rows,
    camp-scoped — never a fabricated category, never a mock-config label
    used as the source of truth.
14. No fabricated data; a genuinely empty camp renders the real zero /
    existing `emptyState()`.
15. Reuse existing loading/skeleton/error/empty-state mechanisms — no new
    UI pattern.
16. Automated cross-camp isolation tests using the two active seeded Camp
    Admin accounts (`admin@camps.ps`, `nour@camps.ps`), verifying actual
    Supabase responses, not just the UI.
17. Automated DB-vs-UI verification, independent of
    `assets/js/supabase/dashboard.js` (a second plain client), covering
    every Camp Admin statistic, the gender split and the aid-type chart.
18. Full existing test suite must stay green; baseline is 102/102 (per the
    task brief — `test:all`'s current chain, confirmed against
    `supabase/package.json`).
19. No push to the remote repository.
20. Work in an isolated worktree; merge to `main` only after tests and
    browser verification pass; remove the worktree/branch afterward.
21. No Phase 4.4+ scope (Camp Admin family list, displaced list, aid
    create/edit, detail pages, Displaced dashboard, etc.) is implemented
    here.
22. If a genuine backend blocker is found, STOP and report — do not
    silently work around it.

## 4 · What is genuinely missing

Only the aid-type breakdown. `aid_distribution_types` has no `camp_id`
column of its own; the camp scope is reached through its parent
`aid_distributions` row. No existing RPC/view answers "count of
distributions per aid type, for one camp" — `get_dashboard_statistics`
returns only a single `aid_distributions` total, not a per-type
breakdown.

Everything else in §3 already exists, already accepts `campId`, and is
already independently verified (Phase 2's `phase2-business-logic.test.mjs`
covers `aids.js`'s query shapes; Phase 4.2's own suite covers the
`dashboard.js` functions it added).

## 5 · Data mapping (mock shape → real source)

`dashboard.js`'s `collect(session)` builds, for a Camp Admin,
`{ stats, byMonth, aidByType, familySizes, requests, recentAid }` (confirmed
by reading `campAdminView()`/`drawCharts()`: `camps`/`campAdmins` are never
read for this role — those are Super-Admin-only fields).

### `stats` (read by `campAdminView()`'s stat cards)

| Field | Mock source (`select.statistics`) | Real source |
|---|---|---|
| `displaced` | `people.length` (camp-filtered) | `getDashboardStatistics(session.campId).total_members` |
| `families` | `familyRows.length` | `getDashboardStatistics(session.campId).total_families` |
| `children` | `people.filter(isChild).length` | `getDashboardStatistics(session.campId).children_under_18` |
| `orphans` | `people.filter(isOrphan).length` | `getDashboardStatistics(session.campId).orphans` |
| `requests` | `pendingRequestCount(session)` | `getDashboardStatistics(session.campId).pending_requests` |
| `aid` | `aidRows.length` | `getDashboardStatistics(session.campId).aid_distributions` |
| `donors` | `new Set(aidRows.map(organizationId)).size` (camp-filtered) | `getDonorOrganizationsCount(session.campId)` (existing) |
| `disability` | `people.filter(disability).length` | `getDashboardStatistics(session.campId).disability` |
| `chronic` | `people.filter(chronicDiseases).length` | `getDashboardStatistics(session.campId).chronic` |
| `males` / `females` | `people.filter(gender=…).length` | `getGenderBreakdown(session.campId)` (existing) |

### `byMonth` (read by `monthlyLine()`)

Mock `displacedByMonth(session, 8)`, camp-filtered. Real:
`getMonthlyRegistrations(session.campId, 8)` (existing, unchanged
semantics from Phase 4.2 — `family_members.created_at`).

### `aidByType` (read by `aidTypeBar()`) — new

Mock `aidByType(session)` counts, per configured aid type, how many
camp-scoped aid records include that type. Real equivalent:
`getAidTypeBreakdown(session.campId)` (new, §6) counts, per real
`aid_types` row, how many `aid_distribution_types` rows exist whose
parent `aid_distributions.camp_id` is the caller's camp — one row per
`(distribution, type)` pair, so this is exactly "how many distributions
in this camp include this type," matching the mock's semantics precisely.
Categories come from `listAidTypes({activeOnly: true})` (real, ordered by
`sort_order`), never from `core/config.js`'s `AID_TYPES` — labels are
`aid_types.label_ar`. Entries with zero count are filtered out, matching
the mock's `.filter((entry) => entry.count > 0)`.

### `familySizes` (read by `familySizeBar()`)

Real: `getFamilySizeDistribution(session.campId)` (existing, unchanged
from Phase 4.2 — `family_stats.members_count`, same 4 buckets).

### `requests` (read by `requestRow()` in the "طلبات تسجيل بانتظار المراجعة" list)

Mock: `store.registrationRequests.list(campId-filtered).filter(status===pending).slice(0,4)`,
consumed as `{ id, fullName, nationalId, createdAt, status }`. Real:
`listRegistrationRequests({ status: 'pending', campId: session.campId, pageSize: 4 }).rows`,
mapped locally (snake_case → camelCase: `full_name → fullName`,
`national_id → nationalId`, `created_at → createdAt`, `id`/`status`
verbatim) inside the new composition function — `registration-requests.js`
itself is not modified, since other, still-mock pages may depend on its
current return shape unchanged.

### `recentAid` (read by `aidRow()` in the "أحدث المساعدات" list)

Mock: `select.searchAid({scope}).slice(0,5)`, consumed as
`{ id, typeLabels, organizationName, beneficiaryCount, date }`. Real:
`listAidDistributions({ campId: session.campId }, { pageSize: 5, sortBy: 'distributed_on', sortDir: 'desc' }).rows`,
mapped locally: `typeLabels` = `aid_distribution_types[].aid_type.label_ar`
joined with `'، '` (same separator `selectors.js`'s existing mock mapping
uses), `organizationName` = `organization.name`, `beneficiaryCount` =
`aid_distribution_families.length`, `date` = `distributed_on`, `id`
verbatim. `aids.js` itself is not modified.

**Known, pre-existing, out-of-scope limitation (not a new regression):**
`requestRow()`/`aidRow()` link to `registration-request-details.html`/
`aid-details.html` with the now-real UUID. Those detail pages are Phase
4.4+ scope and still read mock `core/store.js`, so following the link
currently lands on a not-found/empty state. This mirrors the already-
accepted Phase 4.2 precedent (`campRow()` linking to still-mock
`camps.html` with a real camp UUID) and is not addressed here.

## 6 · `assets/js/supabase/dashboard.js` — additions

Two new exports, appended to the existing Phase 4.2 module — nothing
existing in this file changes.

```js
// New imports alongside the existing ones:
import { listAidTypes, listAidDistributions } from './aids.js';
import { listRegistrationRequests } from './registration-requests.js';

/**
 * Count of aid_distribution_types rows per real aid_types row, scoped to
 * one camp via the parent aid_distributions.camp_id — the one metric
 * Phase 4.2 left mock for the Camp Admin's aidTypeBar chart. Categories
 * and labels come from listAidTypes(), never core/config.js.
 */
export async function getAidTypeBreakdown(campId = null) {
  const client = requireClient();
  const types = await listAidTypes({ activeOnly: true });
  let query = client.from('aid_distribution_types').select('aid_type_id, aid_distributions!inner(camp_id)');
  if (campId) query = query.eq('aid_distributions.camp_id', campId);
  const rows = await run(query);

  const counts = new Map();
  rows.forEach((row) => counts.set(row.aid_type_id, (counts.get(row.aid_type_id) || 0) + 1));

  return types
    .map((type) => ({ value: type.code, label: type.label_ar, count: counts.get(type.id) || 0 }))
    .filter((entry) => entry.count > 0);
}

function mapRequestRow(row) {
  return { id: row.id, fullName: row.full_name, nationalId: row.national_id, createdAt: row.created_at, status: row.status };
}

function mapAidRow(row) {
  const labels = (row.aid_distribution_types || []).map((t) => t.aid_type?.label_ar).filter(Boolean);
  return {
    id: row.id,
    typeLabels: labels.join('، '),
    organizationName: row.organization?.name || '—',
    beneficiaryCount: (row.aid_distribution_families || []).length,
    date: row.distributed_on,
  };
}

/**
 * The full Camp Admin dashboard composition: { stats, byMonth, aidByType,
 * familySizes, requests, recentAid } — the exact shape collect() already
 * builds for this role from mock selectors, now from real data. campId
 * must be the authenticated Camp Admin's own session.campId — the RPC
 * itself rejects any other value for a camp_admin caller.
 */
export async function getCampAdminDashboard(campId) {
  const [globalStats, gender, donors, byMonth, familySizes, aidByType, requestsResult, aidResult] =
    await Promise.all([
      getDashboardStatistics(campId),
      getGenderBreakdown(campId),
      getDonorOrganizationsCount(campId),
      getMonthlyRegistrations(campId, 8),
      getFamilySizeDistribution(campId),
      getAidTypeBreakdown(campId),
      listRegistrationRequests({ status: 'pending', campId, pageSize: 4 }),
      listAidDistributions({ campId }, { pageSize: 5, sortBy: 'distributed_on', sortDir: 'desc' }),
    ]);

  return {
    stats: {
      displaced: Number(globalStats?.total_members) || 0,
      families: Number(globalStats?.total_families) || 0,
      children: Number(globalStats?.children_under_18) || 0,
      orphans: Number(globalStats?.orphans) || 0,
      aid: Number(globalStats?.aid_distributions) || 0,
      donors,
      disability: Number(globalStats?.disability) || 0,
      chronic: Number(globalStats?.chronic) || 0,
      males: gender.males,
      females: gender.females,
      requests: Number(globalStats?.pending_requests) || 0,
    },
    byMonth,
    aidByType,
    familySizes,
    requests: requestsResult.rows.map(mapRequestRow),
    recentAid: aidResult.rows.map(mapAidRow),
  };
}
```

No new Supabase client, no raw SQL, no `service_role` — every call is a
`client.from(table).select(...)` or an already-granted RPC, through the
existing `requireClient()`/`run()` plumbing, so errors map to the same
Arabic `DataAccessError` messages every other page already uses.

## 7 · `assets/js/pages/dashboard.js` — the one changed function

Only `collect(session)` changes, gaining a Camp Admin branch before the
(now-unreachable) old fallthrough. Today the Camp Admin path is the final
`return { stats: select.statistics(session), ... }` block. It becomes:

```js
async function collect(session) {
  if (session.role === ROLES.DISPLACED) {
    return { …unchanged, byte-for-byte… };
  }

  if (session.role === ROLES.SUPER_ADMIN) {
    const real = await getSuperAdminDashboard();
    return { ...real, notifications: select.notificationsFor(session.id).slice(0, 4) };
  }

  // Phase 4.3: Camp Admin reads real data.
  const real = await getCampAdminDashboard(session.campId);
  return {
    ...real,
    notifications: select.notificationsFor(session.id).slice(0, 4),
  };
}
```

`init()`, `loadingView()`, `viewFor()`, `drawCharts()`, `campAdminView()`,
`superAdminView()`, `displacedView()`, every `*Row()` helper — zero
changes. `store.load(() => collect(session))` already adopts a returned
promise regardless of whether `collect` is sync or async (unchanged since
Phase 4.2), so no caller-side change is needed.

### 9.2 · Cross-camp isolation suite (constraint 16)

New Playwright test, `supabase/tests/phase4.3-camp-isolation.test.mjs`:
signs in as `admin@camps.ps` and `nour@camps.ps` (both through a plain

### 9.3 · DB-vs-UI verification (constraint 17)
