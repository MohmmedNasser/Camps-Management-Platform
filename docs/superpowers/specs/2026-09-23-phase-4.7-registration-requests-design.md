# Phase 4.7 — Registration Requests & Approval Workflow on Real Data

**Date:** 2026-09-23
**Status:** Proposed — awaiting review

## 1 · Context

Phase 4.7 connects the Camp Admin's registration-request workflow —
`registration-requests.html` (list) and `registration-request-details.html`
(detail + decision) — to real Supabase data. Both pages are **already
Camp-Admin-only** in `PAGE_ACCESS` (`core/config.js:269-270`); Super Admin and
Displaced never open either page module. That removes the usual "preserve
the other roles' branch" complexity this series otherwise carries: like
`family-create.html`/`aid-create.html`/`aid-edit.html` before them, both
modules become **fully real, no mock branch**, not an `if (session.role ===
ROLES.CAMP_ADMIN)` split.

**Already real, from earlier phases — not rebuilt here:**

- `assets/js/supabase/registration-requests.js` (Phase 4.1) already has
  `listRegistrationRequests({status, campId, page, pageSize, sortBy,
  sortDir})`, `getRegistrationRequest(id)`, `createRegistrationRequest()`
  (used by `register.js`, the public sign-up form — already fully real),
  `approveRegistrationRequest(id, {gender, birthDate})` and
  `rejectRegistrationRequest(id, note)`, wrapping the `approve_registration_
  request`/`reject_registration_request` RPCs.
- The Camp Admin dashboard (Phase 4.3, `assets/js/supabase/dashboard.js`)
  already calls `listRegistrationRequests({status:'pending', campId,
  pageSize:4})` for its "طلبات التسجيل" stat card and recent-requests panel,
  and already links each row to `registration-request-details.html?id=`.
  That link currently 404s under real data because the details page is
  still mock — this phase fixes the dangling link as a side effect, not as
  separate scope.
- `assets/js/supabase/errors.js` already maps every error code the RPCs can
  raise (`P0002`→NOT_FOUND, `22023`→INVALID_STATE, `42501`→FORBIDDEN,
  `23505`→DUPLICATE) to Arabic messages. No new mapping is needed.

**What this phase actually builds:** `registration-requests.js` (list page)
and `registration-request-details.js` (detail + decide page) rewritten to
read/write real data, plus one small addition to the approve RPC's calling
contract (below) and a `getCampRegistrationRequests()` list function.

## 2 · Live schema/RLS/RPC findings (verified via Supabase MCP against project `qlvftlecwoqmvtagaykr`)

**Table `registration_requests`** — columns: `id, user_id (nullable), full_name,
national_id, phone, email, camp_id, status (request_status: pending/
approved/rejected), note, family_member_id (nullable), reviewed_by
(nullable), reviewed_at (nullable), created_at, updated_at`. No `gender` or
`birth_date` column — the applicant doesn't supply these at sign-up; the
approving admin does (see §4).

**RLS (3 policies, matches BACKEND.md §7 exactly):**

- `registration_requests_select_scoped` — super_admin all; camp_admin own
  camp; a user their own `user_id` row.
- `registration_requests_update_camp_admin` — camp_admin, own camp, on both
  `USING` and `WITH CHECK`. **This means a Camp Admin's raw Postgres
  privileges would let them `UPDATE` `status` directly** — but per the
  pasted brief and BACKEND.md §8 ("the registration workflow... would be
  half-applied if driven from the browser"), the app must still go through
  the RPCs, which are the only path that also creates the family/member,
  activates the profile and sends the notification atomically. The plan
  never issues a raw `.update()` on `registration_requests` from a page.
- `registration_requests_insert_self` — any authenticated user, own
  `user_id`, and only while `status='pending', reviewed_by IS NULL,
  reviewed_at IS NULL, family_member_id IS NULL`. Unrelated to this phase
  (already used by `register.js`), but note for tests: **the policy places
  no restriction on `camp_id`** — any signed-in user can create a request
  for any camp. Test fixtures below insert via a service-role client
  instead, to avoid attaching test rows to a real demo account.
- **No `DELETE` policy exists on `registration_requests` for any
  `authenticated` role**, not even `camp_admin`. Confirmed by listing all
  policies on the table (3 total, none `DELETE`). Test cleanup that inserts
  a throwaway request **must** use a service-role client — the app itself
  never needs to delete a request, so this doesn't affect the UI, only the
  test harness (§8).

**Indexes:** `(camp_id)`, `(status)`, `(camp_id, status)` composite,
`(created_at DESC)`, plus the two the workflow relies on implicitly
(`user_id`, `reviewed_by`). No index on `full_name`/`national_id`/`phone`/
`email` beyond the partial-unique on `national_id` — text search stays
client-side (§5), matching the size of data this table will ever hold (one
row per applicant, not a high-volume table).

**Constraints worth knowing:**
- `registration_requests_open_national_id_key` — unique `national_id` among
  non-rejected requests (re-submission after rejection is allowed).
- `registration_requests_review_complete` — `status='pending'` iff
  `reviewed_at`/`reviewed_by` are both null; enforced by the RPCs already,
  never by application code.
- `registration_requests_approved_has_member` — `status <> 'approved' OR
  family_member_id IS NOT NULL`. **Live-schema finding, out of this
  phase's scope to fix:** because `family_members.family_id` cascades and
  `registration_requests.family_member_id` is `ON DELETE SET NULL`,
  deleting a family that originated from an *approved* request would try to
  null that column and hit this `CHECK`, aborting the delete with a raw
  constraint error. This is a pre-existing gap in `families.js`'s
  `deleteFamily()` (Phase 4.4), unrelated to anything this phase changes.
  Noted in §9 as follow-up work, not fixed here. The test harness (§8)
  avoids ever triggering it by deleting its own fixture's
  `registration_requests` row before its fixture family.

**RPC source, read live via `pg_get_functiondef`:**

- `approve_registration_request(p_request_id uuid, p_gender gender default
  'male', p_birth_date date default null)` — re-checks `status='pending'`
  (raises `22023` otherwise) and camp match against `private.is_camp_admin()
  + current_camp_id()` (raises `42501` otherwise) itself; the UI-side check
  is advisory. Creates the family, creates the head `family_member` with the
  **passed-in `p_gender`/`p_birth_date`** (not derived from the request —
  the request has no such columns), sets `families.head_member_id`,
  updates the request to `approved`, and — only `if v_request.user_id is not
  null` — activates the linked `profiles` row and inserts a notification.
  **All five of the seeded demo requests have `user_id = null`**, so that
  branch is untestable against seed data alone without inserting a fixture
  that sets `user_id`; §8's isolation tests don't depend on it, and the
  behavior itself needs no new code — it is entirely inside the RPC.
- `reject_registration_request(p_request_id uuid, p_note text default '')`
  — same pending/camp checks, sets `status='rejected'`, `note`, and (again
  only if `user_id is not null`) sets the profile to `rejected` with
  `rejection_reason` and notifies.
- Both are `SECURITY DEFINER`, `search_path=''`, confirmed granted to
  `authenticated` and denied to `anon` (BACKEND.md §7 function-privileges
  audit).

**Consequence for the UI — the approve action needs a form, not just a
confirm dialog.** `family_members.gender` is `NOT NULL`; the mock's
`select.approveRequest()` silently hardcoded `gender: 'male'` and never
collected a birth date. The real RPC takes both as explicit parameters and
the rest of the app always requires them (`record-forms.js`:
`rules.required('الجنس')`, `rules.required('تاريخ الميلاد')` on every other
place a person is created). The real approve flow must collect gender
(required select, `GENDERS` from `config.js`) and birth date (required date
input, must not be in the future) before calling the RPC — reusing
`formDialog()` (already used by the existing reject flow) instead of
`confirmDialog()`.

**Cross-camp duplicate detection is necessarily best-effort in the UI.**
The mock's `store.displaced.find(person => person.nationalId ===
raw.nationalId)` searches every camp because the mock store is
un-scoped. Real `family_members` RLS only lets a Camp Admin read their own
camp's rows (`family_members_select_scoped`), so a pre-approval client-side
duplicate check can only ever surface a duplicate **within the admin's own
camp** — it cannot see a duplicate registered in another camp. That's fine:
the authoritative guard is the database's global unique index on
`family_members.national_id`; `approve_registration_request`'s `INSERT`
will raise `23505` for a cross-camp duplicate, which `mapError()` already
turns into "هذا السجل موجود مسبقاً" for the approve button's catch handler.
The detail page's pre-approval alert becomes "own-camp duplicate found" vs.
"no duplicate found in your camp" (not "no duplicate anywhere"), and the
approve handler must be ready for the RPC itself to reject with `DUPLICATE`
even when the pre-check found nothing.

**The "linked account" card cannot be populated before approval, so it's
repointed at the new person record instead.** The sign-up trigger
(`private.handle_new_user`) inserts a `profiles` row with `camp_id = null`;
`approve_registration_request` is the only thing that ever sets it (to the
request's `camp_id`). `profiles` RLS (`profiles_select_own_or_admin`) only
lets a Camp Admin read profiles in their **own** camp — so for a `pending`
or `rejected` request, the linked profile is invisible to the reviewing
admin regardless of whether one exists (`camp_id` is still null), and even
post-approval a profile lookup would need the extra, request-shape-specific
condition `user_id is not null` (all 5 seeded requests have `user_id:
null`, so this branch would rarely render anything). Simpler and always
correct within its own precondition: once `status === 'approved'`, the
request's `family_member_id` points at a `family_members` row that's
unconditionally readable (same-camp, `family_members_select_scoped`,
already established since Phase 4.5's `getFamilyMember()`). The card is
repurposed to show that new record (name, "مفعّل") instead of the
`profiles` row; for `pending`/`rejected` it keeps the existing "لا يوجد
حساب مرتبط ظاهر من هنا" placeholder, reworded slightly from "بهذا الطلب" to
make clear this is a visibility limit, not a claim that no account exists.

**Documents are out of scope.** `documents.registration_request_id` exists
as a column, but nothing in the current app — not `register.js`, not any
page — ever writes to it. No page offers a document upload during sign-up.
Adding one would be a new feature, not a real-data connection of an
existing one; left alone per "do not redesign."

## 4 · List page (`registration-requests.js`)

Same UI shape as today (toolbar search + status chips + table + pagination),
same `PAGE_SIZE = 10` client-side pagination `aid.js`/`families.js` already
use for their real branch. Swap the data source only:

```js
async function collect(session) {
  const rows = await getCampRegistrationRequests(session.campId);
  return rows.filter((row) =>
    select.matchesRegistrationRequestFilters(row, { query: state.q, status: state.status })
  );
}
```

`getCampRegistrationRequests(campId)` returns rows already shaped like the
mock's `requestRow()` output (`fullName`, `nationalId`, `phone`, `email`,
`campId`, `campName`, `status`, `createdAt`, `reviewedAt`, `reviewerName`,
`note`, `displacedId`) so `resultsView()`'s column `cell` functions need no
change. `campName` is always the session's own `campLabel` (every row is
already scoped to one camp); `reviewerName` needs a `profiles` join on
`reviewed_by` (readable — `reviewed_by` is set to the reviewing Camp Admin's
own id, and `profiles_select_own_or_admin` lets a camp_admin read their own
row and any other profile whose `camp_id` matches — but the *reviewer's*
profile has `camp_id` = their own camp, i.e. the same camp, so this
resolves for every request this Camp Admin could ever see).

Status chip counts: `requestCountsByStatus(campId)` becomes a `reduce` over
the same `getCampRegistrationRequests()` result already fetched for the
list — no second query, unlike the mock which ran two independent
`store.list()` calls. One fetch backs both the table and the chip counts,
matching the "single query behind the list, its count and the export"
convention CLAUDE.md states for `getFilteredDisplaced`/`getFilteredFamilies`
(no export exists here, but the "one query, never filtered twice" principle
still applies).

Approve/reject from the list row actions call the same two handlers the
detail page uses (§4 below); both are extracted as small `async function
approveFlow(session, request)` / already-existing `rejectFlow` so the two
page modules don't duplicate the RPC-calling logic — `registration-
requests.js` imports both from... itself is fine (no third module needed);
the detail page keeps its own copy today already (duplicated, not shared,
in the current mock code) and the real rewrite keeps that same duplication
rather than introducing a new shared module for two ~20-line functions,
consistent with "don't add abstractions beyond what the task requires."

## 5 · Detail page (`registration-request-details.js`)

```js
async function collect(session, id) {
  const raw = await getRegistrationRequest(id); // throws NOT_FOUND (P0002 doesn't apply here — .single() throws PGRST116) if absent
  // RLS already hides another camp's row; getRegistrationRequest uses
  // .single(), which throws on zero rows — caught by init()'s try/catch,
  // same as any other error, and mapped to errorState(), not emptyState().
  ...
}
```

Wait — `getRegistrationRequest` currently uses `.single()` (throws
`PGRST116` on no match, mapped to `NOT_FOUND` — a thrown `DataAccessError`,
not a clean `null`). Every other real "get one by id" function in this
codebase (`getFamilyByReferenceCode`, `getDisplacedPerson`,
`getAidDistribution`) uses `.maybeSingle()` and returns `null`, so the page
can render its existing `emptyState()` "الطلب غير موجود" panel instead of
falling into the generic `errorState()`. This phase changes
`getRegistrationRequest` from `.single()` to `.maybeSingle()` (still in
`registration-requests.js`, a one-line change) so
`registration-request-details.js` can follow the same `if (!data.request)`
→ `emptyState()` branch its mock version already has, rather than
special-casing this one caller. This is the only signature-preserving
behavior change to an existing exported function in this phase.

```js
async function collect(session, id) {
  const request = await getRegistrationRequest(id, session.campLabel);
  if (!request) return { request: null };

  const duplicate = await findOwnCampDuplicate(request.nationalId, session.campId);
  // Only readable once approved — see §2's profiles-visibility note.
  const account =
    request.status === STATUS.APPROVED && request.displacedId
      ? await getFamilyMember(request.displacedId) // existing Phase 4.5 function, family-members.js
      : null;

  return { request, duplicate, account };
}
```

`findOwnCampDuplicate(nationalId, requestId)` — new, small, lives in
`registration-requests.js` next to the function that needs it:

```js
export async function findOwnCampDuplicate(nationalId, campId) {
  const client = requireClient();
  const row = await run(
    client.from('family_members').select('id, full_name').eq('national_id', nationalId).eq('camp_id', campId).maybeSingle()
  );
  return row; // RLS already scopes this to the caller's own camp; campId kept explicit by convention
}
```

Approve handler (list and detail both), replacing `confirmDialog` with a
`formDialog` that collects gender + birth date:

```js
async function approveFlow(session, request) {
  const values = await formDialog({
    title: 'قبول طلب التسجيل',
    description: `سيتم إنشاء سجل نازح وأسرة جديدة باسم "${request.fullName}" وتفعيل حسابه.`,
    fields:
      selectField({ name: 'gender', label: 'الجنس', options: GENDERS, required: true }) +
      inputField({ name: 'birthDate', label: 'تاريخ الميلاد', type: 'date', required: true }),
    submitLabel: 'قبول الطلب',
    validate: (input) => {
      const errors = {};
      const genderError = rules.required('الجنس')(input.gender);
      if (genderError) errors.gender = genderError;
      const dateRequired = rules.required('تاريخ الميلاد')(input.birthDate);
      const datePast = rules.pastDate('تاريخ الميلاد')(input.birthDate);
      if (dateRequired || datePast) errors.birthDate = dateRequired || datePast;
      return errors;
    },
  });
  if (!values) return false;

  try {
    const memberId = await approveRegistrationRequest(request.id, {
      gender: values.gender,
      birthDate: values.birthDate,
    });
    toast.success('تم القبول', 'تم إنشاء الأسرة وتفعيل الحساب.');
    return memberId;
  } catch (error) {
    console.error(error);
    toast.error('تعذر القبول', error.message || 'حدث خطأ غير متوقع.');
    return false;
  }
}
```

`approveRegistrationRequest()` already returns the new member's `uuid`
(the RPC's `RETURNS uuid`) — the detail page's existing "go to the new
displaced record" behavior (`go('displaced-details.html', {id:
result.person.id})`) becomes `go('displaced-details.html', {id: memberId})`.
`displaced-details.html` already resolves a real Camp Admin session by raw
`family_members.id` (Phase 4.5), so this is a straight swap.

Reject handler needs no shape change beyond swapping `select.rejectRequest`
for `await rejectRegistrationRequest(request.id, note)` inside the same
try/catch-and-toast pattern.

**List reload after a decision.** Both mock handlers call `load(session)`
unconditionally after approve/reject, including when the mock function
returned `null` for "already reviewed." The real version only reloads on
success — reloading after a caught error would silently hide the toast
under a fresh skeleton render for no benefit, and every other real page in
this codebase (`aid.js`'s delete handler) only calls `load()` inside the
try block's success path.

## 7 · Security

- No `service_role`/secret key/database password/Cloudinary secret appears
  anywhere in `assets/js/` — confirmed by grep before implementation and
  again in the diff review step.
- No client-side-only authorization: approve/reject only ever reach the
  database through the two RPCs, which re-check `status='pending'` and camp
  match themselves (§2) — the UI's own checks (hiding the buttons on a
  non-pending request, the pre-approval duplicate alert) are conveniences,
  not the boundary.
- No hand-built `?campId=`/`?id=` trust: every list query is
  `getCampRegistrationRequests(session.campId)` (session-derived, matching
  `getCampFamilies`/`getCampDisplacedPersons`/`getCampAidDistributions`);
  every detail fetch is RLS-scoped regardless of what `id` is in the URL.
- No role switching, no URL-based bypass: both pages stay Camp-Admin-only in
  `PAGE_ACCESS` (unchanged).

## 8 · Testing

**`supabase/tests/phase4.7-camp-isolation.test.mjs`** — same shape as
`phase4.6-camp-isolation.test.mjs` (two seeded Camp Admins, `admin@camps.ps`
/ camp النور and `nour@camps.ps` / camp الرحمة), `node --test` + Playwright
against a same-process static server:

1. Each admin's RLS-scoped `select` on `registration_requests` returns only
   their own camp's rows (raw client, not through the app).
2. `registration-request-details.html?id=<other camp's request>` renders
   the not-found empty state, not the record.
3. `approve_registration_request` on another camp's pending request id is
   rejected with `42501` (raw RPC call, camp admin A → camp B's fixture
   request — see fixture setup below).
4. `reject_registration_request` on another camp's pending request id is
   rejected with `42501`.
5. A raw `.update()` on another camp's `registration_requests` row (status
   flip attempted directly, bypassing the RPC) matches zero rows — proves
   RLS blocks it even though `registration_requests_update_camp_admin`
   exists for the admin's *own* camp.
6. Rendered list at `registration-requests.html` never contains another
   camp's applicant name.

**Fixture, not seed data:** camp الرحمة has zero seeded registration
requests (confirmed live — all 5 seeded rows belong to camp النور), so
tests 3/4 need a pending request that belongs to camp الرحمة. Inserted with
a **service-role client** (`SUPABASE_SECRET_KEY`, Node-only, never in
`assets/js/`), `user_id: null` (matches the seed data's own convention —
all 5 existing rows already have `user_id: null` — and sidesteps any
`profiles` side effect from a real demo account), a fabricated 9-digit
`national_id` that doesn't collide with any real seeded person or request.
Cleaned up in a `finally` block with the same service-role client (§2: no
`DELETE` RLS policy exists for any authenticated role on this table, so
cleanup cannot go through the app's own permissions — this is a hard
constraint of the live schema, not a test shortcut).

**`supabase/tests/phase4.7-registration-requests-verification.test.mjs`** —
same shape as `phase4.6-aids-verification.test.mjs`: an independent
service-role/second-client query recomputes what the rendered page should
show and asserts the browser matches it, for:

1. List: row count and content match a direct `count(*)`/`select` scoped to
   `camp_id` + `status='pending'` (the page's default filter).
2. Search: typing the seeded pending applicant's name filters to exactly
   that row.
3. Status filter chips: switching to "الكل" shows all statuses; counts on
   the chips match direct per-status counts.
4. Detail: every field rendered (`fullName`, `nationalId`, `phone`, `email`,
   `campName`, `createdAt`) matches the direct row.
5. **Approve round trip**, using a **second, dedicated fixture** (own
   service-role insert, `user_id: null`, own fake national id, camp النور —
   so it exercises the real UI through `admin@camps.ps`): drive the real
   form (gender + birth date), submit, assert via a direct query that (a)
   the request's `status` is now `approved` with `family_member_id` set,
   (b) a `families` row now exists with that member as head, (c) the
   `family_members` row has the submitted gender/birth date. **Cleanup
   order matters** (§2's `registration_requests_approved_has_member`
   `CHECK`): delete the `registration_requests` fixture row *first*
   (service-role), *then* the family it points to (cascades to the member)
   — deleting the family first would try to null the already-deleted... no
   — would try to null `family_member_id` on a still-`approved` request and
   fail the `CHECK`.
6. **Reject round trip**, a third fixture: drive the real reject form with a
   note, assert `status='rejected'` and `note` matches directly. Cleanup:
   delete the fixture row directly (service-role) — no family was ever
   created, so no ordering concern.
7. Duplicate-national-id case: a fixture `registration_requests` row whose
   `national_id` matches an existing camp-النور `family_members` row
   (e.g., one of the seed families' heads); assert the detail page shows
   the "duplicate" alert and the approve button is either hidden or the
   approve attempt is rejected client-side before any RPC call.

Both suites clean up every row they insert, in `finally`, regardless of
assertion outcome — matching the existing suites' pattern (see
`phase4.6-aids-verification.test.mjs:352-357`).

**Full regression:** `cd supabase && npm run test:all` after registering
the two new scripts, must stay green. No existing test is modified.
