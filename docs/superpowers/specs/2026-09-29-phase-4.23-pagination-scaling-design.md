# Phase 4.23 — Pagination & Data Scaling (design)

## 1. Current scaling problem

Live data is tiny (39 members, 16 families, 17 distributions, 14 documents), so nothing is wrong today. Two failure modes appear as data grows:

1. **Silent truncation.** Every `getCampX()` / `getAllX()` read is an unbounded `select(...)`. PostgREST caps a response at `max-rows` (default 1000) and returns the first 1000 rows with **no error**. Lists, result counts, Excel exports and statistics would all quietly under-report.
2. **URL overflow.** `families.js` builds `.in('family_id', ids)` / `.in('member_id', ids)` from every id on the page. At ~36 chars per UUID the request line passes common 8 KB limits at roughly 200 ids (HTTP 414 / gateway reject).

A smaller third one: the notifications page passes `pageSize: 100`, and `paginate()` clamps to `MAX_PAGE_SIZE = 100`, so a user with more than 100 notifications sees 100 with no indication.

## 3. Key ruling: list pages stay client-filtered

The list pages filter with predicates that have no PostgREST equivalent over the current schema: `personFacts()` (child/orphan/pregnant derived from birth date and flags), "family contains at least one …" over `family_stats`, and aid-type/donor family-id sets. All of them are shared `matchesXFilters()` selectors used by the list, the count and the export. Re-expressing them as SQL would duplicate domain rules in a second language and risk the list/count/export disagreement `CLAUDE.md` forbids, and would need new views/RPCs. That is a redesign, not a scaling fix, and this phase must not change semantics.

So this phase makes the **fetch complete and bounded per request** (batched, deterministically ordered) and keeps `collect(session)` as the single query behind table, count and export. True server-side page slicing for those pages is **deferred** and recorded as the main remaining risk (browser memory / total transfer at very large row counts).

## 4. Pagination / batching contract

Reuse `assets/js/supabase/query.js` (existing contract: `{ rows, total }` from `listX()`, `paginate()`, `DEFAULT_PAGE_SIZE 20`, `MAX_PAGE_SIZE 100`; UI `PAGE_SIZE 10` in `config.js`). No second contract. Additions to `query.js`:

- `FETCH_BATCH = 1000`: the PostgREST default row cap.
- `fetchAll(makeQuery, { order, batchSize })`: `makeQuery()` returns a fresh builder; the helper applies every `order` column (callers end with a unique tiebreaker), loops `.range()` until a short batch, returns the concatenated rows. No `count` (no extra round trip).
- `fetchAllIn(makeQuery, column, values, opts)`: splits `values` into chunks of 100 and runs `fetchAll` per chunk.

Public return shapes stay arrays, so no caller changes.

## 5. Filtering / search
Unchanged: `matchesXFilters()` over the complete arrays; scope still from session + RLS.

## 6. Count strategy
Plain statistic counts use `select('id', { count: 'exact' }).range(0, 0)`, which returns at most one row plus the exact count. HEAD requests are avoided (they show `ERR_ABORTED` in Chromium against this project, as documented in `notifications.js`).

## 7. Ordering
Every batched read orders by its existing visible sort, then a unique key (`id`, or the junction table's composite key), so batches never overlap or skip when rows are inserted between requests.

## 8. Export
Exports already run on `collect()`, the full filtered set. With batching they stay complete past 1000 rows and are never "current page only". Verified with a small `batchSize` against the live DB.

## 9. Statistics
Gender, monthly registrations and family-size buckets become DB counts (≤ ~20 numbers). Donor-distinct and aid-type breakdown read one narrow column in batches. `statistics.html` reads the four full datasets through the batched readers: complete, but not DB-aggregated (limitation recorded). No new RPC or migration.

## 10. RLS / security
No schema, policy or RPC change. Every query uses the same user-JWT client; batching only adds `.range()`/`.order()`. Camp scope keeps coming from `session.campId` plus RLS; nothing filters by camp in JS. Counts are computed on RLS-visible rows. No service-role in browser code (grep-verified).

## 11. Testing
- `phase4.23-pagination-verification.test.mjs`: `fetchAll` with a small `batchSize` over the real tables as each role, compared with an independent service-role `select`; exact boundaries, empty and one-row results; no duplicates or gaps; ordering; `fetchAllIn` with 250 synthetic ids; DB-count statistics vs independent counts.
- `phase4.23-pagination-isolation.test.mjs`: camp admin never sees another camp through batched reads at any batch size; displaced sees own family only; anonymous denied.
- Browser: affected pages at 320/375/768/1024/1280/1440, console/network errors, body-based overflow check.
- Regression: `npm run test:all`.

## 12. Performance verification
Large fixtures would pollute the live project, so batching is proven with a small `batchSize` (same code path as 1000) instead of inserting more than 1000 rows. Limitation recorded.

## 13. Backward compatibility
All public signatures and returns unchanged. `query.js` only gains exports.

## 14. Explicitly deferred
Server-side slicing for filter-heavy lists; SQL/RPC aggregation for `statistics.html`; DB views for `personFacts`; indexes (none proven necessary).
