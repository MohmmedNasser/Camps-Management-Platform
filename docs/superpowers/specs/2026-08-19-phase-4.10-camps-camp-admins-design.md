# Phase 4.10 — Super Admin Camps & Camp Admins on Real Data — Design

**Status:** approved for implementation (inline execution, no subagents)
**Pages in scope:** `pages/camps.html`, `pages/camp-admins.html` — both Super-Admin-only in `PAGE_ACCESS` (`assets/js/core/config.js:279-280`), so unlike every Phase 4.2–4.9 page there is no second role branch to preserve. Both pages go **fully real, no mock branch**, the same end-state Phase 4.9 reached for `organizations.html`.

## 1. Investigation summary

### 1.1 What already exists (reusable, not mock-only)

Phase 2/3 already built a real data-access layer for camps and profiles that no page has ever called:

- `assets/js/supabase/camps.js` — `listCamps({status,sortBy,sortDir})`, `getCamp(id)`, `createCamp({name,governorate,city})`, `updateCamp(id,patch)` (allow-list: name/governorate/city only), `setCampStatus(id,status)`.
- `assets/js/supabase/profiles.js` — `getOwnProfile()`, `updateOwnProfile(patch)`, `listProfiles({role,campId,status,page,pageSize,sortBy,sortDir})`, `assignCampAdmin(profileId,campId)` (sets role+camp_id together, Super-Admin-only per RLS+trigger), `setProfileStatus(profileId,status)`.
- `assets/js/supabase/dashboard.js`'s private `buildCampBreakdown(camps)` (Phase 4.2) already composes `getDashboardStatistics(camp.id)` + `listProfiles({role:'camp_admin',campId,pageSize:1})` into exactly the per-camp stats shape (`displacedCount, familiesCount, aidCount, adminsCount, disabilityCount, childrenCount, orphansCount`) `camps.js`'s mock `select.campBreakdown()` currently produces. It is private (not exported) and only used by `getSuperAdminDashboard()`.
- `core/config.js` `GOVERNORATES` matches the live `governorate` enum exactly (`north_gaza, gaza, deir_albalah, khan_younis, rafah`); `STATUS.ACTIVE/DISABLED` match the live `camp_status` enum; `campSchema()`/`campFields()` in `ui/record-forms.js` need no field changes for camps.

### 1.2 Live schema/RLS findings (verified against project `qlvftlecwoqmvtagaykr`, not local migration files)

- `camps`: `id, name(unique on lower(btrim)), governorate, city, status(active|disabled), created_at, updated_at`. RLS: SELECT open to `anon`/`authenticated` for `status='active'`, plus full visibility for `is_super_admin()`; INSERT/UPDATE/DELETE all `is_super_admin()`-only, no camp predicate (there's nothing to scope — a camp has no owning camp). `camps_name_key` is a **unique functional index**, so duplicate-name detection is DB-enforced (`23505`), same shape as Phase 4.9's `organizations_name_key`.
- `profiles`: **no `email` column.** Email lives only in `auth.users`, which PostgREST/the publishable key cannot read directly. SELECT/UPDATE RLS: own row, OR `is_super_admin()` (any row), OR `is_camp_admin()` for their own camp. INSERT: `is_super_admin()` only. DELETE: `is_super_admin()` only (`profiles_delete_super_admin`, confirmed live — previously unused by any page).
- Trigger `private.guard_profile_privileges` (fires on every `profiles` UPDATE from a browser session): blocks changing `id` always; blocks changing `role` unless `is_super_admin()`; blocks changing `camp_id` unless `is_super_admin()` (or a camp_admin attaching a newly-approved account to their own camp — the approval flow, irrelevant here); blocks changing `status` unless super_admin or camp_admin; blocks changing `family_member_id` unless super_admin or camp_admin. So a Super Admin can freely change `full_name`, `phone`, `role`, `camp_id`, `status` on **any** profile via a plain `.update()` with the publishable key — no new RPC needed for edit/status/reassignment.
- FK delete rules: every FK from `families/family_members/profiles/aid_distributions/registration_requests/documents` → `camps.id` is `ON DELETE RESTRICT` (`messages.camp_id` is `CASCADE`, irrelevant to blocking). Every FK from `families/family_members/aid_distributions/documents/messages/registration_requests` → `profiles.id` (the `created_by`/`uploaded_by`/`reviewed_by`/`sender_id`/`replied_by`/`recipient_id` audit columns) is `ON DELETE SET NULL`, except `messages.sender_id` (`CASCADE`) and `notifications.recipient_id`/`user_preferences.user_id` (`CASCADE`, a user's own inbox/prefs). **Deleting a `profiles` row is therefore always FK-safe** — it never fails on a foreign key, unlike deleting a camp.
- `router.js`'s `guard()` already redirects a session whose `getSession()` throws `ProfileError('missing')` to `auth-error.html` (`assets/js/core/router.js:89-100`, `assets/js/core/auth.js:110-114`) — so a deleted admin's now-profile-less `auth.users` row already degrades gracefully if they try to sign back in. This existing behavior is what makes "delete camp admin" safe to wire for real: nothing new to build for the failure mode.
- No RPC or Edge Function anywhere creates an `auth.users` row with elevated privilege. `list_edge_functions` returns exactly 3 functions: `documents-upload`, `documents-access`, `documents-delete` (Cloudinary only). `pg_proc` has no `invite`/`create_admin`/`create_user` function. The only path that creates an `auth.users` row is `assets/js/supabase/auth.js`'s `signUp()`, used by the public self-registration flow (`core/auth.js:register()`), which **signs the new user into the current browser client**, replacing whatever session was active.
- No view or function anywhere exposes `auth.users.email` to the publishable key. `information_schema.views` in `public` has only `family_member_facts` and `family_stats`.
- Live data: 3 camps (all `status='active'`), 8 profiles (1 super_admin, 3 camp_admin — one already `status='disabled'`, 4 displaced), 8 `auth.users`. Zero profiles are `role='displaced' AND status='pending' AND camp_id IS NULL` (i.e., there is no self-registered-but-unprovisioned account sitting around to "promote" today). Security baseline: `get_advisors` returns exactly 5 `authenticated_security_definer_function_executable` WARNs (one per existing privileged RPC) + 1 pre-existing `auth_leaked_password_protection` WARN — no other findings.

### 1.3 The one blocked operation, and why

**"Create a new Camp Admin account" (mock: `camp-admins.js` `openEditor(session, null)` — collects name/email/phone/**password**/camp/status and creates a brand-new login in one step) cannot be ported to real data without either:**

1. A new Edge Function using the `service_role` key server-side (same trust model as `documents-upload`/`documents-access`/`documents-delete`) that verifies the caller is `super_admin`, calls the Auth Admin API (`auth.admin.createUser`), and immediately promotes the resulting profile row to `role='camp_admin'` — **this function does not exist today**; or
2. Calling `supabase.auth.signUp()` directly from the Super Admin's own browser tab with the publishable key — which is not "insecure" in the RLS sense, but it **replaces the Super Admin's own authenticated session with the brand-new account's session** (GoTrueClient is a singleton per client instance; this is standard, documented Supabase behavior, not a bug), and the new profile is hard-coded `role='displaced', status='pending'` by `private.handle_new_user` regardless of what the Super Admin picked. There is no way to give this new account `role='camp_admin'` without a second, separately-authenticated write, by which point the acting session is already gone.

Per the phase brief's explicit decision rule, this is exactly the case to defer rather than work around: **Option 2 is a genuine architecture violation (session hijack), not a rough edge, so it is not implemented.** Option 1 is the correct fix but is out of scope for a frontend-migration phase with no `service_role` access from this environment (the phase brief itself says: "Never expose the `service_role` key to the frontend" and "if there is no safe existing mechanism, leave that specific create/invite operation documented as a backend requirement").

**Decision: "Create Camp Admin" is deferred.** `camp-admins.html` keeps its "إضافة مسؤول" button (UI is preserved — nothing is removed), but clicking it opens an explanatory dialog instead of the create form, stating plainly that this action needs a backend capability (secure Auth-user creation) that does not exist yet, and that existing accounts can still be edited, enabled/disabled, or removed. See §4 for the exact backend requirement to unblock this later.

An alternative was considered and rejected: reinterpreting "create" as "promote an existing self-registered-but-unprovisioned account to Camp Admin" using only `assignCampAdmin()` + `setProfileStatus()` (both already real, no privileged operation involved). This is technically safe, but (a) it changes what "إضافة مسؤول" means well beyond "connect the existing UI to real data" — the mock form's password field and one-step semantics say "provision a new person," not "search for a pending signup," and the brief says not to redesign pages or invent new UI flows; (b) there are currently zero eligible accounts in the live database to build and verify this flow against. It is noted here as the cheapest future path (§4) but not implemented.

**A second, smaller gap, same root cause (no email in `profiles`):** the mock's camp-admin list shows each admin's email. The real `profiles` table has none, and there is no existing view/RPC that exposes it. This is not the unsafe kind of gap — it doesn't require Auth-user creation, only a read of `auth.users.email` restricted to `super_admin`, which the existing `SECURITY DEFINER` pattern (`get_dashboard_statistics`, `approve_registration_request`, …) already handles safely elsewhere in this project. §3.1 adds one new function for it.

## 3. Design

### 3.1 Backend: one new function (migration required)

```sql
create or replace function public.get_camp_admin_accounts()
returns table (
  id uuid,
  full_name text,
  email text,
  phone text,
  camp_id uuid,
  camp_name text,
  status public.account_status,
  created_at timestamptz
)
language plpgsql
security definer
set search_path to ''
as $$
begin
  if not private.is_super_admin() then
    raise exception 'لا تملك صلاحية عرض حسابات مسؤولي المخيمات' using errcode = '42501';
  end if;

  return query
  select p.id, p.full_name, u.email, p.phone, p.camp_id, c.name, p.status, p.created_at
  from public.profiles p
  join auth.users u on u.id = p.id
  left join public.camps c on c.id = p.camp_id
  where p.role = 'camp_admin'
  order by p.created_at;
end;
$$;

revoke all on function public.get_camp_admin_accounts() from public;
grant execute on function public.get_camp_admin_accounts() to authenticated;
```

Same shape as every existing privileged RPC in this project (`STABLE`-equivalent read, `SECURITY DEFINER` only because it must cross into `auth.users`, internal `is_super_admin()` check raising `42501` — not RLS, since this is a function not a table read). It adds a 6th entry to the already-accepted `authenticated_security_definer_function_executable` WARN class; `get_advisors` is re-run after applying it to confirm no *new* class of finding appears.

No other schema change. No new table, no new enum, no new trigger, no RLS policy change — every other operation in scope is already covered by existing RLS.

**`ui/record-forms.js`**: `campAdminFields()` gets one small change — when `!isNew`, the email `inputField` is rendered `disabled` with a hint explaining the email cannot be changed here. `campSchema()`/`organizationFields()`/everything else: unchanged. ## 4. Deferred functionality — exact backend requirement

**"Create a new Camp Admin account"** needs, before it can be implemented for real:

- A new Edge Function (e.g. `admin-create-camp-admin`), deployed with the `service_role` key available only in its own server-side environment (same trust boundary as `documents-upload`/`documents-access`/`documents-delete` today).
- The function must: verify the caller's JWT, look up the caller's own `profiles.role` server-side and reject anything but `super_admin`; call `auth.admin.createUser({ email, password, email_confirm: true, user_metadata: { full_name, phone } })`; then, in the same request (using its own service client, which bypasses RLS legitimately because the check already happened), update the resulting `profiles` row to `role='camp_admin', camp_id=<chosen>, status='active'` — overriding the `handle_new_user` trigger's default `role='displaced', status='pending'`.
- Once that function exists, `camp-admins.js`'s create flow becomes a single new data-access call to it; the explanatory modal added in this phase is removed.

No other operation in this phase is deferred.

## 5. Security boundaries

1. `camps.html`/`camp-admins.html` route access: `PAGE_ACCESS` (unchanged) — only `super_admin`.
2. Every read/write in this phase is RLS-gated to `is_super_admin()` at the database, independent of `PAGE_ACCESS`/`can()` (which are UX-only, per `core/auth.js`'s own header comment).
3. The one new function (`get_camp_admin_accounts`) is `SECURITY DEFINER` **only** to cross into `auth.users`; it re-checks `is_super_admin()` internally before returning anything, so granting `EXECUTE` to `authenticated` does not widen access — a `camp_admin`/`displaced` caller gets a `42501` from inside the function, not data.
4. No client-side filtering is relied on as a security boundary anywhere in this phase — every list is what RLS already returns; `matchesCampAdminFilters()` only narrows an already-authorized result set for display.
5. No `service_role` key, database password, or Cloudinary secret is added to any browser-reachable file in this phase — confirmed by grep before commit and by a Playwright page-content check in the new test suite (§6).
6. No hardcoded camp/profile IDs in product code (test fixtures use the live seeded camp IDs the same way existing Phase 4.3/4.6/4.7/4.8 isolation suites already do, as literal constants inside the test file only).

## 6. Testing strategy

Two new suites, same conventions as `supabase/tests/phase4.9-*.test.mjs` (local static server + Playwright + an independent `service_role` client + `.env` loader):

- `supabase/tests/phase4.10-role-authorization.test.mjs`: `super_admin` full camps CRUD + `get_camp_admin_accounts()` succeeds; `camp_admin`/`displaced` camps write rejected `42501`, `get_camp_admin_accounts()` rejected `42501` (via `client.rpc(...)`, independent of any frontend code); anonymous rejected; route guard sends `camp_admin`/`displaced` sessions to `404.html` for both pages; no `service_role` string in rendered page HTML.
- `supabase/tests/phase4.10-camps-verification.test.mjs`: DB-vs-UI camp list/stat/status match an independent `service_role` query; search; create → edit (name/governorate/city/status) → toggle → delete round trip, all against a fixture camp created and destroyed within the test (`finally`); duplicate-name rejection; delete-blocked-while-in-use (fixture camp + fixture family, prove the friendly rejection, then delete the family before the camp in cleanup so the fixture camp itself can be removed without debris).
- `supabase/tests/phase4.10-camp-admins-verification.test.mjs`: DB-vs-UI list/search/campId-filter/status-filter match an independent query; **email is verified against `serviceClient.auth.admin.listUsers()`/`getUserById()` — the Auth Admin API, not the RPC this phase adds** (a genuinely independent path, not "verify the function against itself"); CRUD is proven against a **fixture admin created directly through the service client** (`auth.admin.createUser` + a manual `profiles` upsert to `role='camp_admin'`) since the app itself cannot create one — edit/toggle/delete then go through the real UI/data-access functions against that fixture, and cleanup deletes both the `profiles` row and the `auth.users` row (`auth.admin.deleteUser`) so zero debris remains, even beyond what the app alone could clean up; a case proving the "إضافة مسؤول" button opens the explanatory dialog and creates no row (a deferred-operation is proven deferred, not silently skipped).

`npm run test:all` (from `supabase/`) must still pass unmodified beforehand and after, with the two new suites appended to its script (mirroring how every prior phase added itself).

## 7. Review focus (things likely to bite that no single task's happy-path test would catch)

1. Editing a camp admin's `camp_id` when nothing else changed — `assignCampAdmin` also sets `role='camp_admin'` unconditionally; confirm it's a safe no-op re-set for an account that is already `camp_admin` (it is — `guard_profile_privileges` only blocks *actual changes*, `new.role is distinct from old.role` is false when both are `camp_admin`).
2. Deleting a camp that has zero families/displaced/admins in `listCampsWithStats()`'s counts but still has a `documents` or `registration_requests` row directly against it (not caught by the fast client-side pre-check) — must still surface the friendly "camp in use" message via the DB-RESTRICT backstop, not a raw Postgres error.
3. The disabled email field on edit must still let the rest of the form submit — `readForm()` reads `.value` off disabled inputs via `querySelectorAll`, not `FormData` (confirmed in `ui/form.js`), so this is expected to work, but the plan's test must click through an actual edit save with the field present and disabled, not just unit-test the markup.
4. `toolbar.js`'s `getFilters` hook — confirm whether it awaits a promise before assuming `listCampOptions()` can be passed there directly; if it's synchronous-only, options must be fetched once in `load()`/`init()` and cached in `state`, not passed as an async `getFilters` callback.
5. A `camp_admin` (not `displaced`) signed in and hitting `camps.html`/`camp-admins.html` directly by URL — `PAGE_ACCESS` already blocks this, but the phase 4.9 precedent shows it's worth a dedicated assertion per role, not just "displaced redirected," since `camp_admin` is the role most likely to have a stale bookmark from before this phase.
