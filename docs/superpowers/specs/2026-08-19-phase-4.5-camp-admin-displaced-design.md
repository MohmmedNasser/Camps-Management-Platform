# Phase 4.5 — Camp Admin Displaced Persons on Real Data

**Date:** 2026-08-19
**Status:** Approved for implementation

## 1 · Context

Phase 4.4 connected the Camp Admin's slice of the families flow. Phase 4.5
connects **only the Camp Admin's slice** of the displaced-person flow:
`displaced.html` (list), `displaced-create.html`, `displaced-details.html`,
`displaced-edit.html` — only the `camp_admin` role branch of each. Super
Admin's displaced list/detail and the displaced person's own dashboard/
profile stay mock, unchanged.

**Live project verified via Supabase MCP before writing this spec** (same
project as prior phases, `qlvftlecwoqmvtagaykr`):

- **`family_members` IS the displaced-person table** (BACKEND.md §2: "In the
  frontend every displaced person already belongs to exactly one family, so
  a separate 'displaced' table would have been the same rows twice").
  `family_members.family_id` is **`NOT NULL`** (confirmed via
  `list_tables`: the column carries no `nullable` option) with
  `ON DELETE CASCADE` to `families`. **This means the real backend cannot
  represent a displaced person without a family** — the mock's
  `displacedFields()` "بدون أسرة" (no family) option has no real-schema
  equivalent. CLAUDE.md domain rule 13 already documents the intended
  architecture: *"A family and its members are registered through one
  form... `displaced-create.html` exists only for adding a person to a
  family that already exists."* The real Camp Admin path implements this
  already-stated rule literally; the Super Admin/mock path (which still
  allows "بدون أسرة") is untouched. This is not a schema change or an
  invented rule — it is CLAUDE.md's existing, binding domain rule 13
  finally being enforced for the one path capable of hitting the real
  constraint.
- **Every column `displacedFields()`/the detail tabs read exists on
  `family_members`, with matching enum values**, confirmed column-by-column
  against `list_tables`: `gender` (male/female), `marital_status`
  (single/married/divorced/widowed), `nationality`
  (palestinian/other), `tent_type` (tarp_tent/prefab_tent — exactly two, per
  domain rule 3), `governorate` (5 values, matches `GOVERNORATES`),
  `work_status` (5 values, matches `WORK_STATUSES`), `income_source` (5
  values, matches `INCOME_SOURCES`), `relationship` (9 values, matches
  `RELATIONSHIPS` exactly), `father_status`/`mother_status`
  (alive/deceased, matches `PARENT_STATUS`). **No filter or field needs to
  be dropped or invented.**
- **`is_orphan` is a generated column** (`father_status = 'deceased' OR
  mother_status = 'deceased'`), matching `selectors.isOrphan()` exactly —
  domain rule 14, already enforced server-side, nothing to change.
- **`family_members.status`** (`account_status` enum:
  pending/approved/rejected/active/disabled) exists and matches the mock's
  status filter/badge. In practice every real row's status is `'approved'`
  — a person becomes a `family_members` row only via
  `create_family_with_members`, `add_family_member` (both default
  `status` to `'approved'` when omitted) or `approve_registration_request`
  (which the DB itself sets to approved) — pending/rejected people exist
  only as `registration_requests` rows, not `family_members` rows. The
  status filter still functions correctly against real data; it will just
  never show anything but "معتمد" until/unless a future phase writes a
  different status. Not a mismatch — confirmed by reading
  `insert_family_member`'s source live.
- **`add_family_member(p_family_id uuid, p_member jsonb)`** (Phase 2,
  already built, never called from any page before this phase) internally
  authorizes `is_camp_admin() AND current_camp_id() = (select camp_id from
  families where id = p_family_id)`, raising `42501` otherwise, and calls
  the same `private.insert_family_member()` helper
  `create_family_with_members` already uses — so it reads the **identical
  snake_case jsonb shape** `family-create.js`'s `toMemberPayload()` already
  produces (Phase 4.4). No new RPC is needed for create.
- **`family_members` RLS is camp-scoped on every verb**, identical shape to
  `families`' (confirmed live via `pg_policies`):
  `family_members_select_scoped` (super_admin all / camp_admin own camp /
  displaced own family), `family_members_insert_camp_admin`,
  `family_members_update_camp_admin`, `family_members_delete_camp_admin` —
  all `is_camp_admin() AND camp_id = current_camp_id()`. **Every query in
  this phase is independently camp-scoped by RLS regardless of what the
  client passes.**
- **`documents`** has a real `family_member_id` FK
  (`documents_family_member_id_fkey`, `ON DELETE CASCADE`), and its RLS
  (`documents_select/delete_scoped`, `documents_update_admin`) is
  camp-scoped the same way. `listDocuments({ familyMemberId })` (Phase 2,
  already built) is the exact query the details page's documents tab needs.
- **Deletion cascade, confirmed live, not assumed:**
  `family_members_family_id_fkey.confdeltype = 'c'` (family deleted →
  members cascade — already known from Phase 4.4).
  `documents_family_member_id_fkey.confdeltype = 'c'` — deleting a
  `family_members` row cascades to their documents automatically, which is
  exactly what the mock's `removeDisplaced()` does by hand
  (`store.documents.removeWhere(...)`); the existing confirm-dialog copy
  ("سيتم حذف … وكل ما يرتبط به من مستندات") already matches this behavior
  **without needing a copy change**, unlike Phase 4.4's family-delete copy.
  A trigger, `family_members_promote_head` (`AFTER DELETE ON
  family_members`), reads `pg_get_functiondef` live: if the deleted member
  was the family's head, it promotes the next member (by birth date) to
  head, or deletes the family if none remain — this is domain rule
  "Removing a family head promotes another member," already implemented,
  confirmed by reading the function body rather than trusting BACKEND.md's
  summary.
- **Family reassignment on edit has no server-side integrity net.**
  `family_members_sync_camp` (`BEFORE INSERT OR UPDATE OF family_id,
  camp_id`) derives `camp_id` from the new `family_id` automatically (so
  `camp_id` must never be sent in an update payload — it is
  trigger-derived, matching domain note "a member always lives in their
  family's camp"). But `family_members_promote_head` fires **only on
  `AFTER DELETE`**, confirmed via `pg_trigger` — reassigning a family's
  head to a *different* family via `UPDATE family_members SET family_id =
  ...` does **not** trigger head promotion in the old family, which would
  leave `families.head_member_id` pointing at someone no longer a member.
  This is a genuine, confirmed (not assumed) integrity gap with no
  migration authorized to close it. **Decision:** the real Camp Admin edit
  path does not expose family reassignment (§5.4) — every other field
  remains editable. This is a frontend scope decision, not a schema
  change, and is the same class of "found a real gap, narrowed scope
  rather than inventing a migration" precedent as Phase 4.4 §2's constraint
  12.
- `mcp__supabase__get_advisors` (security): the same 5 pre-existing,
  already-documented `authenticated_security_definer_function_executable`
  WARNs (the 4 Phase 1 workflow functions + `add_family_member`) plus
  `auth_leaked_password_protection` — identical to the Phase 4.4 baseline.
  No new finding. Clean baseline confirmed before writing this spec.

## 2 · Non-negotiable constraints (from approval)

1. **Super Admin stays mock — no exceptions.** Only the `camp_admin` branch
   of each page's `collect()` uses the new real-data path. The displaced
   person's own dashboard/profile/"أسرتي" stay entirely out of scope and
   untouched.
2. **Every write is authorized by RLS, not client code.** No client-side
   camp-id comparison is ever a security gate — only redundant UX copy
   selection, exactly like Phase 4.4's precedent.
3. **Person creation goes through `add_family_member()` only** (existing
   Phase 2 RPC). No new client-side sequence of `INSERT`s. `familyId` is
   **required** for the real Camp Admin create path (§1: DB constraint +
   domain rule 13) — the "بدون أسرة" choice is removed from the real path
   only; the Super Admin/mock path is untouched.
4. **One export pipeline**, same shape as Phase 4.4's: real camp-scoped
   data → the existing shared filter predicate → the existing
   `displacedExportRow()`/`DISPLACED_COLUMNS` → the existing `exportSheet()`.
   No second export implementation.
5. **No unnecessary architectural changes.** No new table, column, RLS
   policy, RPC, trigger or migration. Work happens on local `main` directly
   (per the user's explicit "inline execution only" instruction for this
   phase — no worktree), verified fully before being considered done, never
   pushed to any remote.
6. **Family reassignment is not exposed on the real edit path** (§1's
   confirmed integrity gap). The family field renders read-only there;
   every other field stays editable.
7. `Promise.all` for independent data requests within one page load.
8. No `service_role` or private secret in browser code; no RLS bypass; no
   hardcoded camp id; no client-side role switching.
9. A genuinely empty camp (zero displaced people) renders the real
   `emptyState()` — filters still behave, export is refused the same way
   it already is for an empty mock result.
10. Reuse existing loading/skeleton/error/empty-state mechanisms — no new
    UI pattern.
11. Full existing test suite (142 tests before this phase) must stay
    green, plus this phase's new suites folded into `test:all`.
12. If a genuine backend blocker is found beyond what §1 already resolved,
    STOP and report — do not silently work around it.
13. `session.familyMemberId` (populated from `profiles.family_member_id`
    — the field the Phase 4.5 prompt calls `session.displacedId`; that name
    does not exist in `core/auth.js`, confirmed by reading it) is **not**
    read anywhere in this phase's Camp Admin code path. It is only ever
    relevant to a `displaced`-role session (their own dashboard/"أسرتي"),
    which is out of scope. No auth/session change of any kind is made.

## 4 · What is genuinely missing

Matching the "one or two new functions" shape of prior 4.x phases, all
added to `assets/js/supabase/family-members.js` (already the file that
owns this table):

1. **`mapDisplacedRow(row)`** — local (not exported) mapper, snake_case DB
   row → the camelCase shape `displacedFields()`/`personFacts()`/the detail
   tabs/`displacedExportRow()` already read. The mirror image of the
   already-existing `toFamilyMemberPayload()` (item 5 below).
2. **`getCampDisplacedPersons(campId)`** — new composition function. One
   query over `family_members` embedding
   `family:families!family_members_family_id_fkey(reference_code)`, mapped
   via `mapDisplacedRow`. No second query needed — every field
   `personFacts()`/the table/the export need is a plain column already on
   `family_members`, unlike families' aggregate `family_stats`.
3. **`getDisplacedPerson(id)`** — new function, same shape, `.eq('id',
   id).maybeSingle()`. Used by the details and edit pages. Returns `null`
   for a nonexistent or another-camp id — RLS makes the two
   indistinguishable, exactly like `getFamilyByReferenceCode`.
4. **`getFamilyIdsForAidFilter(campId, { aidTypeCode, organizationId })`**
   (new, in `aids.js` next to the other aid queries) — the list page's
   `aidType`/`organizationId` filters need "which families received a
   matching distribution," which is not on `family_members` at all.
   `listAidDistributions()` (Phase 2) cannot be reused as-is: it
   paginates at `DEFAULT_PAGE_SIZE = 20` (`query.js`), which would silently
   truncate the filter's family set. This new function selects only
   `aid_distribution_families.family_id` through the same
   `!inner`-embedded filter shape `listAidDistributions()` already uses,
   with no `range()` call, returning a `Set` of family UUIDs.
5. **`toFamilyMemberPayload(values, overrides)`** — **extracted**, not new
   logic, from `family-create.js`'s existing local `toMemberPayload()`
   (Phase 4.4 §4 item 5 explicitly predicted this: *"kept local per
   YAGNI — Phase 4.5's displaced-person pages will need the identical
   mapping and can extract it then"*). Moved to `family-members.js` and
   exported; `family-create.js` is updated to import it instead of its
   local copy. Reused by both `displaced-create.js` (as the payload to
   `addFamilyMember`) and `displaced-edit.js` (as the payload to
   `updateFamilyMember`, with `camp_id` never included — §1's trigger
   derives it).

   **One real bug found and fixed during this extraction, not carried
   forward:** the existing `toMemberPayload()` hardcodes
   `relationship: 'member'` for every non-head member
   (`family-create.js`'s member blocks call it with no `overrides` at
   all), but `'member'` is **not a value of the `family_relationship`
   enum** (`head, spouse, son, daughter, father, mother, brother, sister,
   other` — confirmed live in §1). `readMember()` already extracts the
   admin's actual chosen relationship
   (`at('relationship') || 'other'`) into the object passed in, but the
   mapper never reads it — silently discarding it and substituting an
   invalid literal. This never surfaced because Phase 4.4's own creation
   test (`phase4.4-families-verification.test.mjs`) only ever submits a
   head-only family (zero additional member blocks), so
   `create_family_with_members` was never actually called with a
   non-empty `p_members` array carrying this bug. Phase 4.5 must call the
   extracted mapper with real, varying relationship values (the whole
   point of `displaced-create.js`), so the fix is a necessary part of this
   extraction, not optional cleanup: `relationship: values.relationship ||
   'other'` replaces the hardcoded `'member'`. This is a minor
   implementation bug fix (an invalid literal for an enum column), not an
   architectural change, and incidentally fixes the same latent bug for
   `family-create.js`'s own additional-member path.
6. **`matchesDisplacedFilters(row, filters, { aidFamilyIds } = {})`** — new
   function in `core/selectors.js`, next to `matchesFamilyFilters`. Unlike
   Phase 4.4's families predicate, this is **not** extracted from
   `getFilteredDisplaced()`/`searchDisplaced()` — those two mock functions
   are left completely untouched (§7 explains why: their filtering logic
   spans two stages with a scope/campId concern the real path handles
   differently — via RLS instead of a `scopeFilter()` predicate — and there
   is no existing automated regression suite for the mock's displaced
   filters the way Phase 4.4 had for families, so a live, working code path
   is not worth the refactor risk for this phase). The new function
   independently re-implements the *same* filter semantics (search term
   over name/name-en/national ID/phone/family code, gender, status, tent
   type, cumulative age band, `isChild`/`isOrphan`/`hasChronic` via
   `personFacts()`, maternity filters gated on `maternityApplies`, and the
   aid-family-membership check via the `aidFamilyIds` set from item 4) —
   verified against `getFilteredDisplaced()`'s existing logic field-by-field
   in §5.1, and proven correct by the DB-vs-UI suite (§8.3) rather than by
   code sharing.
7. **A `requireFamily` opt-in on `displacedSchema()`** — one additive
   parameter (`displacedSchema({ isDuplicateId, requireFamily = false })`),
   default `false` (mock/Super-Admin behavior byte-for-byte unchanged),
   adding `familyId: [rules.required('الأسرة')]` only when `true`. Passed
   only by the real Camp Admin branches of `displaced-create.js`/
   `displaced-edit.js` (§1 constraint 3/§2 constraint 3).

`core/selectors.js` — the new predicate:

```js
export function matchesDisplacedFilters(person, filters = {}, { aidFamilyIds = null } = {}) {
  const {
    query = '', gender = '', status = '', tentType = '', ageBand = '',
    isChild: childFilter = '', isOrphan: orphanFilter = '', hasChronic: chronicFilter = '',
    isPregnant: pregnantFilter = '', isBreastfeeding: breastfeedingFilter = '',
    aidType = '', organizationId = '',
  } = filters;

  if (gender && person.gender !== gender) return false;
  if (status && person.status !== status) return false;
  if (tentType && person.tentType !== tentType) return false;
  if ((aidType || organizationId) && !(aidFamilyIds && aidFamilyIds.has(person.familyId))) return false;

  const facts = personFacts(person);
  const band = AGE_BANDS.find((entry) => entry.value === ageBand);
  if (band && !isUnder(person, band.max)) return false;
  if (!matchesYesNo(childFilter, facts.isChild)) return false;
  if (!matchesYesNo(orphanFilter, facts.isOrphan)) return false;
  if (!matchesYesNo(chronicFilter, facts.hasChronic)) return false;
  if (pregnantFilter) {
    if (!facts.maternityApplies) return false;
    if (!matchesYesNo(pregnantFilter, facts.isPregnant)) return false;
  }
  if (breastfeedingFilter) {
    if (!facts.maternityApplies) return false;
    if (!matchesYesNo(breastfeedingFilter, facts.isBreastfeeding)) return false;
  }

  const term = query.trim().toLowerCase();
  if (!term) return true;
  return (
    person.fullName.toLowerCase().includes(term) ||
    (person.fullNameEn || '').toLowerCase().includes(term) ||
    (person.nationalId || '').includes(term) ||
    (person.phone || '').includes(term) ||
    (person.familyId || '').toLowerCase().includes(term)
  );
}
```

This is field-for-field identical to `searchDisplaced()`'s
gender/tentType/status/aid/term checks plus `getFilteredDisplaced()`'s
band/facts checks (§4 item 6 explains why it is a parallel implementation,
not an extraction). `aidFamilyIds` uses `person.familyId` (the reference
code), matching the `Set` `getFamilyIdsForAidFilter` returns (§5.1
continued below) once mapped to reference codes.

`getFamilyIdsForAidFilter(campId, { aidTypeCode, organizationId })`
(`aids.js`) — rooted at `aid_distributions` and using the exact same
nested-embed filter shape `listAidDistributions()` in this same file
already uses successfully (`aid_distribution_types.aid_type.code`, one
level of embedded-filter nesting past the root — the pattern PostgREST
actually supports and this codebase already relies on; a query rooted at
the junction table instead, filtering three levels through
`distribution.aid_distribution_types.aid_type.code`, was rejected as an
untested, deeper nesting than any existing query in this codebase uses):

```js
export async function getFamilyIdsForAidFilter(campId, { aidTypeCode = '', organizationId = '' } = {}) {
  const client = requireClient();
  const typesRel = aidTypeCode
    ? 'aid_distribution_types!inner(aid_type:aid_types!inner(code))'
    : 'aid_distribution_types(aid_type:aid_types(code))';
  let query = client
    .from('aid_distributions')
    .select(`camp_id, ${typesRel}, aid_distribution_families(family:families(reference_code))`)
    .eq('camp_id', campId);
  if (organizationId) query = query.eq('organization_id', organizationId);
  if (aidTypeCode) query = query.eq('aid_distribution_types.aid_type.code', aidTypeCode);

  const rows = await run(query);
  const ids = new Set();
  rows.forEach((row) =>
    (row.aid_distribution_families || []).forEach((link) => {
      const code = link.family?.reference_code;
      if (code) ids.add(code);
    })
  );
  return ids;
}
```

```js
async function collectReal(id, session) {
  const person = await getDisplacedPerson(id);
  if (!person || person.campId !== session.campId) return { person: null };

  const family = person.familyId ? await getFamilyByReferenceCode(person.familyId) : null;

    person,
    family: family ? { ...family, campName: session.campLabel } : null,
    aid: aidRows.map(mapAidHistoryRow),
    documents: docsResult.rows.map(mapDocumentRow),
    campName: session.campLabel,
  };
}
```

```js
  bindForm(form, {

      const family = families.find((f) => f.id === values.familyId);
      if (!family) { setFieldError(form, 'familyId', 'اختر أسرة صحيحة.'); return; }
      const familyUuid = (await getFamilyByReferenceCode(values.familyId))._dbId;
      try {
        const memberId = await addFamilyMember(familyUuid, toFamilyMemberPayload(values));

      } catch (error) {

          toast.error('تعذر الحفظ', 'رقم الهوية مسجّل مسبقاً.');

        }
        console.error(error);
        toast.error('تعذر الحفظ', 'حدث خطأ أثناء حفظ البيانات، حاول مرة أخرى.');
      }
    },
  });
}
```

`displacedFields()` itself is unchanged — `families` passed in already
