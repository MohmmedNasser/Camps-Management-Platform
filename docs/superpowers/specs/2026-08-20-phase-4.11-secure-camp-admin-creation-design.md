# Phase 4.11 — Secure Camp Admin Account Creation — Design

**Status:** approved for implementation (inline execution, no subagents)
**Page in scope:** `pages/camp-admins.html` (Super-Admin-only in `PAGE_ACCESS`). Unblocks the one operation Phase 4.10 deferred: "إضافة مسؤول" (create a new Camp Admin account).

## 1. Investigation summary

### 1.1 What Phase 4.10 already decided (re-verified, not re-litigated)

`docs/superpowers/specs/2026-08-19-phase-4.10-camps-camp-admins-design.md` §1.3/§4 and `BACKEND.md` §26 already scoped this exact gap and named the fix:

- The only path that creates an `auth.users` row from the browser is `supabase.auth.signUp()`, which replaces the calling session — unusable for admin-creates-admin.
- The correct fix is "a new Edge Function using the `service_role` key server-side... that verifies the caller is `super_admin`, calls the Auth Admin API (`auth.admin.createUser`), and immediately promotes the resulting profile row to `role='camp_admin'`."
- Suggested name: `admin-create-camp-admin`.
- `camp-admins.js`'s `[data-create]` handler currently opens an explanatory dialog (`openModal` with a warning `alert()`) instead of a form. The mock-era create form already exists and is fully built: `campAdminFields(values, {camps, isNew:true})` renders name/email/phone/campId/status/**password**, and `campAdminSchema({isNew:true, isDuplicateEmail})` validates it. Nothing needs to be designed here — it needs to be **connected**.

This phase re-verified all of §1.2's live findings itself (below) rather than trusting the year-old-in-doc-time snapshot, since the brief requires checking the live project directly.

### 1.2 Live schema/RLS/trigger findings (re-verified live against `qlvftlecwoqmvtagaykr`, 2026-09-24)

- **`private.handle_new_user()`** (`AFTER INSERT ON auth.users`, `SECURITY DEFINER`) inserts a `profiles` row with `role='displaced'` and `status='pending'` **hardcoded** ("never read from user metadata" — a comment in the function itself) plus a `user_preferences` row, both `ON CONFLICT DO NOTHING`. This fires **synchronously inside `auth.admin.createUser()`'s own request** — by the time `createUser()` resolves, the profile row already exists with the wrong role/status. Consequence: the Edge Function must **UPDATE** the profile afterward, never INSERT (a second INSERT would silently no-op on the conflict).
- **`private.guard_profile_privileges()`** (`BEFORE UPDATE ON profiles`) first checks `private.is_browser_session()`, which is `session_user = 'authenticator' AND jwt.role <> 'service_role'`. A request authenticated with the service-role key sets the JWT role claim to `service_role`, so `is_browser_session()` is `false` and the trigger `return new`s immediately — **no restriction applies to a service-role write**. This is what makes "one UPDATE, no RPC" safe: the same trigger that stops a Camp Admin from self-promoting over PostgREST does not fire for the privileged client.
- **`profiles_camp_scope_valid`** CHECK: `role='camp_admin' ⇒ camp_id IS NOT NULL` (and the inverse for `super_admin`/`displaced`). A real DB-level backstop if the Edge Function's own camp validation is ever wrong.
- **`profiles_id_fkey`**: `FOREIGN KEY (id) REFERENCES auth.users(id) ON DELETE CASCADE`. Deleting the `auth.users` row (rollback path) removes the `profiles` row for free — no separate cleanup query needed on that side. `user_preferences.user_id` is likewise `CASCADE` (confirmed in Phase 4.10's own notes, re-confirmed live).
- **RLS on `profiles`**: `profiles_select_own_or_admin` lets any authenticated user read `id = auth.uid()` — enough for the Edge Function's caller-scoped client to read the caller's **own** `role`/`status` without needing `service_role` for the authorization check itself.
- **`account_status` enum**: `pending, approved, rejected, active, disabled`. **`app_role` enum**: `super_admin, camp_admin, displaced`. Both match `core/config.js`'s `STATUS`/`ROLES` constants exactly.
- **Existing camp admin accounts** (unchanged since Phase 4.10): `admin@camps.ps` / `nour@camps.ps` (active), `raed@camps.ps` (disabled) — all `email_confirmed_at` set. **3 camps**, all `status='active'`.
- **`get_advisors` baseline**: 6 `authenticated_security_definer_function_executable` WARNs (one per existing privileged RPC, including Phase 4.10's `get_camp_admin_accounts`) + 1 pre-existing `auth_leaked_password_protection` WARN. This phase adds **no new SQL function**, so this baseline must be identical after implementation — confirmed as part of verification (§6).
- **No migration exists or is needed.** `list_migrations` shows nothing past Phase 4.10's two entries. Nothing above requires a schema change: the trigger, the guard, the CHECK, the FK and the RLS policy already do exactly what this phase needs.

### 1.3 Edge Function conventions already established (Phase 3)

Three functions exist today — `documents-upload`, `documents-access`, `documents-delete` — all `verify_jwt: true`, all Cloudinary-only, all built on the same three shared modules under `supabase/functions/_shared/`:

- **`_shared/supabase-client.ts`**: `callerClient(authHeader)` builds a client scoped to the caller's own JWT (publishable key + the `Authorization` header forwarded verbatim); `callerUser(client, authHeader)` resolves the caller via `auth.getUser(token)`, returning `null` on any missing/invalid token. **No existing function builds a service-role client** — this phase is the first to need one, since every prior function did all of its DB work through the caller-scoped client (RLS did the authorization). `SUPABASE_URL`/`SUPABASE_ANON_KEY` arrive pre-injected by the platform, per that file's own header comment; `SUPABASE_SERVICE_ROLE_KEY` is documented Supabase platform behavior as an equally auto-injected Edge Function secret (same mechanism, never configured via `secrets set` — confirmed by `list_edge_functions` showing zero project secrets set today, since none of the three Cloudinary functions' secrets appear there either — those are configured separately as documented in `BACKEND.md`'s Phase 3 section, orthogonal to this).
- **`_shared/cors.ts`**: static `corsHeaders`, already including the `x-application-name`/`x-supabase-api-version` headers that Phase 4.8 discovered a real browser preflight needs. Reused verbatim.
- **`_shared/http.ts`**: `jsonResponse`/`errorResponse({code, message})`, `ErrorCode` a closed string union. This phase adds one new member, `'duplicate'`, for the duplicate-email case — the only content change to a shared file, and it is purely a compile-time type addition (no runtime behavior for the other three functions changes, and each function gets its own bundled copy at deploy time — confirmed by inspecting `get_edge_function('documents-upload')`'s stored `files`, which shows a private `_shared/*.ts` copy per function, not a shared runtime module).
- **Frontend calling convention**: `assets/js/supabase/cloudinary.js` calls Edge Functions via the shared `client.functions.invoke(name, {body})` (never a second client), and maps the `{error:{code,message}}` failure body to the existing `DataAccessError`/`ErrorType` convention with a small local `EDGE_ERROR_TYPES` map + `mapFunctionError()`. This phase's `createCampAdmin()` (new, in `assets/js/supabase/profiles.js` — the existing home for every other camp-admin data-access function) follows the identical shape, with its own small `EDGE_ERROR_TYPES` (adds `duplicate: ErrorType.DUPLICATE`, which already exists in `errors.js`).
- **Deployment shape**: `mcp__supabase__deploy_edge_function` is the only deployment path available in this environment (no local Supabase CLI session). Inspecting the live `documents-upload` function's stored files confirms the bundle nests the entrypoint one level below its shared deps (`source/index.ts` next to a sibling `_shared/` directory), exactly reproducing the local repo's own `supabase/functions/<name>/index.ts` importing `../_shared/*.ts` from `supabase/functions/_shared/`. This phase deploys with `entrypoint_path: 'index.ts'` and `files` named `index.ts` + `_shared/cors.ts` + `_shared/http.ts` + `_shared/supabase-client.ts` (no function-name prefix), matching that structure. Verified after first deploy by re-fetching the function and confirming it resolves (§6, Edge Function tests) rather than assumed blind.

### 1.4 Request contract, decided from what already exists

`campAdminFields(values, {camps, isNew:true})` already collects **name, email, phone, campId, status, password** — this is not a new design decision, it is the pre-existing (unused) mock-era create form, which the brief says to reuse rather than redesign. This settles the "password vs. invitation" question: the product already chose **admin-created password accounts** (a password field with the hint "6 أحرف على الأقل، يغيّرها المسؤول بعد أول دخول" — the admin changes it after first login), matching exactly how `supabase/seed/seed.mjs` creates every demo account (`auth.admin.createUser({email, password, email_confirm:true, user_metadata:{full_name,phone}})` then a profile UPDATE). No invitation-email flow is introduced; none exists elsewhere in this project to be consistent with, and inventing one would be new UI the brief prohibits.

## 2. Architecture

```
Super Admin browser (camp-admins.html, "إضافة مسؤول")
        │  campAdminFields(isNew:true) + campAdminSchema(isNew:true)  — UNCHANGED UI
        ▼
assets/js/supabase/profiles.js  createCampAdmin({fullName,email,phone,password,campId,status})
        │  client.functions.invoke('admin-create-camp-admin', { body })
        │  (supabase-js attaches the Super Admin's own access token automatically)
        ▼
supabase/functions/admin-create-camp-admin/index.ts
        │
        │ 1. callerClient(authHeader) + callerUser()        → 401 if no/invalid caller
        │ 2. caller.from('profiles').select('role,status')
        │    .eq('id', user.id)                              → 403 unless role=super_admin AND status=active
        │ 3. parse + validate body server-side                → 400 on any bad field
        │ 4. serviceClient: camp exists?                      → 400 if not
        │ 5. serviceClient.auth.admin.createUser({email,
        │    password, email_confirm:true, user_metadata})    → 409 'duplicate' on email collision
        │ 6. serviceClient.from('profiles').update({
        │    full_name, phone, role:'camp_admin', camp_id,
        │    status}).eq('id', newUser.id)                    → on failure: deleteUser(newUser.id), 500
        ▼
201 { admin: { id, fullName, email, phone, campId, status, createdAt } }
        ▼
camp-admins.js: close modal → toast.success → load(session)   — refetches listCampAdminAccounts()
```

The **only** privileged client is created inside the Edge Function, from `Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')`, and is never returned, logged, or otherwise observable outside that one module-scope function call. The caller-identity check (step 2) runs on **every** invocation, using the caller-scoped client — the service-role client is only ever touched after that check passes.

## 3. Request/response contract

**POST `/functions/v1/admin-create-camp-admin`**, `Authorization: Bearer <caller's access token>` (attached automatically by `client.functions.invoke`).

Request body:
```json
{
  "fullName": "string, required, ≥5 chars (matches campAdminSchema's minLength(5))",
  "email": "string, required, RFC-shaped email",
  "phone": "string, required, matches ^[0-9+\\-\\s]{6,20}$ (same pattern as the profiles_phone_format CHECK)",
  "password": "string, required, ≥6 chars (matches auth.minimum_password_length)",
  "campId": "string, required, UUID shape, must reference an existing camps.id",
  "status": "'active' | 'disabled', required"
}
```

No `role` field is ever read from the body — the created role is `'camp_admin'`, hardcoded in the one `UPDATE` statement. A body containing `{"role":"super_admin", ...}` is authorization-inert: that key is simply never destructured.

Success `201`:
```json
{ "admin": { "id": "uuid", "fullName": "string", "email": "string", "phone": "string", "campId": "uuid", "status": "active|disabled", "createdAt": "timestamptz" } }
```

Failure (matches `_shared/http.ts`'s existing `{error:{code,message}}` shape):

| HTTP | `code` | When |
|---|---|---|
| 401 | `unauthorized` | missing/invalid bearer token |
| 403 | `forbidden` | caller authenticated but not an active `super_admin` |
| 400 | `validation` | missing/malformed field, or `campId` doesn't reference an existing camp |
| 409 | `duplicate` | email already belongs to an `auth.users` row |
| 500 | `database` | `createUser`/profile-`UPDATE` failed unexpectedly (post-cleanup attempted for the latter) |

Every message is Arabic and generic enough to carry no backend detail (no SQLSTATE, no constraint name, no Cloudinary-style upstream text — there is no upstream service here).

## 4. Authorization model

Independent of `PAGE_ACCESS`/`can()` (UX-only, per `core/auth.js`'s own header comment) and independent of RLS (the service-role client bypasses RLS by construction). The **only** authorization boundary for this privileged operation is the Edge Function's own explicit check, run on every request, before the service-role client is ever constructed:

```
caller = callerUser(callerClient(authHeader), authHeader)
if caller is null → 401
profile = callerClient.from('profiles').select('role,status').eq('id', caller.id).maybeSingle()
if profile is null OR profile.role != 'super_admin' OR profile.status != 'active' → 403
```

This mirrors `private.is_super_admin()`'s own definition (`role='super_admin' AND status='active'`) exactly, read through the caller's own RLS-scoped visibility of their own row (`profiles_select_own_or_admin`), so no `service_role` access is needed for the check itself — only for the two writes that follow it.

## 5. Failure / rollback strategy

Ordered to make the failure window as small as possible:

1. **All input validation, including camp existence, happens before `auth.admin.createUser()` is called.** This means the only way a Auth user can be created and then need to be rolled back is a genuinely unexpected error on the subsequent `profiles` `UPDATE` (e.g. a transient DB error) — not a validation mistake, which is now impossible to reach that far.
2. If `auth.admin.createUser()` itself fails (including the duplicate-email case), nothing was created — return the mapped error, no cleanup needed.
3. If the `UPDATE` fails or returns no row after a successful `createUser()`, the function calls `serviceClient.auth.admin.deleteUser(newUserId)` — which cascades away the trigger-created `profiles`/`user_preferences` rows via `ON DELETE CASCADE`. If **that** call also fails, the function logs the orphaned user id server-side (`console.error`, id only — an Edge Function log, never a client-visible response) and returns a generic 500. This is the one theoretically-possible-but-practically-near-impossible orphan case (would require the service-role `UPDATE` AND the service-role `deleteUser` to both fail); it is documented here rather than papered over, per the brief's explicit instruction to document rather than fake a guarantee that can't be made absolute.

## 6. Testing strategy

Two new suites, same conventions as every `phase4.*-verification.test.mjs`/`phase4.*-role-authorization.test.mjs` pair (local static server + Playwright + an independent `service_role` client + the repo-root `.env` loader):

- **`supabase/tests/phase4.11-camp-admin-creation-security.test.mjs`** — role/authorization boundary, independent of any frontend code (calls the Edge Function directly via `fetch`/`supabase-js .functions.invoke` with different bearer tokens): `super_admin` succeeds; `camp_admin` / `displaced` / anonymous (no token) / malformed token all rejected with **no `auth.users` row and no `profiles` row created** (checked independently via the service client after each attempt); role-tampering (`{role:'super_admin', ...}` in the body) still creates only a `camp_admin`; invalid/nonexistent `campId` rejected, no user created; malformed JSON body rejected; missing required fields rejected one at a time; a grep-based scan of every file under `assets/` for the literal strings `service_role`/`SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_SECRET_KEY` value, asserting none exist; a Playwright network-log check on the real create flow asserting no request ever carries the service-role key.
- **`supabase/tests/phase4.11-camp-admin-creation-verification.test.mjs`** — the real UI, real browser, real backend, real cleanup: login as `super@camps.ps`, open `camp-admins.html`, click "إضافة مسؤول", confirm the form (not the old deferral dialog) opens, submit valid data with a disposable `phase411-fixture-<timestamp>@example.com` address, wait for success, confirm the row appears in the real list, confirm `auth.users`/`profiles` state independently (`profiles.id = auth.users.id`, `role='camp_admin'`, `camp_id` = selected camp, `status` as chosen), confirm the Super Admin's own session (their `auth.uid()`, read via the still-open page) is unchanged; a duplicate-email attempt against that same fixture address rejected with no second row of either kind; a page refresh keeping the record; `finally`-block cleanup removing the fixture via `serviceClient.auth.admin.deleteUser()` (which cascades the profile) regardless of where the test failed.

Both suites are appended to `supabase/package.json`'s `test:all` script, following the exact pattern every prior phase used to register itself.

## 7. Security boundaries (explicit)

1. `service_role` exists only as `Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')` inside `admin-create-camp-admin/index.ts`'s own function scope — never assigned to a module-level export, never logged, never included in a response body.
2. The Edge Function re-derives the caller's role from the database on every call; it never trusts a role/claim carried in the request body.
3. `camp-admins.html`'s route guard (`PAGE_ACCESS`, unchanged) is UX-only, as already documented; the real boundary is §4 above, verified independently of any frontend code in the security suite.
4. No SQL migration, no new `SECURITY DEFINER` function, no RLS policy change — `get_advisors` must show the identical Phase 4.10 baseline (6 `authenticated_security_definer_function_executable` + 1 `auth_leaked_password_protection`) after this phase, confirmed in verification.
5. CORS reuses the exact `_shared/cors.ts` headers already proven against a real browser in Phase 4.8 (including the `x-application-name` fix) — no new CORS surface to get wrong.

None for the creation flow itself — this phase's whole purpose is to un-defer it.
