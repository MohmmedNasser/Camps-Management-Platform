# Phase 4.14 — Displaced Notifications in Dashboard & Header — Design

## 1. Goal

Remove the last two mock notification dependencies for the displaced role, both explicitly deferred by Phase 4.13 (§6/§7 of `2026-09-24-phase-4.13-displaced-own-pages-design.md`):

1. `dashboard.js`'s displaced-view "الإشعارات غير المقروءة" stat.
2. `ui/layout.js`'s shared header notification bell/dropdown, for the displaced role only.

Camp Admin and Super Admin behavior, `notifications.html` (already real since Phase 4.13), and every other page must be unaffected.

## 2. Current mock behavior (confirmed by reading the code)

**`dashboard.js` line 326** (`displacedView()`):
```js
${statCard({ label: 'الإشعارات غير المقروءة', value: formatNumber(select.unreadNotificationCount(session.id)), ... })}
```
`select.unreadNotificationCount(session.id)` is `core/selectors.js`'s mock function (`store.notifications.count(row => row.userId === userId && !row.read)`) — always 0 for a real session, since no mock `notifications` row's `userId` ever matches a real Auth UUID.

**`dashboard.js`'s `collect()`** also computes, for *all three* roles: `notifications: select.notificationsFor(session.id).slice(0, 4)`. This value is **never read** by `displacedView()`, `campAdminView()`, or `superAdminView()`, nor by `drawCharts()`/`wire()` — confirmed by reading the full 408-line file. It is dead code, left over from before some earlier redesign. It stays mock and is silently wrong for every real account.

**`ui/layout.js`'s `mountShell()`**:
```js
const notifications = notificationsFor(session.id);      // core/selectors.js, mock
const unread = unreadNotificationCount(session.id);       // core/selectors.js, mock
```
runs synchronously for **every page, every role** (Camp Admin, Super Admin, Displaced). `shellMarkup()` renders `notifications`/`unread` into the header bell dropdown and badge. For a real session this is always `[]`/`0` — the bell has been silently empty for every real account of every role since Phase 4.1.

`wireUserMenu()`'s "تعليم الكل كمقروء" (mark-all-read) button writes directly to the mock store:
```js
store.notifications.list((row) => row.userId === session.id && !row.read)
  .forEach((row) => store.notifications.update(row.id, { read: true }));
window.location.reload();
```
Real notifications are never touched by this handler for any role — it always operates on the empty mock collection.

Clicking a notification row in the dropdown is (and has always been) a plain `<a href>` navigation — no mock or real "mark as read on click" behavior exists today, in either version.

## 4. Decisions

### 4.1 Reuse only — no new backend, no new data-access functions

Both target surfaces are covered by functions that already exist and are already correct:
- Dashboard stat → `unreadNotificationCount()`.
- Header list → `listNotifications({ pageSize: 5 })` (badge) + `unreadNotificationCount()` (count) — matches "don't fetch the full list solely for a count" (a count-only PostgREST call, `head: true`, is cheaper than fetching rows).

One helper is added, not a new query: `mapNotificationRow()` (currently a **local, unexported** function inside `assets/js/pages/notifications.js`) moves to `assets/js/supabase/notifications.js` and is exported. This is the exact reusable mapper the brief asks to look for (§ "Do not duplicate notification mapping logic"). `notifications.js` (page) is updated to import it instead of redefining it. This removes the one duplication risk this phase would otherwise introduce (dashboard/header would each need the same `{id, type, title, text, createdAt, read, href}` shape).

No `getNotificationsForDashboard()` / `getNotificationsForHeader()` / `getNotificationsForBell()` is created, per the brief's explicit instruction.

### 4.2 Dashboard: extend `getDisplacedDashboard()`, don't touch `dashboard.js`'s other branches

`assets/js/supabase/dashboard.js`'s `getDisplacedDashboard(session)` gains one more field, `unreadNotifications`, fetched via `unreadNotificationCount()` (imported from `./notifications.js`) **in parallel with, not gated behind, family/person resolution** — a notification's `recipient_id` is `auth.uid()` itself, entirely independent of whether `family_member_id`/`family` resolve. All three of the function's existing early-return shapes (`EMPTY_DISPLACED_DASHBOARD`, the no-family-id branch, the no-family branch) are updated to still carry a real `unreadNotifications` count rather than defaulting it to 0 by construction, so a profile with no family link still shows its real unread count.

`dashboard.js`'s `collect()` for the `ROLES.DISPLACED` branch drops the dead `notifications: select.notificationsFor(session.id).slice(0, 4)` line (§2 — proven unused by every view function) since `collect()` now returns `real` unmodified. **Camp Admin and Super Admin branches keep their identical dead line unchanged** — touching them is out of scope (Rule 5) and they are not part of this phase's mock-removal target; removing dead code there would be a gratuitous, unrelated cleanup this phase must not perform. `select.unreadNotificationCount` becomes unused inside `dashboard.js` after this edit but `select.notificationsFor` stays used by the other two branches, so the `import * as select from '../core/selectors.js'` and `import * as store` stay as they are (`store.load` is still used).

`displacedView()` swaps `select.unreadNotificationCount(session.id)` for `data.unreadNotifications` (already resolved during `collect()`, no new async call inside the render function — render functions in this codebase are always synchronous over already-fetched data, matching every other stat card on the page).

### 4.3 Header: role-branch inside `mountShell()`, Camp Admin/Super Admin untouched

**Decision: displaced role only, this phase.** `ui/layout.js`'s `mountShell()` gains one local async helper:

```js
async function resolveNotifications(session) {
  if (session.role !== ROLES.DISPLACED) {
    return { notifications: notificationsFor(session.id), unread: unreadNotificationCount(session.id) };
  }
  try {
    const [{ rows }, unread] = await Promise.all([
      listNotifications({ pageSize: 5 }),
      fetchUnreadNotificationCount(),
    ]);
    return { notifications: rows.map(mapNotificationRow), unread };
  } catch (error) {
    console.error(error);
    return { notifications: [], unread: 0 };
  }
}
```

(`fetchUnreadNotificationCount` is the real `unreadNotificationCount` from `../supabase/notifications.js`, imported under a distinct local name because `../core/selectors.js` already exports a same-named mock function that Camp Admin/Super Admin keep using — both names coexist in the same module, never conflated.)

`mountShell()` becomes `const { notifications, unread } = await resolveNotifications(session);` in place of the two synchronous mock calls, then proceeds exactly as before. `mountShell` is already `async` and every one of its ~30 callers already does `await mountShell(...)` (confirmed by the existing page-module convention documented in `CLAUDE.md`), so this introduces no new await point at any call site — only inside the function already returning a Promise.

**Why not migrate Camp Admin/Super Admin too, even though the same table/RLS trivially supports them** (`notifications.html` already proves this uniformly for all three roles): the brief's Rule 2 sets the default scope to displaced-only unless a broader migration is *required* to preserve correctness, and it explicitly says not to "automatically migrate all three roles" just because the backend allows it. Leaving Camp Admin/Super Admin exactly as they are today is strictly zero-risk (unchanged code path, unchanged behavior) versus a same-phase, same-diff migration of a component every other role also renders on every page. This is recorded as a known limitation (§7), matching Phase 4.13's own explicit deferral of this exact file for this exact reason.

Fallback on failure: if the real fetch throws (network error, RLS/auth edge case), the header renders with `notifications: []`/`unread: 0` and logs the error — the same "safe empty state, not a crash" pattern used elsewhere in this codebase (`errorState()` for full-page failures; a shared per-page-load header widget cannot render a full error state without breaking every page, so an honest empty state is the correct fallback here, never a fabricated non-zero number).

**Mark-all-read** (`wireUserMenu()`'s `[data-read-all]` handler) gains a role branch:
```js
on(readAll, 'click', async () => {
  if (session.role === ROLES.DISPLACED) {
    try { await markAllNotificationsRead(); } catch (error) { console.error(error); }
  } else {
    store.notifications.list((row) => row.userId === session.id && !row.read)
      .forEach((row) => store.notifications.update(row.id, { read: true }));
  }
  window.location.reload();
});
```
`markAllNotificationsRead()` already exists (`assets/js/supabase/notifications.js`, used by `notifications.html` since Phase 4.13) and is RLS-safe (`notifications_update_own`, scoped to `auth.uid()`).

No other header behavior changes: clicking a notification still just navigates (no click-to-mark-read is added — not in the existing UI, and adding one would be a redesign the brief forbids); there is still no per-item read/unread toggle in the dropdown (that control only exists on `notifications.html`, unchanged); there is still no delete/dismiss control in the header (never existed there).

### 4.4 Read/unread operations actually implemented this phase

| Operation | Supported by RLS? | Used where |
|---|---|---|
| Read own unread count | Yes (`SELECT`, RLS-scoped) | Dashboard stat, header badge |
| Read own recent notifications | Yes (`SELECT`, RLS-scoped) | Header dropdown |
| Mark all own notifications read | Yes (`UPDATE`, RLS-scoped, trigger-guarded) | Header "تعليم الكل كمقروء" |
| Mark one read / unread | Yes (`UPDATE`) | Already implemented on `notifications.html` (Phase 4.13) — not touched here, header has no per-item control |
| Delete / dismiss | **No** (no DELETE policy) | Not implemented anywhere, unchanged |
| Insert | **No** (no INSERT policy for `authenticated`) | Not implemented anywhere; notifications are created server-side (e.g. `approve_registration_request()`), unchanged |

## 5. Identity chain (unchanged, reused as-is)

`session.id` (from `core/auth.js`'s `getSession()`, sourced from Supabase Auth's own `auth.uid()`) is the only identity input, for every role. Neither the dashboard stat nor the header ever reads a URL parameter, `localStorage` value, or DOM attribute to decide whose notifications to fetch. RLS (`recipient_id = auth.uid()`) is the actual boundary in both directions (read and update) — the frontend's role check only decides *whether* to call the real functions at all, never *which rows* they return.

## 7. Deferred / known limitations (unchanged from Phase 4.13, restated)

1. **Header bell/dropdown for Camp Admin and Super Admin** stays mock this phase — §4.3 rationale. Both roles' notification data is real and RLS-ready (proved by `notifications.html`); migrating them is a natural, low-risk follow-up, deliberately not bundled into this phase.
2. **Delete/dismiss** — still no DELETE RLS policy on `notifications`; not implemented anywhere (unchanged from Phase 4.13).
3. **Click-to-mark-read** in the header dropdown — does not exist today (mock or real) and is not added; adding it would be a UI behavior change beyond "replace the data source."
4. Everything else Phase 4.13 already deferred (document edit/delete for displaced, Auth email change, non-editable `family_members` fields) is unrelated to this phase and unchanged.

## 8. Testing strategy

Two new suites, structurally identical to Phase 4.12/4.13's (`.env` loader, local static file server, `login()` Playwright helper, service-role client for independent derivation):

- **`supabase/tests/phase4.14-displaced-notifications-isolation.test.mjs`** — direct RLS probes with the four seeded displaced accounts (`ahmad`, `yousef`, `ibrahim`, `omar`) plus `admin@camps.ps`/`super@camps.ps` as the "must be unaffected" control group: each displaced account can read/count only its own `notifications` rows; cross-account reads return nothing; anonymous reads are rejected; an UPDATE attempt against another account's notification id is rejected/no-ops (zero rows affected, not a thrown error — matches actual Postgres/RLS semantics, not an assumed exception); URL/query-string spoofing on `dashboard.html`/any page cannot change whose count renders (there is no notification-related URL parameter to spoof to begin with — asserted directly); session preservation (`auth.uid()` unchanged after loading the dashboard and after opening the header dropdown); Camp Admin/Super Admin dashboards and headers render unchanged (still their own mock/real-non-notification data, no regression).
- **`supabase/tests/phase4.14-displaced-notifications-verification.test.mjs`** — DB-vs-UI: for each of the four displaced accounts, an independent service-role (or second RLS-scoped client) query of `notifications` (`count(*) where recipient_id = X and not is_read`, and the 5 most recent rows ordered by `created_at desc`) is compared against the rendered dashboard stat and the rendered header badge/dropdown; both must agree with each other and with the DB. A dedicated fixture account (created via `serviceClient.auth.admin.createUser`, approved, family-linked or not as needed) gets 2–3 notification rows inserted directly as `service_role` (bypassing the browser-only trigger guard, exactly as `guard_notification_update`'s own `is_browser_session()` check anticipates) to exercise: initial unread count, mark-all-read reducing the count to 0, a reload showing the persisted 0, and confirmation that another fixture/seeded account's count is untouched by the first account's mark-all-read call. Cleanup in a `finally`: delete the fixture's notification rows and the fixture Auth user/profile; re-verify Camp Admin's/Super Admin's/the seeded displaced accounts' own notification counts are back to the pre-phase baseline in §3 (no debris, no permanent state change to seed data — seeded rows are only ever read, never mutated by these tests except through the fixture account's own rows).

Browser/responsive/security checks (per the brief) are run manually via the same Playwright `login()` helper pattern at the six breakpoints, folded into the verification suite's assertions (`page.setViewportSize` before the relevant `page.goto`) rather than as a separate suite, matching how Phase 4.12/4.13 folded their own responsive/console/security checks into their two suites rather than adding a third.

`npm run test:all` (`supabase/package.json`) is extended with both new suites and must stay green end-to-end.
