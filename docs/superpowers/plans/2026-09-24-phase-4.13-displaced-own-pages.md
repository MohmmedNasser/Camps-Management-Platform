# Phase 4.13 — Displaced Person Own Pages Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (project owner has explicitly prohibited Subagent-Driven Development for this phase — no fresh subagent per task). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Connect `family-details.html` ("أسرتي"), `profile.html`, `documents.html`, `aid.html` and `notifications.html` to real Supabase data for the displaced-person role, without reintroducing `session.displacedId`, without regressing Camp Admin/Super Admin behavior, and with RLS as the only real security boundary.

**Architecture:** Reuse the Phase 4.12 identity chain (`session.familyMemberId → getDisplacedPerson() → getFamilyByReferenceCode()`) via a new `getOwnFamily(session)` composition helper. Add small, structurally-symmetric data-access functions where a real gap exists (`getFamilyDocuments`, `getFamilyAidDistributions`, `markNotificationUnread`, `updatePassword`); reuse every existing real function/predicate otherwise (`getFamilyAidHistory`, `listDocuments`, `matchesDocumentFilters`, `matchesAidFilters`, `getOwnProfile`, `updateOwnProfile`, the three Cloudinary Edge Functions unmodified).

**Tech Stack:** Vanilla ES modules, Supabase JS client (`@supabase/supabase-js`), Node's built-in test runner + Playwright for verification (`supabase/tests/*.test.mjs`).

**Spec:** `docs/superpowers/specs/2026-09-24-phase-4.13-displaced-own-pages-design.md`

## Global Constraints

- Never read/write `session.displacedId` anywhere in this phase's diff.
- Every real query relies on RLS as the actual authorization boundary; `can()`/`inScope()` in `core/auth.js` are UX-only and are never the last line of defense.
- No migration, RLS policy, trigger, RPC, or Edge Function is created or modified.
- No `service_role` key, Supabase DB password, or Cloudinary secret may appear in any file under `assets/` or in any committed test fixture.
- Camp Admin and Super Admin code paths on all five pages are touched only where explicitly justified in the spec (§4.2 and §4.5 — `profile.html`'s account section and `notifications.html`, both role-agnostic already).
- `dashboard.js` and `ui/layout.js` are not modified (spec §6).
- `SEED_VERSION` in `data/mock-data.js` is not touched — this phase adds no mock-data shape changes.
- Arabic UI copy, existing HTML structure, existing responsive/table-to-card behavior are preserved verbatim except where a control is intentionally removed (notification delete/dismiss, spec §4.5) or disabled (profile email field, spec §4.2).

## Review Focus

- A displaced session with `familyMemberId` set but the `family_members` row itself missing/unreachable (deleted, or an approved-but-unlinked profile, the same edge case Phase 4.12's isolation suite fixtures) — every one of the five pages must render a safe empty/not-found state, never throw.
- A displaced account whose family has zero aid, zero documents, or zero notifications — each page's existing empty-state copy must still be the one that renders (not a crash, not the search/filter empty state).
- Two displaced accounts sharing a camp but not a family (`ahmad@camps.ps`/`yousef@camps.ps`) — every one of the five pages, not just the dashboard, must prove isolation.
- A wrong "current password" on the profile password form must produce the existing field-level Arabic error, not a generic toast, and must not throw an unhandled promise rejection.
- Marking a notification read/unread/all-read when the account has notifications from a real seeded flow (`أحمد محمود الشريف`, 3 seeded rows, 2 unread) must leave `is_read`/`read_at` exactly matching what the trigger (`guard_notification_update`) allows, verified by an independent query — and the DB-vs-UI suite must restore that account's seeded read/unread state afterward so later test runs (including this same suite's re-run) start from the same fixture data.

- [ ] **Step 1: Add `getOwnFamily(session)` to `assets/js/supabase/families.js`**

Add the import and function (place after `getFamilyByReferenceCode`, before `deleteFamily`):


```js
/**
 * The signed-in displaced account's own family, resolved through the
 * Phase 4.12 identity chain (profiles.family_member_id -> family_members ->
 * families) — never a URL or localStorage value. Null when the account has
 * no family_member_id yet, or the linked family_member row has no family
 * (both states getDisplacedDashboard() already handles identically).
 */
export async function getOwnFamily(session) {
  if (!session?.familyMemberId) return null;
  const person = await getDisplacedPerson(session.familyMemberId);
  if (!person || !person.familyId) return null;
  return getFamilyByReferenceCode(person.familyId);
}
```

- [ ] **Step 2: Add `getFamilyDocuments(familyId)` to `assets/js/supabase/documents.js`**

Place directly after `getCampDocuments()`:

```js
/**
 * Every document belonging to one family, unpaginated — the real
 * displaced-person document list (Phase 4.13), structural sibling of
 * getCampDocuments() above (same DOCUMENT_SELECT, same mapDocumentRow).
 * RLS (documents_select_scoped's `is_displaced() AND family_id =
 * current_family_id()` clause) independently scopes every row to the
 * caller's own family regardless of the familyId argument.
 */
export async function getFamilyDocuments(familyId) {
  const client = requireClient();
  const rows = await run(
    client.from('documents').select(DOCUMENT_SELECT).eq('family_id', familyId).order('created_at', { ascending: false })
  );
  return rows.map(mapDocumentRow);
}
```

- [ ] **Step 3: Add `getFamilyAidDistributions(familyDbId)` to `assets/js/supabase/aids.js`**

Place directly after `getCampAidDistributions()`:

```js
/**
 * Every aid distribution the signed-in displaced account's own family
 * received (Phase 4.13) — the real "مساعداتي" list/summary/filter query,
 * structural sibling of getCampAidDistributions() above (same
 * DISTRIBUTION_SELECT, same mapAidDistributionRow), so
 * select.matchesAidFilters() (Phase 4.6) works unmodified against either
 * one's rows. No campId/familyId filter is applied at the query level: RLS
 * (aid_distributions_select_scoped's `is_displaced() AND
 * private.family_receives_distribution(id)` clause) already returns only
 * the caller's own family's distributions, and the nested
 * aid_distribution_families embed is independently RLS-scoped per row too
 * (aid_distribution_families_select_scoped), so a shared distribution's
 * OTHER beneficiary families never appear in `beneficiaries`/`familyDbIds`
 * here — a displaced viewer must not learn who else received the same aid.
 * familyDbId is kept for symmetry with getCampAidDistributions(campId) and
 * as a redundant, UX-only narrowing — never the security boundary.
 */
export async function getFamilyAidDistributions(familyDbId) {
  const client = requireClient();
  const rows = await run(
    client.from('aid_distributions').select(DISTRIBUTION_SELECT).order('distributed_on', { ascending: false })
  );
  return rows.map(mapAidDistributionRow).filter((row) => row.familyDbIds.includes(familyDbId));
}
```

```js
/**

 * session only (Phase 4.13) — never `params()`. Mirrors collectReal()
 * above (same getFamilyAidHistory()/listDocuments() calls, same local
 * mappers) with the identity source swapped and no cross-camp check
 * (unneeded: RLS + the identity chain already guarantee it's the caller's

async function collectOwn(session) {
  const family = await getOwnFamily(session);
  if (!family) return { family: null };

  const [aidRows, docsResult] = await Promise.all([
    getFamilyAidHistory(family._dbId),
    listDocuments({ familyId: family._dbId }),
  ]);

  return {
    family: { ...family, campName: session.campLabel },
    aid: aidRows.map(mapAidHistoryRow),
    documents: docsResult.rows.map(mapDocumentRow),
  };
}
```
