# Phase 4.5 — Camp Admin Displaced Persons Implementation Plan

> **Execution:** Inline execution only, in this session, on local `main` directly (per explicit user instruction — no worktree, no subagent-driven dispatch). Full code for every function below is already written out in the spec; this plan sequences the work and states the verification gate for each checkpoint.

**Goal:** Connect the Camp Admin's displaced-person flow (`displaced.html` list, `displaced-create.html`, `displaced-details.html`, `displaced-edit.html`) to real, camp-scoped Supabase data, with automated cross-camp isolation and DB-vs-UI verification, while leaving the Super Admin displaced list/detail and the displaced person's own dashboard/profile byte-for-byte unchanged.

**Architecture:** `family_members` IS the displaced-person table (BACKEND.md §2). Add `getCampDisplacedPersons`, `getDisplacedPerson` and `toFamilyMemberPayload` to `assets/js/supabase/family-members.js`; add `getFamilyIdsForAidFilter` to `assets/js/supabase/aids.js`; add `matchesDisplacedFilters` to `core/selectors.js`; add an opt-in `requireFamily` param to `record-forms.js`'s `displacedSchema()`. Give each of the four page modules a new Camp-Admin-only branch, mirroring the "one function gains a branch" shape Phase 4.4 used. RLS (`family_members_select/insert/update/delete_camp_admin`, all `is_camp_admin() AND camp_id = current_camp_id()`) is the real authorization boundary everywhere.

**Tech Stack:** Vanilla ES6 modules, Supabase JS client, Node's built-in test runner, Playwright.

**Spec:** `docs/superpowers/specs/2026-08-19-phase-4.5-camp-admin-displaced-design.md` (full code for every function/branch below is in §5–§6 of that file — this plan does not repeat it).

## Global Constraints

- Super Admin's displaced list/detail and the displaced person's own dashboard/profile — untouched, out of scope entirely.
- Delete/update/insert authorized by RLS alone — no client-side camp-id comparison is ever a security gate.
- Person creation goes through `addFamilyMember()` (existing Phase 2 RPC wrapper) only. `familyId` is required on the real create path (DB `NOT NULL` + CLAUDE.md domain rule 13) — the mock's "بدون أسرة" option is not offered on the real path.
- Family reassignment is not exposed on the real edit path (confirmed integrity gap: `family_members_promote_head` fires only `AFTER DELETE`, not on reassignment `UPDATE`).
- One export pipeline: `getCampDisplacedPersons() → matchesDisplacedFilters() → displacedExportRow() → DISPLACED_COLUMNS / exportSheet()`.
- No new/modified tables, columns, views, RPCs, triggers, RLS policies, or migrations.
- `Promise.all` for independent data requests within one page load.
- No `service_role`/secret in browser code; no RLS bypass; no hardcoded camp id; no cross-camp data fetched and filtered only in JavaScript.
- A genuinely empty camp renders the real `emptyState()`; export's existing "no rows" guard is unchanged.
- No push to any remote. Working tree stays clean at every checkpoint.
- Test accounts: `admin@camps.ps` (مخيم النور), `nour@camps.ps` (مخيم الرحمة), both password `123456`.
- Baseline before this phase: `npm run test:all` inside `supabase/`, 142/142 green.
