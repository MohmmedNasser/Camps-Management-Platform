# Phase 4.17 — Implementation plan

Design doc:
`docs/superpowers/specs/2026-09-27-phase-4.17-family-account-activation-design.md`.
Execute inline, no subagents. Branch: `phase-4.17-family-activation` (created).

## Self-review before starting

- **Auth user creation**: only inside the one Edge Function, using
  `service.auth.admin.createUser()`, exactly Phase 4.11's shape.
- **service-role usage**: confined to that one function; `consume_family_
  activation` is the only SQL function granted to `service_role` alone —
  double-checked its grant statement before moving on, since a mistaken
  grant to `authenticated` there would let any signed-in user hijack a
  profile's `family_member_id`.
- **Race conditions**: closed by `FOR UPDATE` inside `consume_family_
  activation`, not by anything in JS. Verified by a concurrent-request test
  in the security suite.
- **Duplicate accounts**: `already_activated` check + the unique
  `family_activation_tokens_one_active_idx` + `profiles.family_member_id`
  never overwritten for an already-linked head.
- **Token reuse**: `used_at` set only inside the atomic consume step, after
  `createUser` succeeds — never earlier.
- **Cross-camp isolation**: `generate_family_activation_token`/`get_family_
  activation_status` re-derive `current_camp_id()` from the DB every call.
- **Password handling**: never logged, never echoed in any response body,
  never written to a table — only ever passed to `auth.admin.createUser`.
- **Test cleanup**: every test creates its own disposable family (via
  `create_family_with_members`) rather than touching seeded fixtures, and
  deletes the family (cascades members) + the created `auth.users` row in
  `finally`.

## Tasks

1. **Migration** `supabase/migrations/20260927000000_phase4_17_family_activation.sql`
   - `private.family_activation_tokens` table + indexes (unique `token_hash`,
     partial unique `family_id where used_at is null and revoked_at is null`).
   - `public.generate_family_activation_token(p_family_id uuid)`.
   - `public.get_family_activation_status(p_family_id uuid)`.
   - `public.verify_family_activation(p_token text, p_reference_code text, p_national_id text, p_birth_date date)`.
   - `public.consume_family_activation(p_token text, p_new_user_id uuid)`.
   - Grants: `generate_family_activation_token`/`get_family_activation_status`
     → `authenticated`; `verify_family_activation` → `anon, authenticated`;
     `consume_family_activation` → `service_role` only. Explicit `revoke all
     ... from public, anon, authenticated` on each function first (matches
     003's own documented default-privilege gap).
   - Apply via `mcp__supabase__apply_migration`, then re-run
     `mcp__supabase__get_advisors` (security) and diff against the 6-WARN
     baseline captured during investigation — expect exactly 3 new
     `authenticated_security_definer_function_executable` entries (or 2, if
     `verify_family_activation`'s `anon` grant doesn't also trigger the
     `authenticated`-worded lint — read the actual output rather than
     assuming) and nothing else new.

2. **Edge Function** `supabase/functions/activate-family-account/index.ts`
   - `verify_jwt: false` (anonymous — the caller has no session yet).
   - Body: `{ token, referenceCode, nationalId, birthDate, email, password }`.
   - Validate shapes server-side (never trust the frontend's own
     `bindForm`/`rules` validation) before calling anything.
   - `service.rpc('verify_family_activation', {...})` → map exception to
     `400 bad_activation` / generic Arabic message; `already_activated` field
     → `409 already_activated`.
   - `service.auth.admin.createUser({email, password, email_confirm: true,
     user_metadata: {full_name}})` → duplicate → `409 email_taken`.
   - `service.rpc('consume_family_activation', {p_token, p_new_user_id})` →
     on failure, `service.auth.admin.deleteUser(newUserId)` then `409
     bad_activation`.
   - `201 { ok: true }` on success. No session/token echoed back — frontend
     signs in itself with the credentials it already has.
   - Deploy via `mcp__supabase__deploy_edge_function`, remembering Phase
     4.11's bundling note (`entrypoint_path: 'source/index.ts'`, `_shared/`
     as a top-level sibling) if the flat layout fails the same way.

3. **Frontend data-access** `assets/js/supabase/family-activation.js` (new)
   - `generateActivationLink(familyId)` → `client.rpc('generate_family_activation_token', ...)`, returns `{ token, expiresAt }`, builds the full URL via `pageUrl('activate-family.html', { token })`.
   - `getActivationStatus(familyId)` → `client.rpc('get_family_activation_status', ...)`.
   - `activateFamilyAccount(payload)` → `client.functions.invoke('activate-family-account', { body: payload })`, its own `mapActivationFunctionError()` (same convention as `profiles.js`'s `mapCampAdminFunctionError()`).

4. **`core/auth.js`**: add `'family:activate': [ROLES.CAMP_ADMIN]` to `PERMISSIONS`.

5. **`family-details.js`**: in the Camp-Admin action row (real branch only,
   `collectReal`), add a "تفعيل حساب الأسرة" button gated on
   `can('family:activate')`, opening a modal (`ui/modal.js` `openModal`)
   that: on open, calls `getActivationStatus`; renders current state
   (none/active+expiry/used/revoked/expired) via the existing `badge()`/
   `definitionList()` components; if none-or-expired-or-revoked, offers
   "توليد رابط تفعيل" (or "توليد رابط جديد" if one existed), calls
   `generateActivationLink`, then shows the URL in a readonly input + a copy
   button (`navigator.clipboard.writeText`, toast on success) + expiry text;
   if already activated, shows that state instead with no generate action.
   No page redesign — same card/modal/badge/toast components already in use
   everywhere else in this file.

6. **Activation page** `pages/activate-family.html` + `assets/js/pages/activate-family.js` (new)
   - `pages/activate-family.html`: content-free shell, same `<script
     type="module">` pattern as every other page (font links, `main.css`).
   - `activate-family.js`: reads `?token=` via `params()`. No `mountShell()`/
     `guard()` — this must render for a signed-out visitor by design. Uses
     `authLayout()` (same visual shell as login/register) with a form:
     family reference code, national ID, birth date, email, password,
     confirm password — same `inputField`/`passwordField`/`bindForm`/`rules`
     components `register.js` already uses, `rules.password(6)` for the
     minimum length (matches the project's existing policy, not a new one).
     Empty/missing `?token=` → an inline error state, no form.
   - On submit: call `activateFamilyAccount`; on `already_activated`, show
     the message + a login link instead of a form error; on success, call
     the existing `login(email, password)` then `window.location.href =
     homeFor(session)` — no new session/redirect mechanism.
   - Add to `PAGE_ACCESS`? **No** — `guard()` is never invoked from this
     page, so `PAGE_ACCESS` is irrelevant to it (same reasoning as
     `login.html`/`register.html`, which also carry no `PAGE_ACCESS` entry).
     Do not add a `NAVIGATION` entry either — it is never linked to from
     inside the app shell, only reached via the emailed/shared token URL.
